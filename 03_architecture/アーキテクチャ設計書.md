## 1. 全体方針

**モジュラーモノリス ＋ 2 つの独立プロセス。**

| 構成要素 | 中身 | 独立させる理由 |
|---|---|---|
| **中核**（モジュラーモノリス） | Web ／ API ／ ワーカー | 会社モデルが全機能から参照されるため、分割すると分散モノリスになる |
| **取り込みサービス** | Python（docling / faster-whisper） | 言語が違う。入力＝ファイル・出力＝JSON で**型がまたがらない** |
| **Bridge** | Electron（顧客 PC 常駐） | 実行場所も配布経路も別 |

### 設計の 3 本柱

| 柱 | 内容 | 守り方 |
|---|---|---|
| **会社モデルが中心** | 目標・台帳定義・担当業務・組織・ポリシー・記憶を 1 つの定義に。画面も AI 社員も自動実行もそこだけを読む | 論理層と物理層の二層分離 |
| **関門で守る** | 外界に影響を与える経路を 8 本に絞り、必ず通らせる。**列挙で守らない** | CI の静的解析（迂回を検出） |
| **依存を閉じ込める** | 基盤 SDK は境界 7 ディレクトリの中でしか使えない | CI の import 境界検査 |

### 会話の配線（D-062・D-066・D-090・D-093・D-103・D-104）

```
  人 ⇄ 自分のAI ── Kaname の API（言う → 仕事を積む → Bridge が取る → 途中経過・確認・結末）── AgentChat 1 つが描く（D-103.1・D-103.4）
                       │
                       ├ 会話を出す 5 か所（会話モード・はじめの設定の聞き取り・たたき台・右パネル・AI社員とのやりとり）は同じ会話・同じ部品。違うのは最初のひとこと・入力欄の見本・添える文脈だけ（D-062・D-103.1・D-103.2）
                       ├ 右パネルは共通の枠（AppShell）が必ず出す。出さないのは会話モードだけ（D-103.3）
                       ├ 会話は人が「新しく話す」で分け、一覧（探す・星・名前・消す・記憶に残さない）から戻る。1 会話＝本人の Claude Code の 1 セッション（D-104.1。D-103.1 の「1 本」と D-062.5 の 3 層の整理を改めた）
                       ├ 返事は書きながら少しずつ出る（bridge_jobs.partial）。作業中は吹き出しの外に 1 行・手順・経過時間・道具の行（bridge_job_events: status / plan / tool）（D-104.8）
                       ├ 動いている間：止める（stop）・止めずに直す（steer＝次の区切りで Claude Code の標準入力に渡す）・順番待ち（queued の行・取り消すと cancelled）（D-104.9）
                       ├ 資料と画像：API が会社の置き場に置き（関門 C4）、Bridge が期限つきの署名 URL で受け取って作業場所に置く。保存先の鍵は AI に見せない（D-104.11）
                       ├ 許可：Claude と同じ公式のモード（--permission-mode）と 3 択。「いつも」は permission_rules → 許可の一覧として渡す。全部許可は本人が選んだ会話だけ（D-104.14）
                       ├ 使用量：Bridge が CLI の知らせから 5 時間の枠・週の枠を受け agent_usage_snapshots に最新を残す（D-104.16）
                       └ 部品は 1 組 ＝ messages.kind（question / approval / receipt / status / error …）。
                         選択肢・自信・引用・取り消し先も messages の列で持つ（D-066）
  承認カード・受領・取り消しは、画面が勝手に言わない。関門（C1 actions / C6 notify）の実行記録
  （action_runs・audit_events）から描く。「送った」は証跡があるときだけ出る
```

## 4. DB 設計方針

### 全テーブル共通の原則

| 項目 | 決定 | 後から入れられない理由 |
|---|---|---|
| 主キー | **UUID v7** | 連番はテナント分割・統合で衝突 |
| `tenant_id` | **全テーブル NOT NULL** | 後入れはデータ移行＋全 RLS 書き直し |
| `scope_id` | 共有され得るもの全部 | 後から共有機能を足すと全行の意味が変わる |
| 監査列 | `created_at` / `updated_at` / `created_by` / `updated_by` | 証跡が後から作れない |
| 論理削除 | `deleted_at` 既定 | 物理削除は監査で復元不能 |
| enum | **使わない。マスタ ＋ FK** | 値追加が migration ＋ 型再生成 ＋ 全分岐見直し |
| 多重度 | 中間テーブルを足せる形 | 1 対多 → 多対多は全面書き直し |
| バージョン | 会社モデルの構成物に付与 | 「いつ何が変わったか」が後から作れない |

### アクセス制御

```sql
-- ✗ 禁止（Supabase Auth に固定され、DB 層まで移行不能になる）
USING (tenant_id = (SELECT tenant_id FROM users WHERE id = auth.uid()))

-- ✓ 採用（Postgres 標準。どのクラウドでも動く）
USING (tenant_id = current_setting('app.tenant_id', true)::uuid)
```

API 層が全リクエスト冒頭で `SET LOCAL app.tenant_id / app.user_id / app.role` を発行。
**検証は「上流を故意に壊す」**（`SET` を飛ばして他テナントのデータが取れないことを確認）。正常系では RLS の有無が判別できません。


### 権限モデル（D-073）

権限は **誰に × 何に × どの層で × できること** の 4 つ組（`permissions`）。本人のもの（個人の範囲）は権限なしで自由＝RLS の `self_only` predicate で表し、行を作らない。
層は **会社ごと**（`layers`）：運営／会社／個人は固定、その間（部署・事業…）は会社が 0〜n 個作る。画面にもコードにも「部署」を固定名で書かない。
R3（担当者）・R4（閲覧のみ）も **自分のAI** を持ち（`clones`）、`abilities=view` の行で「見える」を持つ。見えないのが既定の設計にしない（L-010）。
運営（R6）は `ops_members` の権限（support / billing / catalog / admin）で、顧客テナントの行は **既定で読めない**（§2b）。

### 口座状態の出来事と失効（D-074・D-076.13・G-14）

退会・停止（休止）・権限変更・プラン変更（下げる）・層を消す・AI社員を消す・人が抜ける の 7 つは `account_events` の行になり、
`account_event_items` が **flow.json の全オブジェクト**について「消える／残る／移る・戻る／止まる／即失効」と引き継ぎ先を持つ。全部が done になるまで出来事は終わらない（引き継ぎ先を決めるまで消せない）。
失効は **`sessions` を全行 revoked** にする方式。API・Bridge・共有リンク・Webhook はトークンの期限ではなく `sessions` を見る（発行済み JWT が生き残る事故を構造で潰す）。
退会は 猶予（30 日・復元可）→ 完全消去 → `erasure_certificates` を自動発行して代表に送る。法令保管（`retention_holds`）の行だけ残す。

### 動的台帳（最難関）

**ハイブリッド（固定列 ＋ JSONB）を採用。実 DDL を採りません。**

| 方式 | 採用製品 | 不採用の理由 |
|---|---|---|
| 実 DDL | Teable / NocoDB / Baserow | 65 社 × 5 型 ＝ 325 テーブル。**RLS を動的生成する必要があり、1 つ漏れたらテナント越え**。DDL がロックを取る |
| EAV | — | JSONB より約 1.3 倍遅い。条件ごとに JOIN が増える |
| **JSONB ハイブリッド** | **採用** | 固定の中核 ＋ カスタム項目、という Kaname の形に合う |

```sql
ledger_records (
  id uuid, tenant_id uuid,          -- 固定：RLS
  definition_id uuid, scope_id uuid,
  stage_id uuid,                    -- 固定：ファネル集計
  amount numeric(18,4),             -- 固定：金額集計
  occurred_on date,                 -- 固定：期間集計
  assignee_id uuid,                 -- 固定：担当別
  data jsonb                        -- 可変：業界ごとの自由項目
)
```

**目標の集計に使う 4 列を固定列に出します。** ここが JSONB のままだとループが回りません。

**参照から取り込んだ 3 点**
1. NocoDB の**二層構造**（論理メタデータ層／物理層）を明示的な設計原則にする → 将来の方式差し替えが可能
2. Salesforce の**ピボット索引**を Postgres の**式インデックス自動生成**に翻訳（`is_filterable` の項目のみ・`CONCURRENTLY`）
3. 項目定義を **JSON Schema** で持ち、描画・検証・許可リストの 3 箇所に効かせる

**SQL インジェクション対策（4 点・CI で強制）**
許可リスト方式 ／ 演算子は固定 enum ／ 値は必ずバインド ／ 文字列連結を CI で禁止

### 探す（D-098・D-099）

**段階 1 は、自分のAI が探して読む。ベクトルは作らない**（D-099.1）。Claude Code も普段は索引を持たず、言葉で探して読み、足りなければ言い換えて探し直す。Kaname の「探す」（A21）も同じ形にする。

| 段 | やり方 | どこで |
|---|---|---|
| 言葉で探す | **PGroonga**（Supabase 標準の日本語の全文検索）で台帳・記憶・証跡の本文を引く（D-098.2） | DB |
| 言い換え・読んで選ぶ | 自分のAI（Claude・本人のサブスク）が検索語を広げて何度か引き、中身を読んで選ぶ。候補は行レベルの制御の内側だけ（D-098.3） | Bridge |
| 人が直接探す | 言葉の一致で探す | 画面 → API |

**ベクトル（意味の近さ）を入れる境**（D-099.2）：探すたびに件数と時間を記録し、**1 社の本文が 5 万件を超えた**、または **探すのに 20 秒以上かかったことが 1 週間に 10 回を超えた**ら、運営に知らせて入れる判断をする。

**実データで確かめて決める**（D-099.7）：高本さんの実データで答えが分かっている質問 20 個（言葉が一致しないものを半分以上）を自分のAI に探させ、**20 問中 17 問に届かなければ境を待たずにベクトルを足す**。

入れるときの形（D-098・D-099）:
- モデルは **Ruri v3**（日本語の JMTEB 77.24・Apache 2.0）。**作るのは本人の PC（Bridge）**。サブスクでも API でも同じ。**PC が無い会社だけ**、段階 2 のサーバーで同じモデル（D-099.3）
- **入れ方は Bridge と同じ**：人にダウンロードもインストールもさせない。Bridge が自分で取りに行き（配布元・sha256）、空き容量を先に確かめ、進み具合を窓と画面に出し、自己診断に「検索のモデル」の行を足し、壊れていればボタン 1 つで取り直す（D-099.4）
- ベクトルは `search_embeddings` に **モデル名・元の文の指紋・切れ端の番号** つきで持つ。モデルは `embedding_models`（使用中／作り直し中／退役）（D-098.4）
- **モデルを替える**：作り直し中で足す → Bridge が裏で全部作り直す → そろったら切り替え、古いものを消す。そろうまでは古いモデルで探す。画面・API・表の形は変わらない（D-098.5・D-099.6）
- 本文が直されたら、指紋が変わった行だけ作り直す（D-098.6）
- 入っていない・壊れている・Bridge が止まっている間は言葉の一致で探し、画面にそう出す（D-098.7・D-099.5）
- ローカル・CI の Postgres も pgvector と PGroonga の両方を入れた像にする（D-098.9）。ER図の `memories.embedding` はやめた（D-098.10）

## 7. 関門（choke points）── この設計の核

**「列挙で守るな。関門で守れ」**（正本：`.claude/rules/common/choke-points.md`）

| # | 関門 | ゲートウェイ | 関門の中で 1 回だけ書くもの |
|---|---|---|---|
| C1 | ネットワーク | `packages/actions/` | 認可・ポリシー・承認・サービス台帳判定・レート制限・証跡・課金・失敗時ハンドオフ |
| C2 | 永続化（書込） | `packages/db/` | テナント文脈・RLS 前提保証・監査列・論理削除・スコープ解決・証跡 |
| C3 | モデル呼び出し | `packages/llm/` | 経路解決・能力表・支払者・トークン計測・上限・トレース |
| C4 | ファイル | `packages/storage/` | 権限・署名 URL・保持期間・サイズ制限・証跡 |
| C5 | プロセス起動 | `packages/runtime/` | 隔離・**完了信号の検証**・タイムアウト・環境変数の遮断・証跡 |
| C6 | 通知送出 | `packages/notify/` | 宛先解決・購読設定・重複抑止・再送・証跡 |
| C7 | 決済 | `packages/billing/` | **冪等性キー**・Webhook 署名検証・認可・上限整合・証跡 |
| C8 | 秘密の読み出し | `packages/secrets/` | 鍵分離・**AI に渡さない**・ログのマスク・失効の即時反映・証跡 |

### なぜこれで漏れが無くなるか

```
   新種のアクションが増えても、外界に触れる限り関門を通るしかない
        ↓
   迂回は CI が静的解析（import グラフ ＋ 呼び出し式）で検出して落とす
        ↓
   ★拡張点の列挙に抜けがあっても、横断的関心事は漏れない
```

**前提条件**：動的呼び出し（`eval` / 動的 import / 文字列からの関数解決）を CI で禁止する。禁止しないと静的解析が原理的に破れます。

**例外は 2 件のみ**（Bridge のローカルファイル操作／起動時のブート設定）。いずれも代替統制つきで台帳に登録済み。

## 登録の完了点と保留の申し込み（D-088）

登録が終わるのは**メールのリンクを押した時点**。`POST /api/auth-ext/sign-up` は `kaname_auth.pending_signup` に 1 行置いて確認のメールを送るだけで、利用者も会社も作らない。`POST /api/auth-ext/verify-signup` が保留を引いて `signUp`（`app.create_company` の hook 付き）を呼び、そこで初めて 利用者・会社・根の層・代表と全権限・自分のAI ができ、セッションが返る。

- 保留は `kaname_auth` に置く（会社がまだ無いので `public` のテナント分離に乗らない）。触れるのは認証の接続だけ
- パスワードは平文で持たない。`SECRETS_MASTER_KEY` から HKDF で導いた鍵で AES-256-GCM に包み、確認のときだけ開く。30 分で失効
- 確認が済んだ行は消さず `consumed_at` を立てる。消すと「もう済んだ」と「期限切れ」が区別できず、二度押しした人に「はじめからやり直せ」と言ってしまう
- 同じメールで再度申し込んだら上書きして送り直す（`consumed_at` も戻す）。弾くのは確認まで済んだ人だけ
- 送出（関門 C6）の失敗は握り潰さない。`sent_at` / `send_error` に残し、画面は「送りました」と言わない。失敗の理由は 宛先の側 と こちらの側 に分け（`classifyMailError`）、文言と一手を変える


## はじめの設定の進み具合（D-089）

はじめの設定（1 PCをつなぐ → 2 話す → 3 たたき台 → 4 ログイン情報 → 5 テスト → 6 本番へ）を

Bridge はその人の PC、ログイン情報はその人が預けるので、会社単位ではなく人単位で持つ。

## 自分のAIが実際に動く（受け取って返す・D-090）

段階 1 で AI が動く経路は Bridge だけ（D-055）。**文脈は本人の Claude Code が持ち、Kaname は二重に持たない**（D-090.1）。

```
画面 ──言う──▶ app.agent_enqueue ──┐                      ┌─▶ app.bridge_finish_job ──▶ 会話に出す
  （POST /agent/say）              │  bridge_jobs（並び）  │      （done は返事・stopped は「ここで止まりました」＋理由）
                                   └─▶ app.bridge_take_job ┘
```
