## 1. 全体方針

**モジュラーモノリス ＋ 2 つの独立プロセス。**

| 構成要素 | 中身 | 独立させる理由 |
|---|---|---|
| **中核**（モジュラーモノリス） | Web ／ API ／ ワーカー | 会社モデルが全機能から参照されるため、分割すると分散モノリスになる |
| **取り込みサービス** | Python（docling / faster-whisper） | 言語が違う。入力＝ファイル・出力＝JSON で**型がまたがらない** |
| **Bridge** | Electron（顧客 PC 常駐） | 実行場所も配布経路も別 |

### 設計の 3 本柱

| 柱 | 内容 | 守り方 |
|---|---|---|
| **会社モデルが中心** | 目標・台帳定義・担当業務・組織・ポリシー・記憶を 1 つの定義に。画面も AI 社員も自動実行もそこだけを読む | 論理層と物理層の二層分離 |
| **関門で守る** | 外界に影響を与える経路を 8 本に絞り、必ず通らせる。**列挙で守らない** | CI の静的解析（迂回を検出） |
| **依存を閉じ込める** | 基盤 SDK は境界 7 ディレクトリの中でしか使えない | CI の import 境界検査 |

## 4. DB 設計方針

### 全テーブル共通の原則

| 項目 | 決定 | 後から入れられない理由 |
|---|---|---|
| 主キー | **UUID v7** | 連番はテナント分割・統合で衝突 |
| `tenant_id` | **全テーブル NOT NULL** | 後入れはデータ移行＋全 RLS 書き直し |
| `scope_id` | 共有され得るもの全部 | 後から共有機能を足すと全行の意味が変わる |
| 監査列 | `created_at` / `updated_at` / `created_by` / `updated_by` | 証跡が後から作れない |
| 論理削除 | `deleted_at` 既定 | 物理削除は監査で復元不能 |
| enum | **使わない。マスタ ＋ FK** | 値追加が migration ＋ 型再生成 ＋ 全分岐見直し |
| 多重度 | 中間テーブルを足せる形 | 1 対多 → 多対多は全面書き直し |
| バージョン | 会社モデルの構成物に付与 | 「いつ何が変わったか」が後から作れない |

### アクセス制御

```sql
-- ✗ 禁止（Supabase Auth に固定され、DB 層まで移行不能になる）
USING (tenant_id = (SELECT tenant_id FROM users WHERE id = auth.uid()))

-- ✓ 採用（Postgres 標準。どのクラウドでも動く）
USING (tenant_id = current_setting('app.tenant_id', true)::uuid)
```

API 層が全リクエスト冒頭で `SET LOCAL app.tenant_id / app.user_id / app.role` を発行。
**検証は「上流を故意に壊す」**（`SET` を飛ばして他テナントのデータが取れないことを確認）。正常系では RLS の有無が判別できません。


### 権限モデル（D-073）

権限は **誰に × 何に × どの層で × できること** の 4 つ組（`permissions`）。本人のもの（個人の範囲）は権限なしで自由＝RLS の `self_only` predicate で表し、行を作らない。
層は **会社ごと**（`layers`）：運営／会社／個人は固定、その間（部署・事業…）は会社が 0〜n 個作る。画面にもコードにも「部署」を固定名で書かない。
R3（担当者）・R4（閲覧のみ）も **自分のAI** を持ち（`clones`）、`abilities=view` の行で「見える」を持つ。見えないのが既定の設計にしない（L-010）。
運営（R6）は `ops_members` の権限（support / billing / catalog / admin）で、顧客テナントの行は **既定で読めない**（§2b）。

### 口座状態の出来事と失効（D-074・D-076.13・G-14）

退会・停止（休止）・権限変更・プラン変更（下げる）・層を消す・AI社員を消す・人が抜ける の 7 つは `account_events` の行になり、
`account_event_items` が **flow.json の全オブジェクト**について「消える／残る／移る・戻る／止まる／即失効」と引き継ぎ先を持つ。全部が done になるまで出来事は終わらない（引き継ぎ先を決めるまで消せない）。
失効は **`sessions` を全行 revoked** にする方式。API・Bridge・共有リンク・Webhook はトークンの期限ではなく `sessions` を見る（発行済み JWT が生き残る事故を構造で潰す）。
退会は 猶予（30 日・復元可）→ 完全消去 → `erasure_certificates` を自動発行して代表に送る。法令保管（`retention_holds`）の行だけ残す。

### 動的台帳（最難関）

**ハイブリッド（固定列 ＋ JSONB）を採用。実 DDL を採りません。**

| 方式 | 採用製品 | 不採用の理由 |
|---|---|---|
| 実 DDL | Teable / NocoDB / Baserow | 65 社 × 5 型 ＝ 325 テーブル。**RLS を動的生成する必要があり、1 つ漏れたらテナント越え**。DDL がロックを取る |
| EAV | — | JSONB より約 1.3 倍遅い。条件ごとに JOIN が増える |
| **JSONB ハイブリッド** | **採用** | 固定の中核 ＋ カスタム項目、という Kaname の形に合う |

```sql
ledger_records (
  id uuid, tenant_id uuid,          -- 固定：RLS
  definition_id uuid, scope_id uuid,
  stage_id uuid,                    -- 固定：ファネル集計
  amount numeric(18,4),             -- 固定：金額集計
  occurred_on date,                 -- 固定：期間集計
  assignee_id uuid,                 -- 固定：担当別
  data jsonb                        -- 可変：業界ごとの自由項目
)
```

**目標の集計に使う 4 列を固定列に出します。** ここが JSONB のままだとループが回りません。

**参照から取り込んだ 3 点**
1. NocoDB の**二層構造**（論理メタデータ層／物理層）を明示的な設計原則にする → 将来の方式差し替えが可能
2. Salesforce の**ピボット索引**を Postgres の**式インデックス自動生成**に翻訳（`is_filterable` の項目のみ・`CONCURRENTLY`）
3. 項目定義を **JSON Schema** で持ち、描画・検証・許可リストの 3 箇所に効かせる

**SQL インジェクション対策（4 点・CI で強制）**
許可リスト方式 ／ 演算子は固定 enum ／ 値は必ずバインド ／ 文字列連結を CI で禁止

### 外部リソースのコード化

バケット・キュー・秘密・DB 拡張は**全てコードで作る**。「ダッシュボードで作る前提」は禁止（Atelier で Storage バケット未作成により全機能が 502 になった事故の再発防止）。

### git

trunk-based ／ `slice/S<番号>-<名前>` ／ squash ＋ 全ゲート緑で auto-merge ／ worktree 不要（1 人）

## 6. セキュリティ

| 項目 | 対策 |
|---|---|
| 認証 | Better Auth。**トークンベース**（アプリ対応） |
| 認可 | **RLS ＋ API 層の二重チェック**。片方だけに頼らない |
| テナント分離 | 全テーブル `tenant_id` ＋ RLS ＋ **サンドボックスもテナント単位** |
| 資格情報 | Infisical。テナントごとに鍵分離。**AI には一切渡さない** |
| 失効 | 退会・停止・権限変更・パスワード変更・招待取消で **`sessions` を全行 revoked**（発行済みトークン・Bridge・共有リンク・Webhook はこの表を見る。G-14・D-074） |
| **副作用の順序** | **認可 → ポリシー → 承認 → 副作用 → 記録**。RLS 拒否に頼ると副作用だけ実行される |
| プロンプトインジェクション | 外部由来はデータであって指示ではない扱い |
| 監査 | 追記専用。顧客がエクスポート可能（`export_jobs`・C4）。運営がしたことは会社側と運営側の両方に残る（D-074.5・D-077.7） |
| 運営のアクセス | 既定で顧客データを読めない。`support_access_grants`（範囲・期限）があるときだけ。§2b（D-074.5） |

## 7. 関門（choke points）── この設計の核

**「列挙で守るな。関門で守れ」**（正本：`.claude/rules/common/choke-points.md`）

| # | 関門 | ゲートウェイ | 関門の中で 1 回だけ書くもの |
|---|---|---|---|
| C1 | ネットワーク | `packages/actions/` | 認可・ポリシー・承認・サービス台帳判定・レート制限・証跡・課金・失敗時ハンドオフ |
| C2 | 永続化（書込） | `packages/db/` | テナント文脈・RLS 前提保証・監査列・論理削除・スコープ解決・証跡 |
| C3 | モデル呼び出し | `packages/llm/` | 経路解決・能力表・支払者・トークン計測・上限・トレース |
| C4 | ファイル | `packages/storage/` | 権限・署名 URL・保持期間・サイズ制限・証跡 |
| C5 | プロセス起動 | `packages/runtime/` | 隔離・**完了信号の検証**・タイムアウト・環境変数の遮断・証跡 |
| C6 | 通知送出 | `packages/notify/` | 宛先解決・購読設定・重複抑止・再送・証跡 |
| C7 | 決済 | `packages/billing/` | **冪等性キー**・Webhook 署名検証・認可・上限整合・証跡 |
| C8 | 秘密の読み出し | `packages/secrets/` | 鍵分離・**AI に渡さない**・ログのマスク・失効の即時反映・証跡 |

### なぜこれで漏れが無くなるか

```
   新種のアクションが増えても、外界に触れる限り関門を通るしかない
        ↓
   迂回は CI が静的解析（import グラフ ＋ 呼び出し式）で検出して落とす
        ↓
   ★拡張点の列挙に抜けがあっても、横断的関心事は漏れない
```

**前提条件**：動的呼び出し（`eval` / 動的 import / 文字列からの関数解決）を CI で禁止する。禁止しないと静的解析が原理的に破れます。

**例外は 2 件のみ**（Bridge のローカルファイル操作／起動時のブート設定）。いずれも代替統制つきで台帳に登録済み。

## 8. 設計トレードオフ一覧

| 決定 | 得たもの | 失ったもの |
|---|---|---|
| モジュラーモノリス | 1 人で運用可能・1 PR で縦に貫ける | 個別スケール・技術の混在 |
| TypeScript 単一 | 型が端から端まで通る | Python の AI ライブラリが即使えない |
| JSONB ハイブリッド | RLS が安全・DDL ロック無し | 実 DDL より集計がやや遅い（段階 2 で実測） |
| Better Auth | クラウド移行が可能・SSO が OIDC で通る | 習熟度が低く学習コスト |
| Supabase で開始 | 立ち上がりが速い | ISMAP 非登録（段階 4 で AWS へ 5〜8 日） |
| 関門方式 | 列挙漏れが事故にならない | 関門を通す分の間接層 |
| 縦切り | 2〜4 日で触れる・手戻りが早く出る | 並列度が低い（1 人なので影響なし） |
| Realtime を使わない | 移行コストがゼロ | 即時反映を SSE ＋ ポーリングで作る |
| CAPTCHA を突破しない | 顧客のアカウントが凍結しない | 一部操作で人に 1 手渡す |
