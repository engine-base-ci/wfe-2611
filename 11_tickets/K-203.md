## 目的

K-78〜K-81 の準備の途中で、staging の秘密がチャットに出た。チャットに出た値は漏れたものとして扱い、統合テストを流す前に全部作り直す。

## 完了の条件

- [ ] 下の 7 つを全部作り直し、Vercel の `kaname-api` の環境変数（Production・Sensitive）を新しい値にした
- [ ] 古い鍵を、作った所の画面で消した（Supabase の置き場の鍵・Infisical の Client Secret・Resend の鍵）
- [ ] `kaname-api` を配り直し、最新の配りが Ready
- [ ] K-200 の健康診断が緑（実装の担当が流す）

## 前提と制約

- 費用：出ない
- 新しい値は、自分の画面からそのまま Vercel の欄に貼る。チャット・メモ・ファイルに置かない
- 統合テスト（K-65）の前にやる。staging に今ある試しのデータ（試しに作った会社・人）は消えてよい（D-140.3）
- 取り替えると、staging にログインしている人は全員ログインし直しになる（staging を使っているのは代表だけ）
- 鍵・パスワード・接続の文字列の値は、チャット・ファイル・コミット・このチケットに書かない。入れる先は Vercel の環境変数（Sensitive）・Infisical・GitHub の Actions の secrets だけ（infra/STAGING.md §1）

## 実施事項

乱数の作り方：Mac の「ターミナル」を開き、`openssl rand -hex 32` と打って Enter。出た 1 行が新しい値（記号が入らない形。1 回ごとに別の値が出る）。

入れる所はどれも：https://vercel.com → `kaname-api` →「Settings」→「Environment Variables」→ その名前の行の右の「…」→「Edit」→ 値を貼る →「Save」。

1. **DB の役の合言葉 2 つ**：乱数を 2 つ作る。`KANAME_APP_DB_PASSWORD` と `KANAME_AUTH_DB_PASSWORD` に 1 つずつ入れる。続けて `DATABASE_URL` の中の合言葉の所（`:` と `@` の間）を 1 つ目に、`AUTH_DATABASE_URL` の同じ所を 2 つ目に替える
2. **DB の管理者の合言葉**：https://supabase.com/dashboard → `kaname-staging` → 左下の歯車「Project Settings」→「Database」→「Reset database password」→ 新しい合言葉を作って控えずにそのまま写す → Vercel の `DATABASE_ADMIN_URL` の中の合言葉の所を替える
3. **ログインの印を包む鍵**：乱数を 1 つ作り `AUTH_SECRET` に入れる
4. **置き場の鍵**：Supabase → 左の「Storage」→「Settings」→「S3 access keys」→「New access key」→ 出た 2 つを Vercel の `STORAGE_ACCESS_KEY_ID`・`STORAGE_SECRET_ACCESS_KEY` に入れる → 同じ画面で古い鍵の行を消す
5. **預け先（Infisical）の鍵**：https://app.infisical.com → 左の「Access Control」→「Identities」→ `kaname-api-staging` →「Universal Auth」の「Client Secrets」→「Add Client Secret」→ 出た値を Vercel の `INFISICAL_CLIENT_SECRET` に入れる → 古い行を「Revoke」
6. **顧客の資格情報を包む鍵** `SECRETS_MASTER_KEY`：ターミナルで `openssl rand -base64 48` と打って出た値を入れる。そのまま替えてよい（K-200 の切る段がコードから確かめた：替えると、前に預けた試しの資格情報は開けなくなり、メールの確認待ちの登録はやり直しになる。staging の試しのデータは消えてよい・D-140.3）
7. **メールの鍵**：https://resend.com →「API Keys」→「Create API Key」（Permission は「Sending access」）→ 出た値を Vercel の `RESEND_API_KEY` に入れる → 古い鍵の行を消す
8. **配り直す**：`kaname-api` →「Deployments」→ いちばん上の Production の行の右の「…」→「Redeploy」→ Ready になるまで待つ（数分）
9. 実装の担当に「取り替えた」とだけ伝える（値は伝えない）

## リスクと懸念

- 接続の文字列の中の合言葉を替えるとき、前後の `:` や `@` を消すと起動しない。配り直しが Error になったら、その行だけ見直す
- 手順 1 と 2 のどちらかだけ替えて配り直すと、Build（migration）が落ちる。1〜7 を全部替えてから 8 を 1 回

## 申し送り

- GitHub には DB の管理者の接続を入れない（CI に渡すのは、K-202 で作る読むだけの役の接続＝`STAGING_DATABASE_READ_URL`）。管理者の合言葉を替えても GitHub の側は入れ直さなくてよい。K-202 をこの後にするのは、取り替えた直後の staging で最初の回を見るため
- 各サービスの画面の言葉は変わることがある。見当たらないときは、どの言葉が見当たらないかを伝える
