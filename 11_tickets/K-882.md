## 目的

見せたチケット（K-881）のチャットを、ゲストと社内が同じ 1 本で話せるようにする（芯：チケットはチケット・新しいのは「ゲストが見られるか」だけ・D-155.41）。この葉は 3 つを作る：

- **書き込みの印 `ticket_messages.guest_visible`**：ゲストに見える書き込みか。**見せたチケットに、見せた後で書かれた書き込み（種類 post）に自動で付く**（見せる前に書いた物は、見せても見えない）。変更・仕組みの行（kind change・system）には付かない。引き金 1 つで決めるので、書き込みの口（段 7 の K-385）は変えない。**見せた後に社内が書いた物は、社内向けに分ける口を作らず全部ゲストに見える**（勧め：決める人に PM から確かめ、違えば直す・まとめ役の決め 2026-11-23 の 2）
- **書き込みの印 `ticket_messages.from_request`**（まとめ役の決め 1）：依頼から来た書き込みか（`boolean not null default false`）。K-894 が、依頼のやり取りをチャットの頭に写すときに `true` で入れる。ゲストが読む関数と社内の読み（段 7 のスレッドの読む関数）の答えに、**`true` の行にだけ鍵 `from_request: true` を足す**（画面 K-898・K-905・K-913 が「依頼のやり取り」の札と「ここからチケットのやり取り」の区切りを引く元）
- **ゲストが読む関数 `app.portal_ticket_messages(チケット)`**：先方の口 `getPortalTicket`（K-906）が返す `messages` の元。ゲストに見えるチケットで、印が付いた post を古い順に返す。**社内の人の書き込みと、自分のゲストのグループのゲストの書き込みだけ**（依頼から来た書き込みは、書いたゲストが自分のグループなら見える。同じチケットを見せた別のグループのゲストの書き込みは見えない・別のグループどうしは互いに見えない）
- **ゲストが書く口 `postPortalTicketMessage`**（POST /portal/tickets/:id/messages・体 `{ body }`・201 `{ data: { id } }`）：見せたチケットのチャットにゲストが書く。書いたら担当者に「お知らせ」が 1 件入る（知らせは普通のチケットと同じ＝担当者・D-155.44）。メールは送らない

社内の人が書く口は段 7 の `createTicketMessage`（K-385）をそのまま使う（この葉は触らない）。見せる・見せないの付け外しは K-881、見せたチケットの本文・詳細・段の札を返すのは K-906、チャットを描くのは K-913・K-905。

## 前提と制約

分類: CRUD, PERM

- **見えるかの判定は K-878・K-881 の `app.guest_ok()`・`app.guest_sees_ticket(tid)` だけを使う**（自分で書き直さない）。見せていない・外した・グループが消えた・チケットが消えた・下書きのときは、読む関数は null・書く関数は 42501（G-14：毎回その時の状態を見る・キャッシュに持たない）
- **`guest_visible` の決め方**（引き金 `ticket_messages_guest_visible`・before insert）：入れる行が `null` なら「`kind = 'post'` で、そのチケットに今も生きている見せる相手（`ticket_guest_shares.deleted_at is null`）が 1 つでも在る」で決める。入れる側が `true` か `false` を明示すればそのまま（K-894 の「依頼のやり取りをチャットの頭に残す」は `true` で入れる・ゲストが書く関数も `true`）。**既存の行は全部 false**（本線にあるやり取りは見せる前の物で、見せても見えない）。見せたあとで見せるのをやめても、すでに付いた印は消さない（ゲストが読むのは今見せている間だけ・印は「そのとき見えていたか」の記録）
- **`from_request`**：`alter table ticket_messages add column if not exists from_request boolean not null default false`（既存の行は全部 false・引き金は触らない）。入れる側（K-894 の関数）が明示で `true` を入れる。ゲストが書く口と社内の書く口（K-385）は印を入れない（false のまま）
- 読む関数が返す形は 1 件ごと `{ id, side, name, at, text }` に、**`from_request` が true の行にだけ `from_request: true` を足した形**（false の行には鍵を付けない＝今の形のまま・段 7 の試験を替えない）。`side` は書いた人が役割ゲスト（`tenant_memberships.role = 'requester'`）なら `they`・社内の人なら `we`（K-906 の試験と同じ・画面の部品 `Msg` の向き）。`name` は書いた人の表示名（メールアドレス・id・役割は出さない）。`at` は書いた時刻（ISO）。`text` は本文そのまま。メンションの印・引用・反応・変更の中身は返さない
- **書けるのは、見せたチケットのゲストだけ**。社内の人は `role: member` なので先方の口に 403（入口の役の柵・今のまま）。ゲストは社内の口（`createTicketMessage`）に 403
- 本文：前後の空白を取った後が空なら 422（契約の `minLength: 1`・入口の normalize が前後の空白を落とし字を NFKC にする・K-385 と同じ・番号なしの VALIDATION_ERROR）。字数の上限は決めない（D-130.1・守りは送る量 1MB の入口だけ）。体の欄は `body` だけ（`author_member_id`・`kind`・`guest_visible`・`mentions` は入れさせない・知らない欄は 422）
- 書き込みは種類 post・書いた人はセッションの人・`guest_visible = true`。**書いた人（ゲスト）自身には知らせない**。担当者（`tickets.assignee_member_id`）が、止めていない・抜けていない人なら受け箱に 1 件（channel `inapp`・event_kind_id `ticket.message`・payload `{ ticket_id, number, title, message_id, url: "/tickets/<id>" }`・本文は入れない・dedupe_key `ticket.message:<書き込みの id>:<担当者>`・sent_at は今）。担当者が空・止めた・抜けた人なら何も入れない。メンション・知らせる人の指定はゲストには無い（受け箱は担当者だけ）。K-385 の `ticket.message` と同じ種類・同じ形（画面の鈴は同じ読み方でよい）
- 証跡：書いた 1 件ごとに `ticket.guest_message_posted`（payload は `ticket_id` と `message_id` だけ・本文は載せない）
- 書き込みと受け箱の行と証跡は **1 つの取引**（DB の関数 1 回）。途中で落ちたら何も残らない（503・E-PAGE-003・ログは場所と例外の種類だけ・本文を出さない）。守りの判定の例外も 503（D-136.1）
- 二度押しは入口の冪等キー（`idempotency-key`）で 1 つ。キーが違う 2 本は 2 つの書き込みになる（同じ文でも別の書き込み）
- 関門の宣言（頭の欄 choke_points）は [C2, C6]（DB に書く・受け箱の行＝通知）。メール・外のサービスは呼ばない
- **社内の読み**（段 7 の読む関数 `app.ticket_timeline_item`・20261120130000）の 1 件の答えの `message` に、`from_request` が true の行にだけ `from_request: true` を足す（`create or replace`・ほかの鍵と並びは今のまま。段 7 の読む口と試験は替えない）
- 見せた後に書いた書き込みは、社内の人が書いた物も全部ゲストに見える（「社内だけ」の書き込みの口は作らない・D-155.53 代表の答え answer=c2adcba60dbd）。画面側（K-905）が見せている間の書く欄に「見せている間の書き込みはゲストにも見えます」と出す
