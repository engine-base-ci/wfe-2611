## 目的

ワークスペースの管理の「記録」（画面 audit・A33）が読む口。会社の大事な出来事（権限が変わった・外に出した・新しい端末で入った・分身に許可した・消した）を、新しい順に、札・人・チケット・期間で絞って読む（D-150.40：チケットごとの更新の行はやり取りの流れに載るので、ここは別の記録）。

- **読める人（代表の答え・D-154.11）**：会社全体は管理者。**マネージャーは自分のグループの分だけ**（自分のグループのチケットの行と、そのグループに入っている人の操作の行）。普通のメンバー・閲覧のみ・依頼する側は開けない（403）。自分の記録を開く入口は作らない（D-154.2）
- **追記だけ**（D-154.25）：記録は消せない・直せない。この口は読むだけで、画面から書く口は無い
- **書き出しは作らない**（D-154.4）：createExport・getExport は作らない（契約から外すのは K-800）。持ち出しの札は作らない（書き出しが無いので在る記録が無い・代表の答えで下絵からも外した）
- ことば（q）で探すのは孫 K-850。この葉の契約の問い合わせの欄に q は入れない

## 前提と制約

分類: LIST, PERM

- 表 audit_events は在る（0003）：actor_member_id・action・target_type・target_id・payload・occurred_at。**追記専用**（UPDATE・DELETE は引き金で拒まれる）。書くのは関門の関数 app.record_audit だけ。索引は (tenant_id, occurred_at desc) が在る。この葉は表も関数も変えない
- **入口の権限**：契約の言葉は今のまま read（会社の人なら入口を通る）。誰が読めるかは読む関数 `app.audit_list` が見る：管理者（`app.is_admin`）は会社全体・マネージャー（`scope_memberships.role = 'manager'`、または主の所属に行が無いときの tenant_memberships の manager。`app.manages_scope` と同じ条件）は自分のグループとその下のグループの分・それ以外は 42501 → 口が 403（入口の 403 と同じ形・data なし）
- **マネージャーの範囲**（代表の答え：自分のグループのチケットと、その人たちの操作）：(a) 対象が target_type 'tickets'（書く側の名前・0102 と 20261123082800 の tickets.delete）で、そのチケットのグループ（tickets.scope_id）を `app.manages_scope` で管理している行 (b) 行を起こした人（actor_member_id）が、自分が管理するグループ（その下を含む）に入っている行（scope_memberships の主・兼務・消していない、か members.scope_id）。**兼務**（D-154.15）：2 つの層のマネージャーを兼ねる人は両方の分が出る・別の部署に作業員として入っている人の操作は、その部署のマネージャーに出て、入っていない部署のマネージャーには出ない・兼務を外すと出なくなる。範囲の外の行は件数にも漏れない（絞りで範囲外を指しても空の 200・在るかを漏らさない）
- **札**（6 つ・画面の絞りの札）：action の頭から `app.audit_kind(action)`（immutable の DB の関数）で決める。perm 権限が変わった＝`permission.*`・`member.*`・`scope.*`・`layer.*`・`invitation.*`・`workspace.*`／out 外に出した＝`external.*`／device 新しい端末で入った＝`session.new_device`／ai 分身に許可した＝`clone.*`／deleted 消した（30 日は戻せる）＝`tickets.delete` だけ（30 日は戻せる消し方はチケットの消しだけ。前からの `credential.delete`（端末の鍵）・`ticket_link.delete`（チケットのつながり）は戻せないので札なし）／ops 運営がしたこと＝常に 0 件（運営の記録 ops_audit_events は会社の記録に出さない・F12）。どれにも当たらない action は札なし（絞りなしのときだけ出る）。**札の追加は関数 1 つの直し**（書く側が新しい action を足しても、この表に無ければ札なしで出る）
- **並びと続き**：新しい順（occurred_at 降順・同じ時刻は id 降順）。続きは keyset の印 `cursor`：中身 `<occurred_at を UTC・マイクロ秒 6 桁の ISO>_<id>`（読み終えた最後の行の次から。行が増えても重ならない）を **base64url（パディングなし・1〜200 字）** にした文字列。画面はもらった印を返すだけ。入口（op.ts）は一覧の口の cursor を位置の数（10 進）しか通さないので、この口を **KEY_CURSOR_OPS**（op.ts と 05_flow/build_api.py の同じ集まり・K-92・K-161 と同じ形）に足す（PM の決め 2026-11-25・案 a）。印の中の時刻はマイクロ秒のまま（DB の occurred_at はマイクロ秒を持ち、ミリ秒に丸めた印では同じミリ秒の中の古い行を読み飛ばす）。答えの occurred_at はミリ秒（下の答えの形）。1 回 1〜100 件（既定 50）。件数の合計は返さない（範囲外を漏らさず、安く読める）
- **期間**：from は含む・to は含まない（ISO 8601・時差つき）。from が to より後ろは契約に書けない形（2 つの欄の関係）なので 422 にせず 200・0 件（切る段の決め）
- **action・target_type・payload は書く側に合わせる**（この葉は書く側を変えない）：action の名前は K-800 の「記録の action の名前」の表と、書く葉の今の md（K-802〜K-804・K-807・K-811・K-812・K-814・K-848・K-827〜K-830・K-838）のとおり（`member.role_change`・`scope.create` のように動詞の元の形）。target_type は書く側の複数形（`tickets`・`members`・`scopes`・`layers`・`invitations`・`workspace`）。前からの `invitation.created` は単数の `invitation`（20261121091900）
- **文**（`lines.ts`）：画面は「<人> が <文>」と出す。知っている action ごとの文を口の側で作る（画面の字はこの葉が鍵から作る）。知らない action は「<action> を行った」。対象の名前（label）は target_type で引く：`tickets` は番号（tickets.number）・`members` は display_name（消した人・止めた人もそのまま）・`scopes` はグループの名前・`layers` は層の名前（label）。`invitations`・`invitation`・`workspace`・ほかは label なし（null。招待の宛てのメールは出さない）。payload に名前・メールは無い（K-800 の決め）ので、名前は対象の表から引く
- 追記だけの確かめ・書く口が無いことの確かめも試験に入れる（D-154.25）
