## 目的

統合テスト（K-65）は、自分の Mac の上の使い捨ての VM から staging を指して流す。VM は 1 回ごとに捨てるので、住所と鍵は台には置けない。GitHub の「Actions の secrets」（暗号で預かり、流すときだけ VM に渡る）に名前で入れる。

前の書き方（Mac の中のファイル ~/.config/act/kaname.secrets）は前の CI の形なので、やめる。

## 完了の条件

- [ ] GitHub の engine-base/kaname の Actions の secrets に、下の名前がそろっている（値は書かない）
- [ ] K-204 の最初の 1 回で、健康診断の段が緑

## 前提と制約

- 置き場は GitHub の repository secrets（PM が決めた・2026-11-14）。K-201 で「Environments」が在ると分かり、決める人が壁を置くと答えたら、入れ先を「Environments → staging → Environment secrets」に替える（名前は同じ 4 つ。手順はそのとき実装の担当が書き直す・K-204 の決定ログ）。メールは本物を送って Resend の記録を読む（D-140.1）ので、記録を読む鍵が 1 つ要る
- 費用：出ない
- 鍵・パスワード・接続の文字列の値は、チャット・ファイル・コミット・このチケットに書かない。入れる先は Vercel の環境変数（Sensitive）・Infisical・GitHub の Actions の secrets だけ（infra/STAGING.md §1）

## 実施事項

入れる所：https://github.com/engine-base/kaname →「Settings」→ 左の「Secrets and variables」→「Actions」→ 緑の「New repository secret」。「Name」に下の名前、「Secret」に値を貼り「Add secret」。4 回くり返す。

| 名前 | 何を入れる | どこから写す |
|---|---|---|
| `STAGING_BASE_URL` | staging の画面の住所（https:// から） | Vercel → `kaname-web` → 上の「Domains」の住所 |
| `STAGING_API_BASE` | staging の口の住所（https:// から） | Vercel → `kaname-api` → 上の「Domains」の住所 |
| `STAGING_DATABASE_ADMIN_URL` | DB を読む接続の文字列（試験は読むだけ） | Vercel の `DATABASE_ADMIN_URL` と同じ物。Supabase →「Connect」→「Session pooler」の文字列に、K-203 の手順 2 の新しい合言葉を入れた物 |
| `STAGING_RESEND_READ_KEY` | 送ったメールの記録を読む鍵 | https://resend.com →「API Keys」→「Create API Key」→ Permission を「Full access」にして作る（名前は `kaname-staging-ci-read`） |

`STAGING_BASE_URL` が前からあれば、その行の鉛筆の印から新しい値で上書きする。

## 決定ログ

- CI は GitHub と同じ workflow を自分の台で流す（D-128.147）・統合は staging（D-128.144）

## リスクと懸念

- `STAGING_RESEND_READ_KEY` は読む権限も持つ強い鍵。staging 用の Resend の口座が本番と同じなら、本番のメールの記録も読める。本番を作る前（K-83）に、staging と本番で Resend の鍵の持ち方を分けるか決める
- DB の接続は管理者の物。健康診断と試験は読むだけに使う（K-200 の行 016・K-65 の前の決まり 2）。本番の DB の接続は決して入れない
- この 4 つは、staging の回の 2 つの段（健康診断・統合テスト）にだけ渡り、main から起こした回だけが流れる（K-204 の行 004・014）。ただし、枝の側で定義を書き換えれば読める（壁は決める人に聞いている）

## 申し送り
