## 目的

統合テスト（K-65）は、自分の Mac の上の使い捨ての VM から staging を指して流す。VM は 1 回ごとに捨てるので、住所と鍵は台には置けない。GitHub の Environment `staging` の「Environment secrets」（暗号で預かり、`environment: staging` と書いた組が main から起きたときだけ VM に渡る）に名前で入れる。

前の書き方（Mac の中のファイル ~/.config/act/kaname.secrets）は前の CI の形なので、やめる。

## 前提と制約

- 置き場は GitHub の **Environment `staging` の Environment secrets**（代表が 2026-11-14 に済ませた。Environment は起こせる枝を `main` だけに絞ってある）。リポジトリの側の secrets（Settings → Secrets and variables → Actions の「Repository secrets」）には入れない（今 0 件）：そこに入れると、枝から起こした回でも読める。名前は同じ 4 つ。メールは本物を送って Resend の記録を読む（D-140.1）ので、記録を読む鍵が 1 つ要る

## 実施事項

### 1. DB を読むだけの役を作る（Supabase・1 回だけ）

CI に渡す DB の接続は、管理者の物ではなく、**変更の一覧の表 1 つを読めるだけの専用の役**にする（PM の決め 2026-11-14）。与える権限は、DB につなぐ（connect）・schema `app` を使う（usage）・表 `app.schema_migrations` を読む（select）の 3 つだけ。

1. 合言葉を作る：Mac の「ターミナル」で `openssl rand -hex 32` と打って Enter。出た 1 行が合言葉（どこにも控えない。このあと 2 か所に貼るだけ）
2. https://supabase.com/dashboard → プロジェクト `Kaname` → 左の「SQL Editor」→「New query」。下の文を貼り、**`ここに自分で作った値` の所だけ**を 1 の合言葉に置き換えて、右下の「Run」を押す（「Success」と出る）

```sql
create role kaname_ci_read login password 'ここに自分で作った値' nosuperuser nocreatedb nocreaterole noinherit connection limit 3;
alter role kaname_ci_read set default_transaction_read_only = on;
grant connect on database postgres to kaname_ci_read;
grant usage on schema app to kaname_ci_read;
grant select on table app.schema_migrations to kaname_ci_read;
```

3. 確かめる：同じ画面で「New query」をもう 1 つ開き、下の文を貼って「Run」

```sql
set role kaname_ci_read;
select count(*) from app.schema_migrations;
select count(*) from public.tenants;
reset role;
```

   2 行目（`app.schema_migrations`）は数が出て、3 行目（`public.tenants`）は「permission denied」で止まれば正しい（読めるのは 1 表だけ）。3 行目も数が出たら、何もせずに実装の担当に伝える
4. 2 で使った query の文には合言葉が残っている。左の一覧でその query の「…」→「Delete」で消す
5. 接続の文字列を作る：上の「Connect」→「Session pooler」に出ている文字列を写し、① ユーザー名の `postgres.<ref>` を `kaname_ci_read.<ref>` に（`<ref>` の所はそのまま）② 合言葉の所を 1 の合言葉に ③ 末尾に `?sslmode=verify-full` を付ける（もう `?` が在れば `&sslmode=verify-full`）。これが下の表の `STAGING_DATABASE_READ_URL` に入れる物

### 2. GitHub の Environment `staging` に名前を 4 つ入れる

1. Environment を作る（1 回だけ）：https://github.com/engine-base/kaname →「Settings」→ 左の「Environments」→「New environment」→ 名前に `staging` →「Configure environment」。「Deployment branches and tags」を「Selected branches and tags」にして「Add deployment branch or tag rule」で `main` を 1 つ足す（ほかの枝は足さない）
2. 同じ画面の下の「Environment secrets」→「Add environment secret」。「Name」に下の名前、「Value」に値を貼り「Add secret」。4 回くり返す

左の「Secrets and variables」→「Actions」の「Repository secrets」には入れない（前に入れた物が在れば、ごみ箱の印で消して 0 件にする）。

| 名前 | 何を入れる | どこから写す |
|---|---|---|
| `STAGING_BASE_URL` | staging の画面の住所（https:// から） | Vercel → `kaname-web` → 上の「Domains」の住所 |
| `STAGING_API_BASE` | staging の口の住所（https:// から） | Vercel → `kaname-api` → 上の「Domains」の住所 |
| `STAGING_DATABASE_READ_URL` | 読むだけの役の接続の文字列 | 上の「1.」の 5 で作った物。**管理者の接続（Vercel の `DATABASE_ADMIN_URL`）は入れない** |
| `STAGING_RESEND_READ_KEY` | 送ったメールの記録を読む鍵 | https://resend.com →「API Keys」→「Create API Key」→ Permission を「Full access」にして作る（名前は `kaname-staging-ci-read`） |

同じ名前が Environment secrets に前からあれば、その行の鉛筆の印から新しい値で上書きする。前に `STAGING_DATABASE_ADMIN_URL` を入れていたら、その行のごみ箱の印で消す。

## リスクと懸念

- `STAGING_RESEND_READ_KEY` は読む権限も持つ強い鍵。staging 用の Resend の口座が本番と同じなら、本番のメールの記録も読める。本番を作る前（K-83）に、staging と本番で Resend の鍵の持ち方を分けるか決める
- CI に渡す DB の接続は、読むだけの役 `kaname_ci_read` の物（変更の一覧の表 1 つだけ・既定で読むだけの取引・同時の接続は 3 まで）。管理者の接続と本番の DB の接続は決して入れない
- 接続は TLS を確かめる（`sslmode=verify-full`）。確かめに失敗して回が止まったら、確かめを外さずに実装の担当に伝える（Supabase の証明書の元を足す手を K-204 に書いてある）
- 表 `app.schema_migrations` に行の守り（RLS）が掛かっていると、役は 0 行しか読めない。確かめの 2 行目の数が 0 なら、実装の担当に伝える
- 統合テスト（K-65）が DB を読む必要があるなら、要る表を洗い出して、この役に足すか別の役にするかを K-65 の切る段で決める（それまで、この役で読めるのは 1 表だけ）
- この 4 つは、staging の回の 2 つの段（健康診断・統合テスト）にだけ渡り、main から起こした回だけが読める（K-204 の行 004・014・017）。枝の側で定義を書き換えても、Environment の決まり（起こせる枝は `main` だけ）で組が止まり、読めない。この決まりを緩める（枝を足す・Environment を消して Repository secrets に戻す）と壁が無くなるので、変えるときは決める人に聞く
