## 目的

設定の画面の「誰ができるか」（下絵 st-perm）の ▾ で、**プランと支払い**・**ワークスペースを消す** を「管理者」か「管理者とマネージャー」に切り替える口。その 2 つを「いま押せる人か」を 1 か所で決める DB の関数 `app.workspace_can(ability)` は K-827 が作る（設定の画面と読む口の入口に要るので・D-154.83）。この葉は値を変え、変えた直後からその判定が効くことを確かめる。**K-827 の読む口・段 13 の changePlan・段 11 の K-830 がこの関数を呼ぶ**（判定を二重に持たない）。可になったマネージャー・個別に付けた人は設定の画面を開け、可の区画だけ押せる（D-154.83・K-827／K-831）。

**書き出し（export）は作らない**（D-154.4）。人ごとの「できること」を足す・外す機能は作らない（D-154.10）。ここで変えるのは会社全体の 2 つの既定だけ。

## 前提と制約

分類: PERM, CRUD

- 入力 `{ billing?: "admin" | "admin_manager", delete_workspace?: "admin" | "admin_manager" }`（strict・1 つ以上＝契約の minProperties 1）。知らない値・知らない欄（`export` など）・文字でない値は 422。送られなかった欄は変えない
- **変えられるのは管理者だけ**。権限（billing など）を個別に付けた人・「管理者とマネージャー」にしたマネージャーでも変えられない（契約「管理者だけ」・設定の画面でも「誰ができるか」の ▾ は押せない形・D-154.83）。入口は管理者の束。変える口は本人確認を取り直す（直前 15 分・無ければ 403・STEP_UP_REQUIRED・D-154.18・D-125.139）。契約の step_up が always なので、本人確認は入口（op.ts の 3.2）が持つ。順は入口（権限 → 本人確認）→ 口（変更）で、口の中で本人確認をもう一度は見ない
- **値の置き場**：`tenants.who_billing`・`who_delete_workspace`（K-827 の migration が足した列・check で 2 値）。この葉は書くだけ
- **同じ値への変更は 200 のまま記録を書かない**。変えたら記録 `workspace.permissions_changed`（payload `{ changes: [{ key, from, to }] }`・1 回の保存で 1 行・変わった欄だけ）
- **共通の判定** `app.workspace_can(p_ability text) returns boolean`（K-827 の migration が作る・stable・security definer・search_path 固定。中身の決まりはここに書く＝K-827 はこのとおりに作る）：呼んだ人（app.user_id）が、自分の会社の中で、止められていない（suspended でない・外していない）有効な人のとき、ability が `billing` か `delete_workspace` なら ① 会社全体の役割が管理者 → true ② 会社全体の役割がマネージャー（**グループの役割ではない**）で、対応する列が `admin_manager` → true ③ その ability を個別に付けた permissions の行（revoked_at が空・ability_id が同じ）が在る → true。それ以外・知らない名前（`export` など）は false
- **変えた直後に効く（G-12）**：判定は呼ぶたびに列を読む（キャッシュしない）。入り直しは要らない
- 同時の変更は会社ごとの錠 `app.admin_lock()`（K-800）で順に通す（G-16）
- DB の失敗は 503（E-PAGE-003）。新しい断る番号は無い（403 は入口と本人確認の共通・422 は契約の形）
