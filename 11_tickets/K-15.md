## 目的

self・assignee・approver・recipient・manager・read・write の口を、表ごとの「誰の行か」の列（担当者・承認する人・受ける人・持ち主）とグループの役割で、入口でも確かめる（行の守り RLS と二重に・ZT4）。

## 完了の条件

- [x] 表ごとの「誰の行か」の列の対応が 1 か所（契約の生成・`scripts/ci/row_rules.mjs`）にあり、全部の行に結ぶ口（:id のあるもの）が対応を持つ
- [x] 対応の無い口は契約の生成で赤になる（作ってすぐ 10 本が赤になり、表の書く条件を読む形にして 0）
- [x] zt_gate の perm_words_missing が 0（226 → 0）
- [x] CI が緑のまま（手元で static・spec の検査と、変えたところの試験を確かめた。GitHub の結果は push 後に見る）

## 前提と制約

- 行を読むのは行の守りの中（RLS）で読み、見えなければ 404（無いのと同じ）
- 入口で確かめたうえで、hooks の中でも RLS が効く（二重）

## 実施事項

- [x] 表ごとの対応（tickets→担当者・作成者・マネージャー・消した本人、approvals→承認する人、ticket_handovers→受ける人、clients→取引先の担当・担当グループのマネージャー・管理者、本人の行は持ち主の列）
- [x] :id が指す表は path の段で決める（/tickets/:id/runs の :id はチケット）。段の名前が表と違うものだけ対応を書く
- [x] write は表の書く条件（07_functional/entities.json の update の式＝RLS と同じ）をそのまま使う。tickets・knowledge_pages は app.ticket_writable・app.kpage_writable
- [x] 範囲の説明で人が違う口（getApproval・stopApproval・copyWorkType）は口ごとに書く
- [x] op.ts 4.1：:id の行を RLS の中で読み、見えなければ 404・条件に合わなければ 403。まだ作っていない口は先に 501（何も動かない）
- [x] app.manages_scope（0082）：そのグループか上のグループのマネージャーか管理者
- [x] 管理者の「人の 2 段階認証のリセット」が能力の表に無い表（security_events）を指していて誰も呼べなかったのを、人の表（members）の能力に直した。admin の口の表が権限の表に全部あることを試験にした
