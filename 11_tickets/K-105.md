## 目的

K-52 の 3 回目のレビュー（2026-11-06）で見つかった、K-52 より前からある問題。app の関数は静的に数えて 176 個、直に呼べる security definer の関数が約 140 個ある。public から execute を外しているのは 4 個だけで、多くは p_member・p_tenant を引数で受けてそのまま信じる。また search_path に pg_temp が明示されていないので、SQL を流せる役が一時表で tenants・members を隠すと守りを偽って通せる形があり得る。K-52 では新しく作る 2 つの関数だけ kaname_auth に移して直した（決める人の判断）。

## 完了の条件

- [ ] app の security definer の関数がすべて `set search_path = …, pg_temp` を持つ（CI の検査で、無いものを赤にする）
- [ ] 関数ごとに、呼んでよい役（kaname_app・kaname_auth など）だけに execute を渡し、public から外す。呼び手が引数で本人を渡す関数は、本人の確かめ方を一覧にする
- [ ] workflow の全部（act）が緑

## 前提と制約

- 関数の数が多いので、作る役が一覧を作ってから分けて切ってよい

## 実施事項

- [ ] 作る役：関数の一覧（security definer か・search_path・execute の渡し先・本人の受け方）を機械で出す

## テスト仕様と確認の結果

| 確認項目 | 種類 | 判定のしかた | 結果 |
|---|---|---|---|
| pg_temp の無い security definer の関数が 0 | ① 単体（本物の DB） | pg_proc を引いて proconfig を見る | |
