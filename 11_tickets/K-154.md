## 目的

K-144 のテスター Q3（回 13・2026-11-09・セキュリティ）が見つけた。記憶を作る口 `POST /memories`（createMemory・表から作った口）は、入力の形に表の列をそのまま持ち、次の 2 つが起きる。前からある別の場所の問題なので、K-144 に入れず起票した（D-129.32・PM の判断 2026-11-09）。

1. `approved_by`・`approved_at` を利用者が送れ、同僚や別の会社の人を「承認した人」にした記憶が 201 で作れる（全社の記憶にはならないことは Q3 が確かめた）。承認した人は、承認する操作をした本人だけが書けるもので、作る人が書く欄ではない
2. `superseded_by`・`digest_id` に別の会社の行の id を入れると、在るか無いかで 201 と 422 に分かれ、その id がどこかの会社に在るかが分かる（uuid v7 なので当てるのは難しいが、ゼロトラスト D-129.42 に合わない）

## 完了の条件

- [ ] 作る口の入力の形から、利用者が書いてはいけない欄（承認した人・承認した時刻・持ち主など、操作や DB が決める欄）を外す。知らない項目として 422（入口の strict な形）。表から作った口で同じ形の欄を持つ口を全部洗い出してそろえる
- [ ] 参照先の id（置き換え先・まとめ）は、その会社の行だけを見る。別の会社の行と、無い行とで同じ答え（404 か 422 の同じ文）にする
- [ ] 試験：承認した人を送ると 422 で記憶の行が増えない。別の会社の参照先 id と無い id とで、答えの状態コードと文が同じ
- [ ] チケットの CI（act）が緑

## 前提と制約

分類: PERM

- K-144（入口の strict な形・入力の形の作り直し）の取り込みの後にする
- 承認の操作そのもの（誰がいつ承認するか）を作るチケットはまだ切っていない。それまでの間、作る口では承認した人を書けない（承認の欄は空のまま）
