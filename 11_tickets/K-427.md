## 目的

契約 fuzz（G36）が、前からある口 listTickets を `GET /api/v1/tickets?limit=86&scope_id=<uuid>&cursor=&view=&q=<NUL を含むでたらめな字>` で叩くと **500**（`{"error":"internal"}`）になることを見つけた（K-365 の CI。K-365 の変更とは関係ない）。

原因は NUL（U+0000）だった（2026-11-20 切る段で確かめた）：

- 使い捨ての DB で node-postgres から `select $1::text`（値に NUL）を流すと、PostgreSQL が `22021 invalid byte sequence for encoding "UTF8": 0x00` で落ちる。`select $1::jsonb`（JSON の中に `\u0000`）は `22P05 unsupported Unicode escape sequence`。NUL の無い全角・絵文字・`\u0001` は通る
- listTickets の q は入口を何も確かめずに通り、題名の絞り込みの SQL の値になる（`apps/api/src/features/F4/ticket-list/query.ts` の `normalizeQ` は NFKC・trim・小文字だけ）。入口が落ちた番号を 422 に写す表（`apps/api/src/contract/op.ts` の `DB_INPUT_CODES`）には 22021・22P05 が無いので、500 になる
- listTickets の試験を今の版に当てると、この形で 500 になることを切る段で確かめた（試験 K427-API-006）

同じ形は listTickets だけではない。**どの口でも、文字列を DB に渡す口は NUL で 500 になりうる**。契約 fuzz は schemathesis の既定（`generation.allow-x00` が真）で NUL を作るので、口の例が上限（429）に邪魔されず奥に届くようになるほど（K-424）、別の口でも赤になる。fuzz の乱数しだいでどのチケットの CI でも赤になりうる。

この葉は口ごとに直さず、**入口の 1 か所**で直す：

1. **入口（op.ts の `handler`）**：道の値・問い合わせ（名前でなく値）・体（JSON の文字列とキー・入れ子の中まで）のどれにでも NUL があれば、口の振る舞いに届く前に **422・VALIDATION_ERROR**（エラー ID は前からある物のまま・新しく作らない）・欄の名前・理由「使えない文字」。答えに送った字は出さない（代表の決め answer=f0f290e785a9：422＝形の誤り）
2. **2 層目**：入口をすり抜けた NUL（契約の口の外の前の道すじ `apps/api/src/auth/ext.ts` など）が DB に届いて落ちたときの番号 22021・22P05 も、前から 22P02 などが入っている `DB_INPUT_CODES` に足し、`app.ts` の `onError` と `execute` が 500 でなく 422・決まった文で答える（D-130.2 と同じ写し）
3. **契約 fuzz は NUL を作らない設定に**：`scripts/ci/schemathesis.toml` に `[generation] allow-x00 = false`。NUL は契約の形（string）では書けないが入口が必ず断る字なので、fuzz が「形どおりの入力」として作ると 422 を赤と数える（positive_data_acceptance）。入口が断ることはこの葉の試験（K427-API-001〜004）が見る

## 前提と制約

分類: PERM

- 入口の順は変えない：送る量（413）→ 上限（429）→ 認証（401）→ 認可（403）→ 入口の uuid（422）→ ... のうち、**問い合わせと道の値の NUL は入口の uuid と同じ 3.0 の所**（権限の言葉の段 3.1 と、まだ作っていない口の 501 より前）、**体の NUL は体を読んで正規化した直後**（口の前処理 `hooks.input` より前・契約の形 zod の前）。未ログインは 401 のまま（K427-API-006）
- 体の NUL は、`normalize`（NFKC・trim）の後の値を走査する。NFKC も trim も NUL を消さないので、届いたままの体に NUL があるかと同じ。口の hooks が `c.req.json()` で読む届いたままの体（K-144 で入口が器に入れた物）に NUL があるときも、その前に 422 になる
- 走査は文字列の値・オブジェクトのキーの両方を、入れ子（配列・オブジェクト）の中まで見る。jsonb の列はキーの NUL でも 22P05 で落ちる。欄の名前は入れ子の道（`sections.<キー>`・配列は `items.0`）。キーの NUL のときは、キーそのものを出さず、そのキーを持つオブジェクトの道（根なら `body`）
- 走査は 1 回の要求ごとに値の長さの和だけ（体は 1MB が上限・問い合わせは短い）。文の数・取引の数・住所は増えない
- **前の動き（前から決まっていた振る舞い）が変わる所**：次の 3 つの口は、今まで NUL を**黙って取り除いて 201** にしていた。この葉の後は入口が 422 で断る。NUL は人が打てる字ではなく（貼り付けやファイルの読み込みでだけ入る）、取り除くと入れた物と保存した物が食い違う（D-130.4「人が自由に書く欄を黙って切らない」と同じ向き）。NUL 以外の制御文字（`\u0001` など）を取り除く今までの振る舞いは変えない：
  - 登録の name・company_name（`apps/api/src/features/F1/sign-up/input.ts` の CONTROL）→ K51-API-018 の NUL の行を替えた
  - PC の名前 device_label（`/bridge/claim`・K57-API-030）→ NUL の行を替えた
  - 差し戻しの理由 note（`apps/api/src/features/F5/approve-complete/decide.ts`・K63 の差し戻し）→ NUL の行を替えた
  - 預けたログイン情報の text の NUL 除去（`apps/api/src/features/F3/credentials/input.ts` の `replace(/\u0000/g, "")`）は、入口が先に断るので NUL の分は使われなくなる（本体は消さない）。その口の前からの試験に NUL の行は無い
  - 入口の後ろで NUL を取り除く部品の NUL の分が使われなくなるだけで、消す直しはこの葉でしない（NUL 以外の制御文字の除去に使っているため）
  - パスキーの名前（K309-API-011）は前から NUL を 422 で断る。変わらない
- 契約の口の外（前の道すじ `apps/api/src/auth/ext.ts` など）は入口の走査を通らない。2 層目（DB の番号 22021・22P05 → 422）で 500 を防ぐ。前の道すじを契約の口へ移す葉（K-358 などの前の道すじを消す葉）が、移した口は入口の走査に乗る
- 契約 fuzz の設定は `[generation] allow-x00 = false` の 1 行だけ。例の数・seed・並び・ほかの確かめは変えない。NUL を断ることは入口の試験が見る（fuzz が NUL を作らない代わりに、試験が全部の置き場所を見る）
- 試験はこのチケットを切る人が書き、実装する人は変えない（D-128.125）。実装の前に試験を流して赤を確かめない（D-128.143）

## 目録で探した結果

- 入口の確かめの置き場は既にある：`apps/api/src/contract/op.ts` の `uuidParamIssues`（3.0・道の値と問い合わせの uuid）・`normalize`（体の表記ゆらぎ）・`dbInputFailure`・`DB_INPUT_CODES`・`DB_INPUT_REPLY`（D-130.2）。この葉は同じ場所に同じ形で足す（新しいファイルも新しいエラー ID も作らない）
- `app.ts` の `onError` と `op.ts` の `execute` は同じ `dbInputFailure` を使う（K-145）。番号を表に足せば両方が 422 に写す
- NUL を扱う前からの部品：sign-up・approve-complete・credentials の入力整形は NUL を取り除く（上の「前の動き」）。パスキーの名前は NUL を 422 で断る。DB の層に NUL を弾く制約は無い（text には入らないので要らない）
- 探したが無かった物：契約（openapi）の string に NUL を禁じる pattern は無い（107 か所の pattern はどれも別の形）。この葉は契約を変えず、fuzz の設定で NUL を作らないようにする（選ばなかった形は下の「リスクと懸念」）

## 外に影響する手順

外に影響する手順は無い（入口で字を調べて断るだけ。DB に書かない・外を呼ばない・セッションや錠を作らない・後片付けは無い）。落ちる所は走査の中の例外だけで、走査は文字列と配列とオブジェクトを歩く純粋な関数なので、例外は起きない形にする（深い入れ子は JSON.parse が先に断る・1MB が上限）。

## リスクと懸念

- **前の動きが変わる 3 つ**：NUL を黙って取り除いていた 3 つの口が 422 になる。代表が決めた（answer=c8b3f4c3aef8）。「取り除く」案（`normalize` に NUL の除去）は選ばなかった
- **選ばなかった形（契約に NUL を禁じる pattern を書く）**：契約の作り手（`05_flow/build_api.py`）で全部の string に `pattern` を足すと、schemathesis の設定を変えずに NUL を作らなくできる。ただし 107 か所の既存の pattern と合わさり、openapi.yaml・型・契約の形の表・生成の試験が全部変わる大きい直しになる。入口の断り＋fuzz の設定 1 行のほうが小さく、見る物（NUL を断ること）は試験が持つ。形を契約に載せるのは別の葉で決める（PM に出す）
- 契約 fuzz の設定で NUL を作らなくすると、NUL を口の外の前の道すじに送る確かめは fuzz からは無くなる。前の道すじは 2 層目（番号 22021・22P05 → 422）で 500 を防ぎ、K427-API-007 が番号の写しを見る。前の道すじを契約の口に移す葉が、移した口で入口の走査に乗る
- 深く入れ子の JSON で走査が再帰で落ちないか：JSON.parse が先に深さの上限（V8 の既定）で断るので、走査に届く深さは限られる。走査は再帰でなく、行きがけの順に配列の道で歩く形にしてもよい（実装の自由）
