## 目的

契約 fuzz（G36・`scripts/ci/fuzz.sh`・schemathesis）は、作った口を契約から作った入力・契約の外の入力で叩き、500 を出さない・形どおりの入力を断らない・答えの形が契約どおり、を見る。ところが今は、**ほとんどの例が入口の回数の上限（429）で断られて、奥の振る舞いに届いていない**。

- 原因：的（`apps/api/test/fuzz/server.ts`）は試験の土台（makeHarness）の上限の差し替え口 `h.limits` を空のまま立てるので、入口（`apps/api/src/contract/op.ts` の 1) 上限）は契約の値（口の 6 割が 60／分・3 割が 120／分・14 本が 10／分・1 本が 5／分）で数える。鍵は人（Bearer boss の 1 人）か IP（的は x-forwarded-for を付けないので、全部が `unknown` の 1 つ）なので、fuzz の全部の例が同じ鍵に積まれる
- 実測（K-353 の CI 回 44682070516 の G36）：59 本で 4844 例・21.8 秒。schemathesis 自身が「Rate limited: 16 operations mostly returned 429 responses」と出している
- そのため、奥の不具合は「上限に当たる前の最初の数十例」に入ったときだけ赤になる。例の順と時間（VM の混み具合で 1 分の窓に入る数が変わる）で、同じ版でも赤になったり緑になったりする（K-355・K-352 の申し送り・`.ticket-flow/followups.md`）

直し方（1 つの形・特例を足さない）：

1. **的だけ、全部の口の上限を大きくする**（`FUZZ_PER_MINUTE = 1_000_000`）。試験の土台の差し替え口 `h.limits` に入れる。qa-d.test.ts（BIG）・ticket-list.test.ts などが前から使う形と同じ。本番のサーバー（`src/server.ts`）は差し替え口を使わず契約の値のまま
2. **入口の上限に当たった回を数えて赤にする**：的の fetch を包み、入口が上限で断った要求（429 かつ code RATE_LIMITED）を 1 行ずつ記録する。fuzz.sh は schemathesis の後に記録を数え、1 回でもあれば道ごとの回数を出して赤（新しい上限の道ができて奥に届かなくなったら、黙って緑にしない）
3. fuzz が見る物は弱めない：schemathesis の設定（`scripts/ci/schemathesis.toml`）・例の数・seed・並びは変えない。429 を「断った」と数える並びもそのまま（ログインの締め出し E-AUTH-002 などの 429 は製品の振る舞いで、入口の上限とは別）

選ばなかった形：**fuzz の要求ごとに別の人・別の IP として数える**。要求ごとに鍵が新しければ毎回届くが、そのためには schemathesis で要求ごとに頭（x-forwarded-for・Bearer）を変える仕掛けが要り、人ごとの鍵の口のために偽のセッションの人を何十人も作る要がある。的と fuzz.sh の作りが大きくなるわりに、見る物は上げる形と同じ。上限で 429 を返すこと自体は、入口の 1 つの道（op.ts の 1)）からしか出ず、生成の試験（`apps/api/test/generated/*` の `*_rate_limited`・「3 回目が 429・RATE_LIMITED・副作用なし」）と K424-FZ-004 が見ている（ただし生成の試験の `*_rate_limited` は、まだ it.todo の口も多い。それは生成の試験の側の話で、この葉では触らない・申し送り）。

## 実施事項

1. `scripts/ci/fuzz_limited.py`（新しいファイル）：`python3 scripts/ci/fuzz_limited.py <記録>`。記録の各行の前後の空白を落とし、空の行は数えない。0 回（ファイルが無い・空）なら `[G36] 入口の上限（429 RATE_LIMITED）は 0 回` と出して exit 0。1 回以上なら `[G36] 入口の上限（429 RATE_LIMITED）に <合計> 回当たった` と、道ごとに `  <方法 道> ×<回数>`（多い順・同じ数は 1 行（方法 道）の字の順）を出して exit 1
2. `scripts/ci/fuzz.sh`：
   - 的を立てる行に `FUZZ_LIMITED="$TMP/limited.log"` を足す（`FUZZ_BUILT=…` と同じ行）
   - schemathesis を流す行の前に `rc=0`、流す行の終わりに ` || rc=$?`（set -e で止まらず、赤を rc に持つ）
   - その後に `python3 scripts/ci/fuzz_limited.py "$TMP/limited.log" || rc=1` と、最後の行 `exit "$rc"`
3. `scripts/ci/g65.d/K-424.txt`：`python3 scripts/ci/k424_fuzz_limited_test.py` の 1 行
4. `scripts/ci/ci_scope.d/_base.json`：gates "36" の並びの終わりに `scripts/ci/fuzz.sh`・`scripts/ci/fuzz_limited.py`・`scripts/ci/fuzz_targets.py`・`apps/api/test/fuzz/**` を、jobs.database.paths の終わりに `scripts/ci/fuzz.sh`・`scripts/ci/fuzz_limited.py`・`scripts/ci/fuzz_targets.py` を足し、作り手 `python3 scripts/tickets/regen_all.py` で `scripts/ci/ci_scope.json` を作り直す
5. 運ぶ物（切る段が書いた・作る段では変えない）：`apps/api/test/fuzz/limits.ts`（FUZZ_PER_MINUTE・fuzzLimits・applyFuzzLimits・isEntryLimited・recordEntryLimited）と `apps/api/test/fuzz/server.ts`（hooks を差した後に `applyFuzzLimits(h, ENDPOINTS)`・serve の fetch を `recordEntryLimited(h.fetch, process.env["FUZZ_LIMITED"])` で包む）

## リスクと懸念

- **奥の不具合が前からある口で出る**：上限を外すと、今まで 429 に隠れていた 500・ST202 などがチケットの CI の G36 で赤になるかもしれない（範囲の地図を直したので、この葉のチケットの CI で G36 が流れる。G36 は範囲に依らず、作った口の全部（今は 59 本ほど）を回す）。出たら、作る段の TS はその場で直さず、出た口・例・schemathesis の再現の命令を全部集めて 1 回で PM に出す（今のチケットが取り込めなくなる物なので、PM が決める人に聞いて、直しの葉を前に入れるか決める）。この葉の中で schemathesis の設定に外す口を足して緑にすることはしない（検査を緩めない）

- 切る段では schemathesis が手元に無いので、上限を外した G36 を前もって流していない。奥の不具合が出るかどうかは、作る段のチケットの CI で初めて分かる
- G36 の時間が延びる（上の「速さ」）
