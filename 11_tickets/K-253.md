## 目的

外枠の左上の会社の印は、名前を返す口ができるまで頭文字だけ出す決まりだった（D-144.2）。決める人が、今回この会社名を出す口も作ると決めた（answer=f0b42d2edbed・2026-11-16）。画面の側（欄が在れば頭文字と会社名を出し、無ければ出さない）は外枠のチケット（K-138）が持つ。このチケットは口の側だけで、外枠がいま役と名前を読んでいる口（`apps/web/features/F4/create-ticket/ticket-shell.tsx` → `useMyRoles`（`apps/web/lib/auth/role.tsx`）→ 鍵 `["me"]` の `me()`（`apps/web/lib/auth/ext.ts`）→ `GET /api/auth-ext/me`）の答えに、今いる会社（ワークスペース）の名前の欄 `workspace_name` を足す。

## 前提と制約

- 「今いる会社」は、セッションが指す会社（app.session_check が返す tenant_id・D-125.150 の同じログインの人が別の会社にも入っている場合も、セッションの会社だけ）

- 名前の扱い：前後の空白（全角を含む）を取る。取った後に空なら null（空の文字を返さない）。長くても切らない（画面が詰める）。会社の行が読めない（消した印つき）なら null で、ほかの欄は今のまま返す（500 にしない）
- 前からの欄（member_id・tenant_id・display_name・role_id・scope_id）の名前と値は変えない（読む画面が 4 つある：ticket-shell・ai/chat・require-setup・role.tsx）
- 画面の型（apps/web/lib/auth/ext.ts の me() の型）は画面の側なので K-138 が直す。このチケットは apps/web に触らない
- 試験を書いた後は変えない（D-128.125）。実装の前に試験を流して赤を確かめない（D-128.143）

## 確かめたこと（切る段・2026-11-16）

1. 外枠が読む口：ticket-shell.tsx は useMyRoles を使い、useMyRoles は `useQuery({ queryKey: ["me"], queryFn: me })`、me は `ext("/me")`＝ `GET /api/auth-ext/me`（apps/api/src/auth/ext.ts の `app.get("/me", …)`）。答えは `{ data: { member_id, tenant_id, display_name, role_id, scope_id } }`
2. この口は手で書いた道すじで、移す先は契約の口 getMe（08_api/auth-ext-routes.json の `"to": "getMe"`・D-128.88）。getMe の答えの形は 05_flow/screen_api.py 798 行 `"getMe": ("Me", {"member": "object", "workspaces": "array"})`、契約は 501、目録の持ち主は K-70
3. 会社名は tenants.name（not null・登録で前後の空白を取って 120 文字まで・migration 0020／0021）。行レベルの制御は `tenants_tenant_read`（app.member_ok() かつ今の会社）
4. 欄の名前：この口の答えは鍵が英字の小文字と _（tenant_id・display_name）。契約は利用者に見せる言葉を「ワークスペース」で書く（Me.workspaces・DELETE /me/workspaces/:id）。外枠の作り手が仮に置いた workspace_name と合うので、そのまま workspace_name にした（招待の下見の口は tenant_name を返すが、別の口なので合わせない）
5. 試験の組み方：この口は契約の hooks ではなく authExt の道すじなので、試験の道具（features/fixture.ts）では叩けない。前からの apps/api/test/draft_credentials.test.ts と同じく、本物のログイン（Better Auth・セッションの見張り）で組む
