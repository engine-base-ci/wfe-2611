## 前提と制約

分類: CRUD

- **記憶を直す（updateMemory）**：契約は body を文字だけにする（INPUT_RULES の allOf）。口は前のまま（null・空白だけは 422 欄 body「覚えることが空です」）。入口の zod は変えない（null を通し、口が断る：K144-SHAPE-023 の決まり）
- **記憶を作る（createMemory・表の素の書き込み）**：覚えること body は文字（INPUT_RULES の allOf・PATCH と同じ）。**null は契約に合わず 422（欄 body）**、無いのは 201（`{}` も 201 のまま）。実物の失敗（K-424 の G36・手元の記録 `.ticket-flow/side-notes/PM-fuzz-契約の見本/memories-fuzz-実物.md`）は POST も PATCH も body が null だけだった。以下の外部キー・種類・確かさは、**実物の体が乱数の uuid（承認した人・要約・持ち主・置き換え先）を含んでいた**ので、body を直した次に同じ 422（DB の外部キー）が出る類の先回りとして残す（確かさ・種類は実物では通っていた値で、DB の桁・外部キーが断る値を契約に書く先回り。外すと G36 が 1 つ縮んだ例で出し直しになる）：種類 kind_id は `rule`・`preference`・`example` か null（契約の enum・DB の memory_kinds の 3 行と同じ）。確かさ confidence は numeric(3,2) の桁と**同じ**（四捨五入で 10 以上になる 9.995 以上は契約に合わない・9.994 は合う）。承認した人・承認の時刻・要約・置き換え先・持ち主は本人が決めない欄で、**送っても受けて、入れない**（持ち主は本人・ほかは空のまま）。契約の入力の形は変えない（表の形から欄を外すと、手書きの入力の `_id` は uuid の決まり K144-SHAPE-004 に当たる）
- **引き取り（claimPairingCode）**：形どおりのコード（英数字 6 けた・表記ゆらぎを直した後）が DB で使えない（違う・期限切れ・使い終わった・出し直す前）は **404 E-CONN-013**・正本の文。欄・details は付けず detail は空。形の誤り（5 文字・空・33 文字・使わない字）は 422 欄 code のまま。1 分に 5 回の上限（429）・コードの 1 回だけ・期限・PC の印の渡し方は前のまま。Bridge は body の文を窓に出すので状態コードが変わっても動く（claimReply は状態で分けない）
- エラーの類：E-CONN-013 を `validation` → `not_found`（`errors.d/_base.json`）。口は `new KanameError(code).status` で番号を決めているので、口の状態の番号は類から出る（E-CONN-013 → 404）
- 契約 fuzz の期待：契約に合う入力を口が 422 で断らない／契約に合わない値は 4xx で断る
- 試験はこのチケットを切る人が書き、実装する人は変えない（D-128.125）。実装の前に試験を流して赤を確かめない
