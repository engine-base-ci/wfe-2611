## 目的

決める人の決定 D-128.169（チケットごとの CI は機械で出した影響の範囲に絞る）は K-107 で仕組みが入ったのに、2026-11-09 の取り込み 2 回（K-144・K-143）はどちらも「範囲：全部」で流れ、1 回 23.5 分かかった（11 組を順に 1 つずつ・段の合計 20.1 分）。決める人「なんでそんなに CI が時間かかるの」「更新部分とか影響部分だけ流してそうなんだ本気で？？」。act の回の記録を実測して原因を 3 つに切り分けた。

1. **範囲の表の抜け**：`scripts/ci/ci_scope.json` に生成物（07_functional/*・08_api/*・07_qa/test-plan/*・11_tickets/tickets.json・01_hearing/要件一覧.md ほか `scripts/ci/generated.json` の outputs）と、その作り手（05_flow/*.py）が載っていない。載っていないファイルは unmapped として「全部」に倒れる。どのチケットも取り込みの前に生成物を作り直すので、実質どのチケットも全部になる（K-144 の回の理由：unmapped（05_flow/build_api.py・07_functional/features.json・08_api/api-decisions.json …））
2. **spec の G27（層の棚卸し）3.5 分**：`layer_audit.py --run` が 62 の検査を全部流し直す。中に `pnpm -s type-check` 8 回・bridge の build 2 回・trace_gate 6 回など、static の段（G1・G2）や spec の他の段で既に流している検査の繰り返しが入っている
3. **spec の G46（部品の確かめ）2.6 分**：`stack_gate.py` の S6 が毎回 npm の registry に lockfile の全部（約 1,000 個）の出た日を聞きに行く。lockfile が変わっていない回でも同じ答えを取りに行く

## 完了の条件

- [ ] 範囲の表に生成物とその作り手を載せ、普通のチケット（アプリの部品だけを変える）の CI が「触った部品の単体の試験 ＋ static ＋ spec」だけになる。act の static の段の「チケットの CI の範囲：」の行で確かめる（全部にならない）
- [ ] G27 は「static と spec の他の段で流していない検査だけ」を流す（繰り返しは一覧に残し「○○の段で流す」と印を付ける）。G27 の時間が 1 分未満
- [ ] G46 の S6 は lockfile の内容の印（sha）が前回と同じなら記録（リポジトリの中の JSON）から答え、違うときだけ registry に聞く。記録には聞いた日を書き、21 日の決まり（D-128.124）の判定は今日の日付で行う。G46 の時間が 10 秒未満（lockfile が変わらない回）
- [ ] act の並べ方に合わせて組の依存（needs）を整える：act は「needs の無い組」を 1 段目、それを待つ組を 2 段目…と段ごとに流し、段の中の全部が終わるまで次の段を始めない（GitHub は組ごとに needs が揃い次第始める）。いま spec は needs が無いので 1 段目で static と並び、spec が終わるまで database・unit・web が始まらない（2026-11-09 22:10 の実測：static が 1 分 20 秒で緑の後、spec だけが 1 本で走っていた）。spec に `needs: [static]` を足す（GitHub でも意味は変わらない・static は 1 分台）。act の段の並びは act.log の Start image の時刻で確かめる
- [ ] 組を同時に流しても成果物（upload-artifact）が落ちない：3 組同時にすると、組の容れ物（Docker の VM・host network）から Mac の LAN の IP（act の成果物サーバー 192.168.0.120:34567）への接続が EHOSTUNREACH で落ちる（2026-11-09 の実測：4 回目は 5 組・5 回目は 7 組全部。1 組ずつの回は今日 3 回とも届いた。落ちた後に同じ住所へ curl すると 200）。原因の候補は台の負荷（Docker 4 CPU・Mac 10 CPU）で VM の網が詰まること。Docker の CPU を 6 に・同時 2 で測る → それでも落ちるなら、成果物を act のサーバーに上げずに作業場の置き場（--artifact-server-path の下）へ直に書く形（workflow の upload を act のときだけ cp にする composite action）を検討する。測った数字を報告に書く
- [ ] 全部を流す回（取り込み 5 本ごと・CI の設定を触った回）が 3 組同時で 8 分以内、普通のチケットの回が 3 分以内（act の run.json の start/end で実測して報告に書く）
- [ ] 範囲の判定の試験（ci_scope_test.py）に「生成物だけを変えたら spec だけ」「作り手を変えたら spec だけ」の行を足す。G27 の絞り込みと G46 の記録の試験を足す

- [ ] 生成試験（apps/api/test/generated/*）の beforeAll（makeHarness）の 10 秒の上限は、台の負荷で割れる（2026-11-09 21:30 の回で unit-2 が時間切れ・同じ日に 3 回は緑）。起動にかかる時間を CI の記録から測り、上限を「実測の最大 × 3」の形で決めて 1 か所（vitest.config の hookTimeout）に置く。時間で隠すのではなく測って決める
- [ ] チケットの CI（act）が緑

- 範囲を絞り過ぎると、生成物の作り手の変更が unit の試験に効く場合を見落とす。取り込み 5 本ごとの「まとめの全部」が拾う（正本 §9）
