## 目的

チケットの本体の表（チケット・本文の区画と版・種別と区画の並び・作業の段・分類の軸と値・渡すときの決まり）を作り、契約の API が読み書きできるようにする。行の守りで、他の会社・グループの外の人には見せない（関わっている人は除く）。

## 完了の条件

- [x] migration（`packages/db/migrations/0071_tickets.sql`）で表と列ができ、まっさらな DB に全部入る（71/71）
- [x] 表ごとに RLS の決まり（`packages/db/policies/0071_tickets.sql`・gen_rls.py ← `05_flow/rls_policies.py`）がある
- [x] repository の表の一覧（`packages/db/src/repository.ts` の TABLES）に入っている
- [x] 場合表（access-matrix.json）にこの表の行があり、全部通る（全体で 1220 件 PASS・FAIL 0）
- [x] チケットの子の表（本文・版・分類）は元のチケットの見え方に従う（D-128.115）
- [x] 番号はグループの頭＋連番で、横渡し・頭の変更で変わらない（D-128.115）
- [x] 上限（種別 10・作業の段 8・足す軸 5・区画 20）と親子 3 段が DB でも守られる
- [ ] CI が緑のまま（全部の試験を流して確かめる）

## 前提と制約

- 表は ER 図 §16 と「足す列」が正。足すだけで、消す・名前を変える migration は作らない
- 全部の表に `tenant_id` と RLS。RLS を飛ばす鍵はサーバーで使わない（ZT3）
- 範囲（グループ・本人・担当・承認する人・取引先の人・運営の 1 時間の許可）は RLS の条件と API の権限の両方で見る（ZT4・D-073）
- 前の `tasks` は後のフェーズのものとして残す（D-127.1）

## 決定ログ

- 番号は横渡しで変えない。頭を変えても作った番号は変わらない。「前の番号なら新しい番号へ案内」はやめる（D-128.115・2026-11-03 高本さん）
- グループの外でも関わっている人は、関わっている間そのチケットを読める。担当者は書ける（D-128.115・2026-11-03 高本さん）
- 消したチケットは 30 日後に本文ごと完全に消し、「消した」記録だけ残す（D-128.116・2026-11-03 高本さん）。消す仕事そのものは KN-11（チケットの 1 件：消す・戻す）で作る
- 優先度は 中・高 のまま（D-128.116・2026-11-03 高本さん）
- 初めの種別は 4 つ（タスク・課題・QA・会議）。課題・QA・会議の区画は D-128.117 の案（2026-11-03 高本さん）

## リスクと懸念

- 場合表は「層を持たない表は会社全体が見える」として扱うので、子の表が親に従うことは確かめきれない。ここでは専用の試験で確かめた。場合表そのものを直すのは KN-47
- `has_permission` は、会社全体の権限を確かめるとき（層＝なし）に、1 つのグループだけに付けた権限でも通してしまう。グループの edit を持つ人が、会社全体の決まり（種別など）を直せる恐れがある。KN-3 で直す

## 申し送り

- KN-39（ticket_handovers）と KN-44（approvals.ticket_id）で `app.ticket_involved` を作り直し、渡された相手・承認する人を入れる（今は担当者だけ）
- KN-41 で `tickets.client_id` に外部キーを付け、取引先の人（client）が見せると決めたチケットだけ読める決まりを足す
- KN-42 で兼務（scope_memberships）を `visible_scopes` に入れる
