## 目的

確かめは二重にする（2026-11-13・決める人）：CI の画面の試験（機械）と、人が実機を触る確かめ。CI は画面の写真を残さなくなった（K-186）ので、人の目の確かめは「テスト仕様書」の表（Excel）で行う。
表を手で書き起こすと、チケットと試験の仕様の表（正本）からずれる。正本から台本で作り、人が書くのは結果（確認日・確認者・試験日・OK/NG・エビデンス・備考）と課題管理だけにする。作り直しても、人が書いたものは消さない。

- 1 チケット＝1 冊（小さい）。子・孫を持つチケットは、子・孫の行をまとめた 1 冊
- 中間・統合のチケット（kind: QA）は、組のチケット（depends_on）の行を流れの順にまとめた 1 冊

## 完了の条件

- [ ] `python3 scripts/qa/human_sheet.py <チケット番号>` が、下の表の行のとおりに 07_qa/human/<チケット番号>.xlsx を作る・作り直す
- [ ] 試験 K188-HS-001〜020 が緑・チケットの CI が緑
- [ ] 実装した人が、本物のチケット 1 本（画面の行を持つもの）と中間のチケット 1 本で冊を作り、Excel で開いて 6 つのシートと列を目で見た（作った冊はコミットしない。最初の冊を版に入れるのは、人の確かめを始めるチケット）

## 前提と制約

- 正本は 11_tickets/K-*.md の頭の欄（id・title・kind・parent・depends_on）と、07_qa/test-specs/k/*.md の表（列：ID・画面・テスト観点・テスト項目・前提条件・操作手順・期待結果・結果・備考・タスク・実行条件）。台本は正本を読むだけで、書き換えない
- 前からある scripts/ci/build_qa_xlsx.py（古い手順のファイルから作る別の作り手）は変えない。前の版が読めないときに黙って空として続ける作り（人の結果が消える）は、こちらでは取らない
- 作った冊は人の結果が入るので版に入れる。作り手の目録（scripts/ci/generated.json）には足さない（作り直すと人の結果ぶん中身が変わる物で、目録の検査の対象ではない）。台本の先頭 3 行に、目録の検査が拾う言い回し（scripts/ci/generated_gate.py の MARK）を書かない
- 環境の値（URL・アカウント・合言葉）は冊に書かない。「どこを見るか」だけを書く
- 環境は手元（scripts/dev/up.sh）だけを書く。staging の行は、staging をそろえるチケットがこの台本の「試験前提条件」の中身に足す
- 冊を作る命令は、人の確かめを始めるときに PM か確かめる人が流す。進め方（ticket-flow）の段から自動で呼ぶ所は、このチケットでは作らない
- openpyxl（3.1.5）を使う。CI の部品の一覧（scripts/ci/requirements-ci.txt）に版つきで足す

### 冊に入るチケットと行

| 欄 | 決まり |
|---|---|
| 人が触る行 | 仕様の表の行のうち、ID が `…-UI-…` の形の行（画面の行）を全部。口の行（`…-API-…`）とほかの形の ID の行は入れない：口は人が画面から直に触れず、口の試験が本物の DB で持つ。画面から起きる口の結果は、画面の行の期待結果に書いてある |
| 行の持ち主 | 仕様の表の「タスク」の列のチケット番号（`,` で区切って複数可）。番号はそのまま比べる（K-5 と K-50 を取り違えない） |
| ふつうのチケット | そのチケットと、parent: をたどった子・孫の行。並びは仕様の表の順（ファイルの名前の順 → 表の中の順）。depends_on の先のチケットの行は入れない |
| 中間・統合のチケット（kind: QA） | depends_on に書いた順に、1 つずつ「ふつうのチケット」と同じまとめ方で並べる。depends_on の先が kind: QA なら、その depends_on を同じ決まりで開く。同じ行（同じ ID）が 2 度出たら最初の 1 度だけ。QA のチケット自身が持ち主の画面の行があれば最後に置く |
| 行が 1 つも無い | 冊を作らず、理由を出して止まる |
| 詳しさの穴 | 入る行のうち、テスト項目・前提条件・操作手順・期待結果のどれかが空（空白だけ）の行があれば、冊を作らず、行の ID と欄の名前を全部出して止まる（穴は正本の側で埋める） |
| 正本の形の誤り | 画面の行の ID が 2 つのファイル・2 つの行で重なる／欄の数が 11 でない行／頭の欄 depends_on が 1 行の並び（`[K-1, K-2]`）でない → ファイルの名前と行の ID（か欄の名前）を出して止まる |

### シートと列（参考の「テスト仕様書」の形に、仕様の表の列を当てる）

シートは この順：テスト項目・進捗サマリ・試験前提条件・エビデンス・課題管理・前の版の結果。

**テスト項目**（1 行目に題「【人の確かめ】<番号> <題>」と 項目数・消化数・OK 数の式。見出しは 4 行目・行は 5 行目から・見出しで窓を固定）

| 列 | 見出し | 入れるもの | 書く人 |
|---|---|---|---|
| A | No | 1 からの通し番号 | 台本 |
| B | 機能名/画面名 | 仕様の表の「画面」 | 台本 |
| C | 区分１ | 行の持ち主のチケット番号（タスクの列に複数あれば、この冊で先に出るチケット 1 つ） | 台本 |
| D | 区分２ | 「テスト観点」 | 台本 |
| E | 区分３ | 「テスト項目」 | 台本 |
| F | 区分4 | 「実行条件」（L1 など） | 台本 |
| G | パターン番号 | 「ID」（K63-UI-001 の形。引き継ぎの鍵） | 台本 |
| H | 検証内容/パターン説明 | `【事前条件】<前提条件>` 改行 `【操作】<操作手順>`。仕様の表の「備考」が空でなければ、改行 `【補足】<備考>` を足す。表の中の `\|` は `|` に戻す | 台本 |
| I | 確認項目 | 「期待結果」 | 台本 |
| J〜O | 確認日・確認者・試験日・OK/NG・エビデンス・備考 | 空（OK/NG は OK か NG を選ぶ） | 人 |

仕様の表の「結果」（機械の試験の PASS・BLOCKED）は入れない（人の結果と混ぜない）。

**進捗サマリ**（見出しは 3 行目：No・チケット・題・項目数・消化数・OK数・NG数・消化率・合格率）：冊に行を持つチケット 1 つにつき 1 行（冊に先に出る順）と、最後に「合計」の行。数はテスト項目の C 列と M 列を数える式（人が OK/NG を入れると変わる）。消化＝OK/NG の欄が OK か NG、合格＝OK。

**試験前提条件**（A 項目・B 中身・C 記入。3 行目から）

| 項目 | B 中身（台本が書く） |
|---|---|
| 試験目的 | CI の画面の試験（機械）と別に、人が実機で触って確かめる |
| 対象 | この冊のチケットの番号と題（まとめた冊は、入っているチケットを順に全部） |
| 試験範囲 | 画面の行 N 件。口の行は CI の試験が持つので入れない |
| 参照資料 | 11_tickets/<番号>.md と、行を読んだ 07_qa/test-specs/k/ のファイルの名前 |
| 試験環境 | 手元（自分の PC）。実ブラウザ |
| 立ち上げ方 | `bash scripts/dev/up.sh`（止める：`--stop`・今の状態：`--status`） |
| URL とアカウント | URL は `bash scripts/dev/up.sh --status` に出る。アカウントは自分で新規登録して作る（やり直すとき：scripts/dev/reset-users.sh・招待が要るとき：scripts/dev/invite.sh）。値はここに書かない |
| 必要な準備 | 各行の【事前条件】のとおりに画面から作る。作れない事前条件は NG にせず課題管理に書く |
| 判定基準 | 全部の行が OK。NG が 1 つでもあれば、このチケットは人の確かめを通っていない |
| NG のとき | 課題管理に 1 行書く（パターン番号・現象）。直した後に同じ行を確かめ直す |
| エビデンスの置き方 | 下の「決める人に聞く」の答えの文（答えが出るまでは「エビデンスのシートに、何を見たかを文で書く」） |
| 試験者 | B は空。C に人が書く |
| 確認者 | B は空。C に人が書く |
| 試験期間 | B は空。C に人が書く |

**エビデンス**（見出しは 3 行目：No・対応するパターン番号・取得日・取得者・種別・ファイル名／内容）と **課題管理**（見出しは 4 行目：No・パターン番号・機能名/画面名・現象内容・対応内容・ステータス・記入日・記入者・対応日・対応者・確認日・確認者・OK/NG・エビデンス・備考）は、見出しと No だけを置き、行は人が書く。

**前の版の結果**（見出しは 1 行目：パターン番号・理由・検証内容/パターン説明・確認項目・確認日・確認者・試験日・OK/NG・エビデンス・備考）：作り直しで行から外した人の結果を、消さずにここへ足す（下の表）。

### 作り直し（前の冊があるとき）

| こと | 決まり |
|---|---|
| 同じパターン番号の行が今もあり、H（検証内容）と I（確認項目）が前と同じ | J〜O をそのまま引き継ぐ（行の並びや A〜F が変わっても） |
| 同じパターン番号の行が今もあるが、H か I が前と変わった | 前の J〜O は、その行に残さない（前の中身に対する OK を今の中身の OK にしない）。J〜O のどれかに書いてあれば「前の版の結果」に理由「中身が変わった」で前の H・I と一緒に足す。行の J〜O は空に戻る（確かめ直し） |
| 前にあったパターン番号が今は無い | J〜O のどれかに書いてあれば「前の版の結果」に理由「行が消えた」で足す。何も書いていなければ消えるだけ |
| 新しいパターン番号 | J〜O は空 |
| エビデンス・課題管理・前の版の結果 | 人が書いた行（No の他の欄に何か書いてある行）を全部、同じ並びで引き継ぐ |
| 試験前提条件の C（記入） | A の項目の名前で引き継ぐ |
| 列の幅 | どのシートも、前の冊の幅を引き継ぐ |
| 前の冊が開けない（壊れている） | 冊の道を出して止まる。上書きしない |
| 正本も人の結果も変わっていない | 何度作り直しても、どのシートのどの欄の値も変わらない（日付や時刻を冊に書かない） |

## 決める人に聞く

1. エビデンス（人が撮った画面の写真など）のファイルをどこに置くか。台本の作りはどちらでも同じで、試験前提条件の「エビデンスの置き方」の 1 行の文だけが変わる
   - A（推し）：リポジトリには入れない。手元か共有の置き場に置き、エビデンスのシートにはファイルの名前と置き場を書く（写真でリポジトリが重くならない。CI で写真を残さないと決めたのと同じ向き）
   - B：リポジトリの 07_qa/human/evidence/<チケット番号>/ に入れてコミットする（冊と写真が同じ版で残る。リポジトリが写真の分だけ重くなる）

ほかに聞くことは無い。切る段で、合意（画面の行は全部・口の行は入れない・人の結果は消さない）から決めたこと：

- ID が `-UI-` の形でない行（部品の見本の表の KSC-… など）は冊に入れない（合意の「画面の行＝ID が …-UI-… の形」のとおり）
- 行の中身（検証内容・確認項目）が変わったら、前の結果はその行に残さず「前の版の結果」へ移す（消さないが、前の中身の OK を今の OK にしない）
