## 目的

設定の画面の「ワークスペースを消す［消す手続き］」の小窓（下絵 st-delete・st-delete-ready）と、手続き中の帯の「本人確認して取り消す」（st-deleting）が使う口。

- `requestWorkspaceDeletion`（POST /api/v1/workspace/deletion）：名前を打って確かめ・本人確認を取り直し、消す手続きを始める（14 日のあいだ取り消せる）
- `cancelWorkspaceDeletion`（DELETE /api/v1/workspace/deletion）：14 日のあいだ取り消す

**手続き中も全員いつもどおり使える**（D-154.5）：人を止めない・セッションを切らない・機能を止めない。上の帯の「あと N 日」は読む口（K-827）の `deletion` から作る。**14 日を過ぎたら運営が消す＝段 11 は消す仕組みを作らない**（時間で動く仕組みは無い・D-148.9。運営の F12 が段階 2 で受ける）。**先に書き出せるは無い**（D-154.4）。

## 前提と制約

分類: PERM, CRUD

- **押せる人**＝ `app.workspace_can('delete_workspace')`（K-827 が作る）が true の人：管理者・「管理者とマネージャー」にしたときのマネージャー・個別に付けた人。取り消せるのも同じ人（手続きを始めた人でなくてもよい・D-154.5）。この人たちは設定の画面を開け、消す区画だけ押せる（D-154.83・K-827 の access・K-831／K-832）。契約の入口の言葉は管理者の束から **write（ログインした会社の人だけ・運営は通さない）に下げ**（K-827 の読む口と同じ）、口の中で判定を見て、無ければ 403（権限の 403 と同じ形・中身を返さない）
- **順**：入口の本人確認（契約の step_up は always なので op.ts の 3.2 が先に 403・STEP_UP_REQUIRED・直前 15 分・D-154.18）→ 口の判定（403）→ 名前（409・E-WS-030）→ 状態（409）→ 実行
- **入力** `{ confirm_name: string }`（始める口だけ・strict）：1〜100 字・NUL は入口で 422。**打った名前が今の名前と同じか**は DB の中身で決まるので 409・E-WS-030（控え帳：契約に書けない 422 は使わない）。**正確に比べる**＝全角半角・前後の空白・大文字小文字を同じとみなさない（打ち間違いで消えるのを防ぐ）
- **状態**：始める → すでに手続き中は 409・E-WS-031。取り消す → 手続き中でなければ 409・E-WS-033・始めて 14 日（`deletion_requested_at + interval '14 days'`）を過ぎていれば 409・E-WS-032（D-154.16・D-128.65）。**14 日の境**：13 日 23 時間は取り消せる・14 日 1 分は取り消せない
- **会社ごとの錠 `app.admin_lock()`（K-800）で順に通す**（G-16・D-154.21）：同時に 2 人が始めると 1 つだけ成功し、もう 1 つは 409・E-WS-031。K-827 の名前の保存・K-829 の「誰ができるか」と同じ錠にそろえる（tenants の行の `for update` は錠の後に読むときに付けてよいが、別の錠にはしない）
- **始めた・取り消した**とき、ほかの有効な管理者全員（呼んだ本人を除く・止めた人・外した人を除く）に受け箱の行を 1 通ずつ：種類 `workspace.deletion_requested`・`workspace.deletion_cancelled`・channel `inapp`・メールは出さない・payload は `{ by: { id, name }, delete_at? }`・dedupe_key は種類＋手続きの時刻＋宛て（二度押しで増えない）。マネージャー・メンバー・閲覧のみには出さない
- 記録（追記だけ・D-154.25）：`workspace.deletion_requested`・`workspace.deletion_cancelled`（payload は `{ requested_at }`・取り消しは始めた時刻と日数）
- DB の失敗は 503（E-PAGE-003）。始める・取り消す本体と受け箱・記録は 1 つの取引（途中で落ちたら全部戻る）
