## 目的

チケットの CI は workflow の全部（static・database・unit-1〜6 の試験 約 2,400 本・spec・web）を毎回流し、小さなチケットでも 15 分かかっていた。影響の範囲はチケットを切る時点で書く決まりが既にあり、毎回の全部は目的に対して無駄（D-128.169）。依存の地図で影響の範囲を機械で出し、そこだけ流す。抜けは区切りの全部で拾う。

## 完了の条件

- [ ] 変えたファイル → 依存の地図（パッケージの依存・import のつながり）→ 影響を受ける試験、を出す台本がある
- [ ] チケットに書いた影響の範囲と、機械で出した範囲を突き合わせ、片方にしか無いものを赤にする
- [ ] migration・共通の部品・CI の設定・部品の版（lockfile）に触ったときは全部を流す
- [ ] workflow に「範囲を絞る」入口（workflow_dispatch の入力など）があり、act_ci.sh から渡せる。GitHub でも同じ workflow で動く
- [ ] 決まり（ai-driven-process.md §1 原則 7・§9）とスキル（ai-team-delivery の references/ci.md・act_ci.sh）を直し、.skill を作り直す
- [ ] 範囲を絞った回と全部の回の両方が緑。小さなチケット（例：文言 1 か所）で時間が縮んだことを数字で出す

## 前提と制約

- 仕組みが入るまでは、今の全部を流す
- 型・lint・生成物の検査は速いので毎回流す
- 自作の実行器は作らない。workflow の中で範囲を受け取る形にする（GitHub と同じ workflow のまま）

## 実施事項

- [ ] 作る役：依存の地図の作り方を決める（pnpm のワークスペースの依存・vitest の changed / related など既存の仕組みを先に探す）

## テスト仕様と確認の結果

| 確認項目 | 種類 | 判定のしかた | 結果 |
|---|---|---|---|
| 影響の範囲だけが流れる | ② 結合 | apps/web の文言を 1 か所変えた写しで流し、API の試験が流れないこと・時間 | |
| 全部に切り替わる | ② 結合 | migration を 1 本足した写しで流し、全部が流れること | |
| チケットに書いた範囲と食い違うと赤 | ① 単体 | 影響のあるパッケージをチケットに書かない写しで検査を流す | |
