## 目的

K-999（段 13 の統合テスト）の運営の筋（受信箱で返す・1 社にお知らせ・中を見る・止める日・再開・値段の案）を staging で通すには、**試験の回が使える運営の人とパスキー**が要る。運営の入口はパスキーだけで、外から作れる道は開けない（D-156.22）。そこで、運営の人がふつうの手順（運営の人の画面で足す → 届いたリンクでパスキーを付ける）で試験だけの運営の人を作り、そのパスキーを**仮の認証器**（Chrome の開発者の道具の WebAuthn）で付けて、鍵を GitHub の Environment staging の秘密に置く。試験は秘密の鍵を仮の認証器に入れ直して入る（読む口と試験は K-1102）。

## 完了の条件

- [ ] staging の運営の人の画面に「統合テスト」の運営の人が 1 人いて、できることは 問い合わせ・中を見る・止める・お知らせ・配るもの・値段の案 の 6 つ（お金・値段を決める・運営の人は付けない）・パスキーが「有る」
- [ ] GitHub の Environment staging の秘密に、次の 3 つの名前が在る（値は見ない・書かない）：`STAGING_OPS_PASSKEY_KEY`・`STAGING_OPS_PASSKEY_ID`・`STAGING_OPS_PASSKEY_USER`
- [ ] 書き出した鍵のファイルを消した（ダウンロードの置き場にもゴミ箱にも残っていない）
- [ ] 仮の認証器を外したふつうのブラウザでは、その運営の人で入れない（鍵は秘密の中だけ）ことを確かめた

## 前提と制約

分類: AUTH

- **値を書かない**：秘密鍵・資格の id・利用者の印は、チャット・ファイル・コミット・チケットに書かない。チケットに書くのは設定の名前だけ（ai-driven-process.md §6.1）。書き出した鍵のファイルは秘密に置いたらすぐ消す
- **試験だけの運営の人**：メールは運営が受けられる宛て（顧客として登録したメールとは別・K-944 のリスク）。名前はメールの @ の前（K-985）なので、宛ては「統合テスト」と分かる形にする（例：`<運営の宛ての名前>+ops-e2e@<運営のドメイン>` の形・実際の宛ては運営が決める）
- **できることは最小**：K-999 の運営の筋に要る 6 つだけ（問い合わせ・中を見る・止める・お知らせ・配るもの・値段の案）。お金（請求書を出す・入金）・値段を決める・運営の人は付けない（鍵が漏れても、お金を動かせず・値段を決められず・運営の人を足せない）
- **仮の認証器の設定**（Chrome の開発者の道具 → 右上の︙ → その他のツール → WebAuthn）：「仮の認証器の環境を使う」に印 → 認証器を足す：Protocol ctap2・Transport internal・Supports resident keys に印・Supports user verification に印（運営のログインは名前を打たずにパスキーで入る形）
- **署名の回数**：仮の認証器は署名のたびに回数を 1 つ増やす。試験は回ごとに今の時刻の秒を回数に使う（K-1102）ので、ここで書き出した回数は秘密に置かない
- 鍵を無くした・漏れた疑いがあるとき：運営の人の画面でこの人を外し（K-1009・パスキーとセッションが消える）、この手順をもう一度（同じメールは同じ人として足し直る・K-985）

## 実施事項

1. 運営の最初の 1 人（K-1002）で staging の運営の場所に入り、「運営の人」→「足す」で、メールに試験だけの宛て、できることに 問い合わせ・中を見る・止める・お知らせ・配るもの・値段の案 の 6 つを選んで足す（本人確認の取り直しを求められたら、自分のパスキーで確かめる）
2. 届いたメールのリンク（/ops/setup）を、**仮の認証器を足した Chrome のタブ**で開く（上の「仮の認証器の設定」を先にする。ふつうのパスキー（指・顔・PC のロック）では付けない）
3. 「パスキーを付ける」を押す。開発者の道具の WebAuthn の Credentials の表に 1 行出たことを確かめる
4. その行の「Export」で秘密鍵のファイル（PEM）を書き出す。同じ行の Credential ID と User Handle は、画面から写さず、次の命令で直に秘密に入れる（クリップボードを使ったら、使った後にクリップボードを空にする）
5. 秘密に置く（GitHub の画面の Settings → Environments → staging → Add secret でもよい）：
   - `gh secret set STAGING_OPS_PASSKEY_KEY --env staging < <書き出したファイル>`
   - `gh secret set STAGING_OPS_PASSKEY_ID --env staging`（聞かれたら Credential ID を貼る）
   - `gh secret set STAGING_OPS_PASSKEY_USER --env staging`（聞かれたら User Handle を貼る）
6. 書き出したファイルを消し、ゴミ箱も空にする。`gh secret list --env staging` で 3 つの名前が在ることを確かめる（値は出ない）
7. 開発者の道具の WebAuthn で、足した認証器を外し「仮の認証器の環境を使う」の印を外す。ふつうのタブで運営のログイン（/ops/login）の「パスキーで入る」を押し、この運営の人では入れない（パスキーの選び先に出ない）ことを確かめる

## 外に影響する手順

1. staging の DB に運営の人・リンク・パスキーの行ができる（K-985・K-1003 の口が書く）［残る］（失敗：足す小窓が断りを出す（もう運営の人・顧客のメール）・宛てを替えてもう一度）
2. メールを 1 通送る（K-985 の口）（失敗：届かなければ、運営の人の画面で同じ宛てを外して足し直す）
3. GitHub の Environment staging に秘密を 3 つ置く［残る］（失敗：gh が 0 以外で終わる・権限を確かめてもう一度。後片付け：置き違えたら `gh secret delete <名前> --env staging`）
