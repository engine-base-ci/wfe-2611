## 目的

K-990 で決めた値段の版が、実際に請求書とプランの選びに効くようにする（D-128.72「いまの顧客はお知らせから N 日たった最初の月の分から新しい値段／ずっと今の値段のまま（新しく入る人だけ新しい値段）」・下絵 oq-plan-review の「決めると起きること」の 3〜4）。

- **1 か所**：`app.plan_terms(p_plan uuid, p_tenant uuid, p_day date) returns jsonb`（`{ version, price_monthly, member_limit }`）。会社とその日で、効いている版を決める
- **読む所を置き換える**：K-981 の請求書の行（`app.ops_invoice_lines`）・K-961 の選べるプラン（`app.workspace_plans`）・プランを変える決め（K-968 が K-961 の `app.plan_change` から分けた `app.plan_change_for`。会社の口と運営が代わりに変える口の両方が呼ぶ）・**K-968 の運営が見る 1 社の値段と上限（`app.ops_workspace_billing`）**・**K-1103 の招く・リンクの口の席の確かめ（`app.seat_check`）**が、`plans.price_monthly`・`limits->>'members'` を直に読む所を `app.plan_terms` に（式を写さない）
- **設定の「変わる」**：listWorkspacePlans のいまのプランの行の `upcoming`（K-962 がまとめ役に頼んだ欄）を、この葉が埋める

## 前提と制約

分類: PAY

- 口の持ち主：listWorkspacePlans の持ち主（apis:）は K-961。この葉は口を足さず、その口の答え・入力を変えるだけなので apis: は空（hooks の登録は K-961 のまま。同じ口を 2 つの葉が持たない）
- **効いている版の決め**（`app.plan_terms`・security definer・stable・関数の中の 1 か所）：その会社のそのプランの始めた日 S（効いている `subscriptions.started_at` の日本の日付・契約が無ければ会社を作った日）。そのプランの版の行（`plan_versions`・K-990 の列）を版の新しい順に見て、最初に当たる版：
  - 版 1（`proposal_id` が null の種の行）はいつも当たる
  - 新しく入る人：`S >= greatest(coalesce(new_from, released_at の日本の日付), released_at の日本の日付)`（new_from が決めた日より前でも、決めた日より前に始めた会社＝もういる顧客には新しく入る人の値を当てない。もういる顧客の変わる月は existing_from だけで決まり、昔にさかのぼらない・K-988 の K988-API-014）
  - いまの顧客：`existing_from is not null and p_day >= existing_from`
  - 版の行が 1 つも無ければ `plans` の `price_monthly`・`limits->>'members'`（前と同じ答え＝前からの試験が緑）
- **請求書**：`app.ops_invoice_lines` の「値段の契約のプランの price_monthly」を `app.plan_terms(<そのプラン>, <会社>, <その月の 1 日>)` の price_monthly に（税・日割りの式は変えない）
- **選べるプラン**：`app.workspace_plans` の各行の price_monthly・member_limit を、いまのプランの行は `app.plan_terms(<そのプラン>, <会社>, <今日>)`、ほかの行は「今日始めるなら」の値（S を今日として同じ決め）に。上げる・下げるの比べも同じ値で
- **upcoming**（いまのプランの行だけ）：そのプランの版のうち `existing_from > 今日` で、今の版より新しい物の最も早い 1 つ → `{ price_monthly, member_limit, from_month（"YYYY-MM"）, noticed_on（版の released_at の日本の日付） }`。無ければ null。ほかの行は null
- **プランを変える**（`app.plan_change_for`・K-968 が分けた 1 か所）：人数の上限・上げる／下げるの比べ・日割りの額を、**全部** `app.workspace_plans` と同じ値で決める。今のプラン＝`app.plan_terms(<今のプラン>, <会社>, <今日>)`、変える先＝`app.plan_terms(<変える先>, null, <今日>)`（今日始めるなら）の price_monthly・member_limit。
  - 上限：変える先の member_limit で比べる（断り over_limit の detail の member_limit もこの値）
  - 上げる／下げる：変える先の price_monthly ＞ 今のプランの price_monthly なら上げる（今日から）・そうでなければ下げる（来月 1 日から）
  - 日割り：`app.plan_prorate(<変える先の price_monthly> − <今のプランの price_monthly>)`。頼みの行の `prorated_amount`（＝次の請求書に足す日割り）と答えの `prorated_amount` は、押す前に `listWorkspacePlans` がその行に見せた `upgrade.amount` と同じ額になる（画面の額と請求書の額を食い違わせない）
  - プランの列（`plans.price_monthly`・`limits->>'members'`）を直に読む所は残さない
- **運営が見る 1 社**（K-968 の `app.ops_workspace_billing`）：`plan.price_monthly` と `members.limit` を `app.plan_terms(<今のプラン>, <会社>, <今日>)` の price_monthly・member_limit に（請求書の行・会社の選べるプランと同じ値）。ほかの欄（plan_key・name・since・members.count・invoices）と答えの形は変えない
- **招くときの席**：K-1103 の `app.seat_check` の上限（今は `plans.limits->>'members'`）を `app.plan_terms(<いまのプラン>, <会社>, <今日>)->>'member_limit'` に。数え方（社内の人＋招待中）・断り（P0001・E-PLAN-003・detail）は変えない。置き換えないと、決めた版で人数を 12 人にしても、プランを変えると選べるプランは 12 人なのに招くは 10 人で止まる
- 置き換えは create or replace で、前の葉の関数の本体の「読む所」だけを変える（ほかの式・断り・答えの形は変えない）。置き換える前の本体は前の葉の migration のとおり（取り込みの順で K-961・K-981・K-968 の後）
- 契約：listWorkspacePlans の行の `upcoming` は K-1005 の断片に在る（D-156.43・K-961 は null で返す）。この葉の断片 `05_flow/screen_api.d/K-1017.py` は住所だけ
- 止めている会社の「再開した月から新しい値段」は、止めている月に請求書を出さない（K-981 の出す会社の決め）ことで受ける。再開した月の請求は、その月の 1 日の plan_terms＝変わる月を過ぎていれば新しい値段
