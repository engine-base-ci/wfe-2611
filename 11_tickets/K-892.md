## 目的

ゲストの依頼（`client_requests` の `guest_group_id` を持つ行・K-878）を、社内の人が読めるようにする（D-155.43：チケットになる前の依頼は、ゲストのグループが持つ「依頼が届く社内のグループ」に届く）。この葉は、依頼まわりの置き場を全部作り、読む口 2 本を作る。ほかの葉（K-893〜K-897・K-907〜K-910）はここの物を使う：

- **依頼のやり取りの表 `client_request_messages`**（D-155.7・会話の表には置かない）。ゲストが書く（`side = 'guest'`）・社内が返す（`side = 'company'`）。最初の本文は依頼の行の `body` に在り、この表には 2 つ目以降が入る
- **案の列**（`client_requests.draft`・`draft_state`・`draft_job_id`・`draft_at`）：分身の案を入れる所。書くのは K-896・K-897。この葉は読んで返すだけ
- **社内の読む・直す守り**：届け先のグループ（`routed_scope_id` があればそれ、無ければゲストのグループの `request_scope_id`）が見える人が読める。直せるのは、その届け先で `client_requests` を edit できる人（`has_permission`）。K-878 が足さなかった方針をここで足す（K-893〜K-895 の更新はこの方針を使う）
- **読む口**：`listClientRequests`（GET /client_requests・問い合わせ `state`：`live`（新しい・聞いている）か `done`（チケットにした・断った）か無し）と `getClientRequest`（GET /client_requests/:id）。形は画面の葉 K-898 が前提にした形と同じ
- **依頼の出し手へお知らせを入れる内部の関数 `app.client_request_notify_author`**：返事（K-893）・断り（K-895）が使う（受け箱の 1 件と、メールの宛先を返す）

書く口は K-893（届け先を変える・返事）・K-894（チケットにする）・K-895（断る）。ゲストが出す・読む・書く口は K-907・K-908。

## 前提と制約

分類: LIST, PERM

- **見えるのは「ゲストのグループの依頼」だけ**（`guest_group_id` が空でない行）。前の取引先の形の行（`client_id` だけ）は読む口に出さない。消した依頼（`deleted_at`）・別の会社の依頼は出さない
- **届け先** `app.client_request_route(依頼)`＝`coalesce(routed_scope_id, ゲストのグループの request_scope_id)`。そのグループが消えていれば null（届け先なし）
- **見える人** `app.client_request_visible(依頼)`：社内の人で、届け先が `visible_scopes(自分)` に入る人、または `has_permission(自分, 'client_requests', null, 'edit')`（会社全体の edit＝管理者）。届け先が null の依頼は、会社全体の edit を持つ人にだけ見える。**直せる人** `app.client_request_actable(依頼)`：`has_permission(自分, 'client_requests', 届け先, 'edit')`。読むだけの人は見えるが `can_act` が false
- 状態の写し：DB の `new`・`asking` は `new`・`asking`のまま、`ticketed`・`declined` は `done`（札 `tag`：`チケットにした`・`断った`）。一覧は新しい物（`new`・`asking`）を `created_at` の新しい順に（`live`）、続けてさばいた物（`done`）を `updated_at` の新しい順に 50 件まで。`counts.live` は新しい物・聞いている物の数
- 読む口は何も書かない（既読の印も付けない・updated_at も変えない・K892-API-014）。答えは `Cache-Control: private, no-store`（入口）
- 答えの形（K-898 の「読む答えの形」と同じ）：
  - 一覧 `{ data: { items: [{ id, title, from_name, group_name, route_name, created_at, state, tag? }], counts: { live } } }`。`from_name`＝出した人（`created_by`）の表示名・`group_name`＝ゲストのグループの名前（グループが消えていても名前は出す）・`route_name`＝届け先の社内のグループの名前（無ければ鍵ごと省く）・`tag` は `done` のときだけ
  - 1 件 `{ data: { request: { id, title, from_name, group_name, route_name, body, state, created_at, ticket_id?, declined_reason? }, messages: [{ id, side, name, at, text }], routes: [{ id, name }], can_act, pc_connected, ticket_draft, reply_draft, questions, route_suggestion } }`。`messages` は古い順・`side` は `they`（ゲスト）か `we`（社内）・`name` は書いた人の表示名。`routes` は見ている人が届け先にできるグループ（`app.client_request_routes()`＝この会社の消していないグループで、見ている人が `client_requests` を edit できる物を名前の順・K-893 の入力の確かめも同じ関数）。`pc_connected`＝**`app.account_pc_live(見ている人)`**（本線 0092 の関数：アカウント全体で、種類 bridge・失効していない・生きた知らせが届いている（`alive_at` あり）・最後の知らせから 75 秒未満。失効していなくても 75 秒より前から静かな PC は false）。K-899 の「案を作る」の前提で、K-896 の積む前の確かめも同じ関数を使う（古いセッションだけが残っていて、積んだ仕事を誰も取らない形を作らない・G-15）。`ticket_draft`・`reply_draft`・`route_suggestion` は `draft_state = 'ready'` のときだけ中身を返し、無ければ null（`ticket_draft`＝`draft.ticket`・`reply_draft`＝`draft.reply`・`route_suggestion`＝`draft.route`）。`questions`＝`client_requests.questions`（K-897 が書く・無ければ空の並び）。`ticket_id`・`declined_reason` は在るときだけ
- 見えない・無い・消した・別の会社・前の取引先の形の依頼は 404・E-GST-100（欄・details なし・在るかを漏らさない）。入口の言葉は read（`perm.row` は付けない・見える判定は関数が持つ＝2 層目は DB の方針）
- 依頼の出し手へのお知らせ `app.client_request_notify_author(p_req, p_kind, p_payload)`：出し手（`created_by`）が今も会社に居て・止めていない・役割ゲストで・依頼のグループに入っているときだけ、受け箱（`notifications`・channel `inapp`・event_kind_id は `p_kind`・payload は `{ request_id }` に `p_payload` を足した物・dedupe_key `p_kind:<p_payload.ref か乱数>:<出し手>`・sent_at は今）に 1 件入れ、`{ member_id, email, notification_id }` を返す（宛先が無ければ null）。`email` は認証の表から引く（メールを送るのは呼んだ口・K-893・K-895）。内部の関数なので口は持たない（public から外し、**誰にも execute を渡さない**＝本線の決まり 0092・D-128.171（中だけで使う関数は渡さない）。K-893・K-895 の security definer の関数の中から呼ぶ）。見える・直せる・届け先の関数（`visible`・`actable`・`route`）は方針の式から呼ぶので kaname_app に渡す
- 関門の宣言（頭の欄 choke_points）は [C2]（読むだけ。受け箱の行を書く関数は K-893・K-895 が使う時に C6 を宣言する）
