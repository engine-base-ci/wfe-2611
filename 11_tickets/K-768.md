## 目的

承認待ちの AI の成果物を、**まとめて承認**できるようにする（束 E・D-153.11＝代表の答え 9：作る。「まとめて（全部）」と「選んだもの」の 2 つ・取り消せない物も対象・件数と取り消せない旨と件数とチェックの無い確認項目の件数を出してから承認・1 件ずつの承認と同じ守りを 1 件ずつ通し、通らなかった物は件数と行で返す）。今は札・ボタンが押せない形で、2 つの口は契約だけ（501）。

1. **確かめる** `previewBulkApproval`（POST /api/v1/approvals/bulk/preview・何も書かない）：体は任意の `approval_ids`（1〜50 個）。無ければ「自分が承認する承認待ちの成果物の全部」（古い順・50 件まで）。答えは **承認できる物 `eligible`（承認ごとの approval_id・ticket_id・number・title・irreversible・unchecked）・承認できない物 `excluded`（approval_id と理由）・件数 `count`・取り消せない件数 `irreversible_count`・チェックの無い確認項目の件数 `unchecked_count`**。画面の確かめの小窓の「AI の成果物 6 件をまとめて承認します」「取り消せない物が 3 件含まれます」「チェックの無い確認項目が 4 件あります」を作る元（下絵 `BulkConfirm`）。
2. **承認する** `bulkApprove`（POST /api/v1/approvals/bulk）：体は `approval_ids`（1〜50 個・必須）。**古い物から順に 1 件ずつ**、1 件承認する口と同じ DB の関数 `app.approval_decide(承認, 'approve', null)` を呼ぶ（承認する人だけ・今の状態・書けるか・任せた人の AI が使えるかの守りは**その関数のまま**）。1 件ごとが別の取引なので、**一部が決まっていても通った物は承認される**（下絵 `bulk-partial`：「1 件は承認できませんでした：EG-127 … は、先にほかの人が決めていました。EG-128 は承認しました」）。答えは `updated`（承認できた物：approval_id・ticket_id・number・run_id・pc）と `skipped`（承認しなかった物：approval_id・number・title・理由）。
3. **全部は「確かめで見た id」を渡して承認する**：画面は確かめの `eligible` の approval_id の並びをそのまま `bulkApprove` に渡す。**確かめの後に増えた承認待ちは、その回には入らない**（見ていない物を承認しない）。選んだものも同じ口（選んだ id を渡す）。
4. **「取り消せる物だけ」の縛りは外した**（D-128.86・D-128.177 の「骨格では承認は全部取り消せない扱い」を変える代表の決め）：取り消せない物（`irreversible`）も対象。確かめの小窓がその件数を見せてから承認する。
5. **チェックの無い確認項目が残っていても承認できる**（D-153.5）：件数を出すだけで止めない。確認項目のチェックには触らない。

分類: PERM, CRUD

代表の決め：聞くこと 9＝answer=f493bd620f24（作る・全部／選んだもの・取り消せない物も対象・件数を出してから承認・1 件ずつ守りを通す）。D-153.11・D-153.5（チェックの無い確認項目が残っていても承認できる）。

- **押せる人・対象**：承認する人（今の担当者）が、**自分が承認する**承認待ちの成果物（kind `artifact`・決まっていない・取り下げの印が無い・消していない・チケットが消えていない）だけ。「全部」はこの全部。別の人の承認・別の会社・成果物でない承認（上位の承認など）は入らない
- **1 件ずつの取引**：1 件の承認ごとに `withTenant`（1 接続・1 取引）で `select app.approval_decide($1, 'approve', null) as v` を呼ぶ。**承認の関数・その中の守り・承認の後の実行の仕事の積み方は 1 件承認する口と同じ**（K-162・0100・K-744 が作り直す版。K-744 の 4 つ目の引数は既定値があるので 3 つの引数の呼び方のまま通る）。この葉は `app.approval_decide` を**直さない**
- **承認の関数の答えの扱い**：成功（`error` が無い）＝updated（`run_id`・`pc` は関数の答えから）。`decided` ＝skipped（decided）・`not_approver` ＝skipped（not_approver）・`not_writable` ＝skipped（not_writable）・`not_found`・`not_member` ＝skipped（unavailable）。**`guard_failed`・知らない言葉・関数の例外は 503・E-PAGE-003**：その 1 件で止め、それまでに承認できた物は承認のまま（返さない）・落ちた物と後ろの物は決まっていない（ログに場所と例外の種類だけ・題名・番号・id を出さない）。画面は 503 のあと承認待ちを読み直す
- **任せた人の AI が使えない物**（外された・直せなくなった・PC が無い）は、1 件承認する口と同じく**承認は記録され、実行はその場で止まり**（updated に入る）、チケットは作業中に戻る。画面は読み直して分かる（実行の止まった理由は読む口が返す）
- **migration は 1 本**（番号−600＝168 分 → 02:48 → `packages/db/migrations/20261125024800_approval_bulk.sql`）。読むだけの関数 `app.approval_bulk_scan(p_ids uuid[], p_all boolean) returns jsonb`（`language plpgsql stable security definer set search_path = public, app, pg_temp`・`revoke all … from public`・`grant execute … to kaname_app`）：呼んだ人は `app.user_id()`・会社は `app.tenant_id()`。無ければ **null**。`app.approval_member_now()` でなければ `{"error":"not_member"}`。`p_all` が真なら自分が承認する物（`approver`＝`t.assignee_member_id = 自分`）の承認待ちの成果物を `created_at`・`id` の昇順に全部、**50 件を超えれば `{"error":"too_many","total":件数}`**。偽なら `p_ids`（重複を 1 つに・50 個を超えたら `too_many`）の 1 つずつを次の順で分ける：無い・別の会社・消えた・成果物でない・`app.ticket_visible` でない → `unavailable`／決まっている・取り下げた → `decided`／担当者が自分でない → `not_approver`／`app.ticket_writable` が偽 → `not_writable`／それ以外 → 承認できる。**`app.ticket_writable` が例外になったときは承認できる側に残す**（承認の関数が fail-closed で止める＝K768-API-016）。答えは `{ "items": [承認できる物…古い順], "excluded": [ {approval_id, reason, number, title} … ] }`。`items` の 1 件は `approval_id`・`ticket_id`・`number`・`title`・`irreversible`・`unchecked`（`app.approval_check_summary(チケット, false)` の `total − done`・K-739・無ければ 0）。`excluded` の `number`・`title` は `app.ticket_visible` のチケットだけ（unavailable は null）。**何も書かない**

**「まとめて承認（全部）」が 50 件を超えるとき**
- (a) ★ 50 件を超えたら「全部」は使えず、選んで承認してもらう（409・E-APR-030）。1 回で承認する件数に上限を置く（取引・待ち時間の見積もりのため）
- (b) 古い 50 件だけをまとめて承認し、残りは次の回にする
- 実例：承認待ちが 80 件たまった人が「まとめて承認（全部）」を押すと、(a) は「50 件を超えているので、選んでください」と出る。(b) は「古い 50 件を承認しました。まだ 30 件あります」と出て、もう 1 度押す
- 訳：(a) は「全部」の言葉と食い違わない（押したら全部が承認される）。(b) は 1 回で終わらず、見ていない残りを次の回に押す手間が増える

## リスクと懸念

- **K-744 が `app.approval_decide` を 4 つ目の引数つきで作り直す**：この葉は 3 つの引数で呼ぶ。K-744 が 4 つ目に既定値を置く決め（`p_next text default 'clone'`）が崩れたら、この葉の呼び出し（TS の 1 行）を直す
- **1 回の承認が最悪 50 取引**：待ちが長いと画面の確かめの小窓が長く busy になる。K-769 は `bulk-running`（busy）の間は押せなくし、答えが来たら読み直す。接続は 1 要求につき 1 本で順に使う（並列にしない）。目標を超えたら 50 を下げる（代表の決めが要る）
- **承認の後の実行は 1 件ずつ順に積まれる**：PC は古い物から順に取る（`bridge_take_job` は `created_at` の昇順）。下絵の「実行は 1 件ずつ順に始まります」と合う
- **確かめと承認の間に権限が変わる**：承認の関数が 1 件ずつ今の権限で決めるので、変わった分は skipped（not_writable・not_approver）になる。確かめの数は目安
- **途中の 503 のあと、画面はどこまで承認できたか分からない**：答えに `updated` を返せないため。画面は承認待ちを読み直して確かめる（K-769 の 503 の文は「一部は承認されているかもしれません。承認待ちを読み直してください」）
- **取り消せない物をまとめて承認できる**：代表の決め（D-153.11）。確かめの小窓が「取り消せない物が N 件含まれます」を必ず見せる（K-769）
