## 目的

migration には既にあるのに、repository の表の一覧に入っていないため契約の API から使えない表を使えるようにする。パスキーと登録の保留はログインの部品の側に置き、業務の表からは触らせない。

## 完了の条件

- [x] repository の表の一覧に `bridge_jobs` `bridge_job_events` `agent_usage_snapshots` `artifact_versions` を足した
- [x] パスキーの表の置き場所を決め（ログインの部品の側・kaname_auth・D-128.119）、ER 図に書いた。`pending_signup` も kaname_auth にあるので一覧に入れない
- [x] 足した表の RLS を見直した（PC の仕事と出来事は本人だけ）
- [ ] CI が緑のまま（起動時の存在確認：`apps/api/test/vercel_entry.test.ts`・`apps/api/test/server.test.ts`）

## 前提と制約

- 表の中身は変えない（一覧に足すだけ）。PC の印（device）の口は /bridge/ の下だけ（ZT10）で、表は直接読まず関門の関数（app.bridge_*）だけを通る

## 実施事項

- [x] `packages/db/src/repository.ts` の TABLES に足した
- [x] パスキーの置き場所を決めた（D-128.119）。仕様にあった passkeys の守りが「ログイン済みなら誰でも読める」になっていたので、業務の表からは誰も読めない守りにした（public に表は作らない）
- [x] ★PC の仕事（bridge_jobs）と出来事（bridge_job_events）は、同じグループの人に他人の PC の仕事が見えていた。本人だけにした。出来事は足すだけ（直せない）

## 決定ログ

- パスキーはログインの部品の側に置き、業務の表からは読めない。自分の設定の一覧はログインの部品の口から出す（D-128.119・2026-11-03 高本さん）
- 契約は第1フェーズの画面の API だけ（D-128.112）。PC の口は本人のセッションに結ぶ（D-128.93）

## リスクと懸念

- パスキーの表は、ログインの部品でパスキーを有効にするとき（K-18・KN-8）に kaname_auth に作る。それまで自分の設定のパスキーの口は 501
- パスキーの表を Better Auth と二重に持たない

## 申し送り

- K-18・KN-8：Better Auth の passkey を有効にし、パスキーの一覧・名前を変える・外すの口（renamePasskey・deletePasskey・getMySecurity）をログインの部品の口にする
