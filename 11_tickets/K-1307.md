## 目的

K-1304 で web の組を分けた後、段の全部の CI（流す置き場 engine-base-ci/wfe-2611・回 45816366366・2026-11-26）でいちばん長いのは spec の組で 約 25 分（12:07:49〜12:32:42）。
1 台で順に流れていて、中身は G65（CI の形の試験）840 秒・G57（チケットの CI の範囲の台本の試験）374 秒・ほかの段 約 3 分・準備（checkout・部品・Python・DB・分かれ目）約 80 秒。
G65 の中（75 本）の実測：k248 の試験 370 秒・k625 165 秒・k1121 44 秒・k622 33 秒・k172 20 秒・ほか 70 本で 約 190 秒。

代表の決め（2026-11-26・PM 経由）：**流す試験も照らしも 1 本も減らさず**、段の全部の CI を **10 分前後** にする。分ける数は置き場の変数で持ち、変数が無いときは今と全く同じ流れ（今だけの設定。K-1304 と同じ）。

PM の決め（作り方・K-1304 にそろえる）：
1. 分ける数は置き場の変数 `SPEC_SHARDS`（無ければ 1・1〜20 の整数。数でない・範囲の外は赤で黙って 1 にしない）。static の段 `id: spec_shards` が env で受け（命令の文字に入れない）、`spec_run.py shards` で `spec_shards`（数）と `spec_parts`（新しい組の matrix の一覧）を出す。1 なら `["off"]`（組は飛ぶ。空の matrix は GitHub が赤にするので印を置く）、2 以上なら `["g57", "g65-1"…"g65-N"]`
2. **1 か無い回は今と全く同じ**：spec の組が G57・G65 を今の名前・今の命令（G65 は今の && の並び）で流す。spec の組は static の出力を見ない決まり（static が赤でも spec の段は流す・K-143）なので、spec の組は自分の段 `id: spec_shards`（static と同じ命令と変数・if は `!cancelled()`・チケットの Python の試験の後）で数を出し、G57・G65 の段の条件に `fromJSON(steps.spec_shards.outputs.spec_shards || '1') < 2` を足すだけ（出力が空でも 1＝spec の組で流す。変数が読めない回は static と spec のこの段が赤で、G57・G65 は spec の組が流し、spec-parts は飛ぶ）
3. 2 以上の回は、spec の組は G57・G65 を流さず（ほかの段は今のまま）、新しい組 `spec-parts`（matrix part・fail-fast: false・needs: [static]・if は `> 1`）が流す。組ごとに spec と同じ準備（部品・Python・DB・本線との分かれ目 scope の段）を持つ
   - `g57`：段 `G57.p …` が spec の G57 と同じ命令・同じ範囲の条件（scope=full か gates に 57）
   - `g65-<i>`：段 `G65.p …` が `spec_run.py g65`（env SPEC_PART・SPEC_SHARDS）。並びは作り手と同じ部品（gate_cmds.commands・最後は G65_LAST）から作り、N 組に分けた i 番目を元の順に流す。流す前に junit/ を作る（spec の組では前の段「チケットの Python の試験」が作る置き場で、k216 の node の試験はそこに書く。無いと node は書けず赤）
   - G65.p の後に spec と同じ時間切れの見分けの段（K-193・hook_note）を置く（分けた回の k216 の JUnit は spec-parts にだけ在る）
   - static の spec_shards の段は if `!cancelled()`（static の前の段が赤でも流し、spec の組の自分の段と同じ数を出す。飛ぶと spec-parts は 1 と見て飛び、spec の組は 3 と見て G57・G65 を流さず、どこでも流れない）
   - 段の名前を `G57.p`・`G65.p` にするのは、spec の G57・G65 と同じ番号の段を 2 つ数えないため（単体の試験の `G3.<i>` と同じ印）
4. **G65 の止まり方は分けても同じにする（訳）**：1 組の G65 は命令を `&&` でつなぐので、1 つが赤ならその後ろは流れず段は赤。分けた組も、自分の組の命令を元の並びの順に流し、1 つが赤ならその組の残りは流さず、その番号で赤で終わる。G65 が緑になるのは、どちらの形でも「並びの命令が全部 0 で終わった」ときだけ（分けた組の和は並びとちょうど同じで、足し引きも重なりも無い）。分けた形が赤を緑にすることは無く、違うのは赤の回にほかの組の命令が流れて赤を多く見せることだけ（赤を全部いっぺんに見る決まりと同じ向き）
5. 分け方：実測の重さ（spec_run.py の SECONDS・上の回の実測。載っていない命令は 2 秒）で、重い順にいちばん軽い組へ入れる（同じ重さは前の組）。k248 の試験（G65_LAST・決まり K248-G57-016）は最後の組に置き、並びの最後なのでその組の最後になる。どの組も元の並びの順を保つ
6. JUnit：G65 で JUnit を書くのは k216 の node の試験 1 本（junit/spec-k216-mjs.xml・置き場の名前は今のまま）。spec-parts は JUnit を書いた組だけ（`hashFiles('junit/*.xml') != ''`）`junit-spec-parts-<組>` を上げ（空なら赤・赤の組でも always()）、junit の組は spec-parts も待つ。artifact「junit」にそろうファイルの名前と中身は今と同じなので、ticket-flow の照らしと ci_results の記録は今と同じ行を見る。チケットの Python の試験（junit/spec-py.xml）は spec の組のまま
7. 見込み（上の回の実測から）：SPEC_SHARDS=3 で G65 の組は 約 245 秒・244 秒・370 秒（k248 が 1 つで 1 組）、G57 の組は 374 秒。組の準備 約 80 秒を足して spec の家族でいちばん長い組は 約 7.6 分（今 25 分）、spec の組は 約 4.7 分。段の全部の CI は static 2.5 分＋7.6 分＝**約 10 分**（web の組は K-1304 で 約 10 分）。2 だと G65 の組が 約 430 秒で 約 8.5 分、4 以上は k248（370 秒）と G57（374 秒）が床で縮まらない。**すすめる数は 3**（組は 4 つ増える）
