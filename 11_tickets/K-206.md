## 目的

2026-11-14 に PM が確かめた事実：GitHub の main に入るたびに、Vercel の 2 つのプロジェクト（kaname-api・kaname-web）が commit status「Deployment was blocked」（failure）を返していた（`gh api repos/engine-base/Kaname/commits/<sha>/status`）。2 日分・約 30 本のチケットが 1 つも staging に配られていなかった。

訳：コミットの名義（author）が、Vercel のチームに入っていない利用者（個人の GitHub の利用者）だった。チームに入っているのは組織の利用者だけ。11/2 頃までのコミットは組織の名義（メールの @ の後ろが engine-base.com）で、その後、作業フォルダの git の名義が個人の物に変わっていた。配りが止まっても CI は緑なので、だれも気づかなかった。

PM は 2026-11-14 に、このリポジトリの git の名義（local の user.name・user.email）を組織の物に替えた（作業場所は設定を共有する）。このチケットは、名義がまた変わったときに、GitHub に出す前に機械で止める：本線との差分のコミットの author のメールが、決めたドメインで終わらなければ赤にする検査を、CI の static の組に足す。

## リスクと懸念

- **`Co-Authored-By:` の行（AI の名義）が配りに効くかは未確認**。この検査は author だけを見る。このチケットの取り込みが、組織の名義で main に入る最初のコミットになるので、取り込みの後に PM が Vercel の commit status を見て確かめ、結果をこのチケットに書く（完了の条件）。blocked が続くなら、別のチケットで切り分ける
- Vercel が見ているのが「先頭のコミットの author」だけか、入った全部のコミットかは未確認。この検査は全部を見る（厳しい側）
- AI の名義が author のコミット（本線に 267 本・11/1〜11/9）は、この検査で赤になる。その作り方をまた使うなら、名義を組織の物にしてからコミットする
- 台本は、メールのドメインが合うことだけを見る。そのメールの利用者が Vercel のチームに入っているかは見られない（組織のドメインの、チームに入っていない人の名義は緑になる）
- 取り込みの台本が作る取り込みのコミットの名義は、取り込む人の git の設定で決まる。本線の上で作られるコミットは、次のチケットの回では比べる元より前になるので、この検査では見ない。取り込む人の名義が個人の物に戻ると、配りがまた止まる：全部の回は 0 本で緑のまま。見つけるのは、取り込みの後の commit status（今回は PM が手で見る。毎回見る形にするかは PM が決める）
- 走っている枝に、名義を替える前のコミットが残っていると、この検査が入った後の回で赤になる。今は 0 本（「確かめたこと」の 3）
