## 目的

運営が受信箱の 1 件から顧客に返事を書き、運営の中だけの社内メモを残せるようにする（行為 A70）。返事は問い合わせた本人の 困ったとき・お知らせ と鈴に届き（D-156.28）、社内メモは顧客に出ない（D-156.25）。

- **replyOpsInquiry**（ops:inquiry）：入力 `body`（1〜4000・空白だけは pattern `\S` で 422）だけ（運営が添付を上げる口が無いので `attachment_ids` を持たない・D-156.40）・答え OpsInquiryMessage の 6 欄（K-948）
- **addOpsInquiryNote**（ops:inquiry）：入力 `body`（1〜4000）・答えは同じ 6 欄（kind note）
- **お知らせの種類の表**（段 8 の K-461 の `kinds.ts`）に `inquiry.replied` を 1 行足す（この葉が持つ・切り方 3 章）
- **鈴の文はこの葉で足さない**（D-156.73・D-156.41 を改めた・PM 2026-11-23）：文の表 `notice-text.ts`（段 8 の K-467）は画面のコードなので、inquiry.replied の文 「運営から問い合わせに返事がありました」 の行と試験は押した先の画面の葉 K-1007 が持つ。この葉は種類の表 `kinds.ts` の 1 行だけ

## 前提と制約

分類: MAIL, PERM

- **代表の答え 2026-11-23（D-156.28）**：問い合わせの返事は鈴に出す。運営のお知らせ（notices）は鈴に出さない
- **代表の答え 2026-11-23（D-156.25）**：見えるのは書いた本人だけ・社内メモは顧客に出ない
- **生成の試験は作る段の最初に作る**：契約の断片（`05_flow/screen_api.d/K-975.py`・`scripts/ci/contract_shape.d/K-975.py`）を足して作り手で生成の試験を作り、**実装より先に 1 つのコミットにする**。先の葉の契約を前提にした前からの試験は carry に入れない
- **返す**：書き込み `messages`（その問い合わせの会話・`sender_member_id null`・`kind 'inquiry_reply'`・`visibility 'all'`・`author_name`＝返した運営の人の display_name（K-949 の写しの列）・`attachments '[]'`）。問い合わせは `state 'waiting'`（顧客には 返事あり）・`later_until null`・`last_message_at now()`。済みに返しても waiting に戻す
- **担当**：担当が自分 → そのまま。担当なし → 自分を担当にして返す（返した人が持つ）。ほかの人 → **409 E-OPS-005**（K-974 の番号・欄なし・何も書かない）
- **鈴（関門 C6）**：送るのは `@kaname/notify` の NotifyGateway の中だけ（K-967 の形）。受け手は問い合わせた本人（opened_by）・channel は `inapp` だけ（`channelsOf` で inapp に絞る・メールは送らない＝D-125.130）・event kind `inquiry.replied`・payload `{ inquiry_id }`（本文の字を入れない）・dedupe の鍵は返事の書き込みの id。inapp の送り口は同じ取引の接続で `notifications` に 1 行書く（落ちたら取引ごと戻る）。「送れた」は deliveries に sent があるときだけ（G-15）
- **お知らせの種類の表**：`apps/api/src/features/F7/notifications/kinds.ts` の KINDS に `"inquiry.replied": { tag: "setting", ticket: false, href: "/notices" }`（困ったとき・お知らせ の画面。1 件の道 `/inquiry/<id>` は表の行き先が固定なので組めない＝申し送り）。足さないと K461-API-016 が赤・鈴に出ない
- **社内メモ**：書き込み（`kind 'inquiry_note'`・`visibility 'ops_only'`・`sender_member_id null`・`author_name`）。担当・状態・`last_message_at` は変えない（顧客の側の並びが動かない）。ほかの人が担当でも書ける（運営の中の申し送り）。鈴・お知らせは出さない
- **添付**：運営が添付を上げる口は契約に無い（uploadInquiryAttachment は顧客の口）ので、K-948 が replyOpsInquiry の入力から `attachment_ids` を外した（D-156.40）。送ってきたら知らない欄として契約の形で 422（additionalProperties false）。書き込みの `attachments` はいつも `'[]'`
- **本文の形**：空白だけは契約の INPUT_RULES（K-948 の body の決まり・K-385 と同じ形）で 422・NUL は入口で 422（控え帳）
- 記録（運営の関数は書くなら必ず記録）：返す `inquiry.reply`・メモ `inquiry.note`。どちらも `app.record_ops_audit(<会社>, <操作>, 'inquiries', <問い合わせの id>::text, null, {target_label: <題>})`（本文の字を入れない）
- 断る番号（控え帳）：ログインなし 401・運営でない・inquiry を持たない 403（入口）・形 422（入口・契約）・無い・消した問い合わせ・添付 404（欄なし）・ほかの人の担当 409 E-OPS-005・鈴が書けない・DB の失敗 503 E-PAGE-003（何も残さない）・上限 429。ログは `[ops] inbox-reply の DB が失敗した（<SQLSTATE>）` だけ

### 関数（migration `20261128011500_ops_inbox_reply.sql`・K-975 → 75 分）

- `app.ops_inquiry_reply(p_id uuid, p_body text) returns jsonb`（security definer・volatile）：ⓐ `app.ops_require('inquiry')` ⓑ 問い合わせ（K-973 の条件）を `for update`・無ければ `no_data_found` ⓒ（添付は受けない）ⓓ ほかの人の担当なら `{"error":"taken"}` ⓔ 書き込み・状態・担当 ⓕ `app.record_ops_audit('inquiry.reply' …)` ⓖ `{"data": <OpsInquiryMessage>, "asker": <問い合わせた本人の members.id>, "tenant": <会社>}`（口が鈴を送るのに使う・答えには出さない）
