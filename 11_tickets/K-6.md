## 目的

取引先の表（取引先・担当グループ・先方の人・届いた依頼・検収）を作り、社内の人と取引先の人（クライアントの場所）の見え方を行の守りで分ける。

## 完了の条件

- [x] migration（`packages/db/migrations/0074_clients.sql`）と RLS（`packages/db/policies/0074_clients.sql`）
- [x] repository の TABLES に入っている・場合表が全部通る
- [x] `tickets.client_id` に外部キーを付けた（K-3 の申し送り）
- [x] 取引先の人は、自分の取引先の中だけ・会社が見せると決めたチケットだけ読める（D-125.122）
- [x] ★柵の穴を塞いだ：取引先の人・PC の文脈で会社の人の守りを通れない
- [ ] CI が緑のまま

## 前提と制約

- 表は ER 図 §16 と「足す列」が正。足すだけで、消す・名前を変える migration は作らない
- 全部の表に `tenant_id` と RLS。RLS を飛ばす鍵はサーバーで使わない（ZT3）
- 自分の表の読む守りに「その表を id で引く関数」を使わない（作った行がその場で見えず INSERT … RETURNING が弾かれる）

## 実施事項

- [x] 表：`clients` `client_groups` `client_contacts` `client_requests` `acceptances`
- [x] 列：`clients.email_domain`・`client_requests.questions`・`acceptances.reminded_at`
- [x] RLS の範囲（社内）：全員に見える取引先か、取引先の担当か、担当グループが見える人。取引先を直せる人（既定は管理者）は全部
- [x] RLS の範囲（取引先の人）：自分の取引先・同じ取引先の人と依頼。依頼は依頼できる人が自分として出し、受けてもらう前は直せる。検収は頼まれた本人が返す（直してほしいなら何をかが要る）
- [x] ★`app.member_ok()` は「運営でなければ通す」だったので、取引先の人・PC の文脈でも会社の人の守りを通れた。app.role='member' で取引先の人でない人だけにし、取引先の人は `app.client_ok()` で別に守る（gen_rls に client の役を足した）
- [x] 場合表に取引先の人の場合（登録の無い人・他の会社・文脈なし）を足した

## リスクと懸念

- 取引先の人がチケットのどの項目を見られるか（client_share）は、行の守りでは絞れない。API が client_share で項目を絞る（KN-27）
- 取引先の人のメンバーの行は会社のメンバーの表にある。ほかの守り（visible_scopes など）は柵（member_ok）で弾いている
