## 目的

K-62 で契約の fuzz（G36・Schemathesis）の的を K-57・K-60 の口まで広げたら、前から食い違っていた所が 4 件見つかった（K-62 の 8 本の口はどれも緑）。どれも「契約の書き方」と「口の実際の振る舞い」がずれていて、fuzz が赤になる。K-62 の完了の条件は「広げた範囲で fuzz が緑」なので、これを先に直す（決める人の決定：起票して K-62 の前に入れる・2026-11-08 answer=c8bb89cac057）。

1. `GET /bridge/releases/{name}/file`（K-57）：配布物が無いとき 404 を返すが、契約に 404 が無い
2. `GET /ticket_kinds`（K-60）：`color` が null を返す（DB の列は null を許す）が、契約は文字（string）
3. `POST /bridge/pairing-codes`（K-57）：知らない項目を 422 で断るが、契約に `additionalProperties: false` が無い
4. `POST /me/ticket-drafts`（K-60）：`draft_id` が uuid でないと 422 で断るが、契約に `format: uuid` が無い

**4 件はどれも「類」の 1 件**（精査 R1 回 1・L-008）。fuzz が 1 本ずつしか赤にしなかったのは例の数（-n 30・seed 固定）のたまたまで、同じ形のずれが入力の形全部・ほかの uuid の欄・同じ口のほかの応答・ほかの答えの null にある。決める人の決定 D-129.42（ゼロトラスト：uuid の欄は契約に format: uuid を書いて入口で厳しく確かめる・入力の形は知らない項目を許さない・同じ形のずれは K-144 で全部そろえる）に従い、**類ごとに全部**このチケットでそろえる。

## 前提と制約

分類: CRUD, EXT, PERM

- 直す向き：**契約を実装に合わせる**。ただし uuid の欄だけは D-129.42 で**入口を厳しくする**（契約に format: uuid を書き、作り手の入口の形 z.uuid() が版と variant の桁まで確かめる）。前の口の正規表現（`/^[0-9a-f-]{36}$/i`）が通していた「36 個のハイフン」「版の桁が 0 の 36 字」は 422 になる（中の `$1::uuid` で 500 になる道を残さない）。PM の 08:50 の決め（口の振る舞いは変えない）は、08:57 にこの決定に合わせて直した（.ai-team/pm-decisions-2026-11-08.md）
- 入力の知らない項目：入口は前から z.strictObject で断っている。契約に `additionalProperties: false` を書くだけで、振る舞いは変わらない。**例外は同意の口（consentToTerms）だけ**：前処理（apps/api/src/features/F1/consent-terms/index.ts の parseConsent）が知らない項目を落としてから確かめていたので、他の会社・他の人の id を体に入れても 201 で無視していた（K53-API-021）。D-129.42 に合わせて、前処理は知らない項目を落とさず、入口の strict な形で 422 にする（K53-API-021 の期待を 422 に改めた・K-53.md の行も直した）
- ②の色の null は、DB が null を許していて、画面は null のとき決まった色で出す前提。契約を nullable にする（DB の列を not null にするのはこのチケットではしない）
- 入口の uuid の理由：入口が uuid の形で断るときの details の message は、道の id と同じ `"uuid"` にそろえる（zod の英語の文を出さない。画面が出すのは欄の名前ごとの文で、改ざんした体のときだけ出る）
- 契約の元は 05_flow（screen_api.py → build_api.py）と 08_api。生成物は手で直さない
- E 必須の欄（回 9・Q5 回 8 追加-1）：口が「無い」ことで 422 にする欄は、契約の入力の形に `required` を書く。**入口の zod は前から全部 `.optional()`**（契約に required が 1 つも無かったので、作り手が全部 optional にしていた）で、必須の確かめと文言は口の振る舞い（hooks・前処理）が持っている。PM の指示の「入口の確かめ（zod の optional でない欄）と突き合わせ」は、zod に必須の欄が無いので、**口の振る舞いと突き合わせる**（下の「E の機械の洗い出し」・本物の DB で {} と 1 欄ずつ抜いた体を送る K144-API-033・034）。**振る舞いは変えない**：required を書いた入力の形には `x-required-by: hooks` を付け、作り手（contract.mjs）はその欄の zod を `.optional()` のままにする（入口が先に VALIDATION_ERROR にすると、K-52 の確認の {} が 422・E-PAGE-006 でなくなり K52-API-015 と画面 verify-link.tsx の案内が変わる。登録の E-VAL-004・010・005、同意の E-VAL-019 も同じ）。型（08_api/types.ts・packages/contracts の types）は必須の欄に `?` が付かなくなる（作る役が写しで画面と口の型の検査を流して緑）
- E の分け合う形：updateMemory と createMemory は同じ入力の形 MemoriesInput を使うが、必須が違う（updateMemory は body が無いと 422「覚えることが空です」、createMemory は {} で 201）。作り手は、必須の違う口に自分の形（`UpdateMemoryInput`・欄は MemoriesInput と同じ・知らない項目は許さない）を作って持たせる。受ける欄は変えない
- E で required にしない欄：条件つきで要る欄（stepUp の code は 2 段階を使う人だけ・createTicket の区画は種別ごとの必須を DB が見る・優先度「高」の理由）。値があっても断る欄（空の題名・形の違う接続コード など）は値域の話で、類 G で扱う
- G 体の値の値域（回 9 の続き・PM の判断 2026-11-09）：契約の形に合う値を口が 422 で断る欄は、書ける値域（pattern・minLength・maxLength・enum・minimum・maximum・maxItems・propertyNames・anyOf）を契約の欄に足す。**足すのは値域の言葉だけで、type・format・nullable は変えない**（入口の zod は値域の言葉を読まないので変わらない＝今のエラー ID と文言のまま。E と同じ）。値域は**口が受ける値の集合より狭く書かない**（狭いと契約の外の値を口が受けて fuzz の ST201）。書けない分だけ広くし、その分（今日より前の期限・暦に無い日・外部キーの在りか・条件つき・NFKC で長さが変わる字 など）は口の振る舞いのまま 422 とし、その口の 422 の説明と `x-unexpressible-422` に理由を書く。fuzz でそれをどう扱うか（その検査の外し方）は K-62 の fuzz の引数の受け持ち（K-62 の次の作るの段で足す）
- G の続き（回 10・精査 R1 回 10 追加-1・追加-2・PM の判断 2026-11-09）：**入口の文字の上限も値域**。作り手の zod は文字の欄（format の無い type: string）を全部 10000 字で断るので、契約の入力の形（体を受ける口の全部・まだ作っていない口も）の文字の欄に maxLength を書く（入口の 10000 と口の値域の maxLength の小さい方）。答えの形には書かない。**長さの数え方はコードポイント**（JSON Schema の maxLength・Postgres の文字数と同じ）にそろえる：入口の zod の `.max(10000)`（UTF-16 の単位）・区画の 20000（create-ticket/input.ts:71）・接続コードの 32（connect-pc/code.ts:29）。上限の数は変えない。変わるのは 4 バイトの字（絵文字など）を含む値だけ。画面の字数の数え（作る面の題名・登録の名前と会社名）はもうコードポイントなので変えない（apps/web/features/F4/create-ticket/create-ticket.tsx:37・apps/web/features/F1/sign-up/signup-form.tsx:38〜40）。作る面に区画の字数の数えは無い
- 表の素の書き込みの 422（op.ts）が DB の例外の文をそのまま答えに出している（details の message に DB の文の頭 200 字）。㉓ で同じ形（22003・23514）が増えるので、答えには決まった文だけを出し（4 つの DB の答えで同じ文）、DB の文は console.error のログにだけ残す（PM の判断 2026-11-09）
- C の続き（回 9 の続き・PM の判断 2026-11-09）：会話と記憶の口（apps/api/src/hooks/agent.ts）の成功の答えは表の行でなく、口が返すとおりの形（会話を作る `{id, conversation_id}`・名前を変える／記憶を直す `{id, ok}`）。契約をこの形に合わせる（口の振る舞いは変えない）。あわせて、接続コードを出す口がセッションの人がその会社のメンバーでないときに 500 を返す件と、表の素の書き込みで記憶の確かさが DB の桁を超えると 500 を返す件は、契約に無い 500 なので直す（下の「接続コードの口の 500 の原因」「直すもの ⑳〜㉕」）
