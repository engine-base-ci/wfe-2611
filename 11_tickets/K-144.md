## 目的

K-62 で契約の fuzz（G36・Schemathesis）の的を K-57・K-60 の口まで広げたら、前から食い違っていた所が 4 件見つかった（K-62 の 8 本の口はどれも緑）。どれも「契約の書き方」と「口の実際の振る舞い」がずれていて、fuzz が赤になる。K-62 の完了の条件は「広げた範囲で fuzz が緑」なので、これを先に直す（決める人の決定：起票して K-62 の前に入れる・2026-11-08 answer=c8bb89cac057）。

1. `GET /bridge/releases/{name}/file`（K-57）：配布物が無いとき 404 を返すが、契約に 404 が無い
2. `GET /ticket_kinds`（K-60）：`color` が null を返す（DB の列は null を許す）が、契約は文字（string）
3. `POST /bridge/pairing-codes`（K-57）：知らない項目を 422 で断るが、契約に `additionalProperties: false` が無い
4. `POST /me/ticket-drafts`（K-60）：`draft_id` が uuid でないと 422 で断るが、契約に `format: uuid` が無い

## 完了の条件

- [ ] 4 件とも、契約が口の実際の振る舞いを書いている（直す向きは下の「実施事項」）。生成物（openapi・registry・types・test-plan）を作り手で作り直してある
- [ ] 4 件それぞれに、契約の形を確かめる試験の行がある（下の表）
- [ ] K-62 の fuzz の的（K-62 の枝の apps/api/test/fuzz/server.ts）を当てたときに、この 4 件で赤にならない（K-62 の取り込みの前に K-62 の作業場所で確かめる）
- [ ] チケットの CI（act・このチケットの範囲）が緑

## 前提と制約

分類: CRUD, EXT

- 直す向き：**契約を実装に合わせる**。4 件とも、実装の振る舞いの方が決まり（入力は契約の strict な形で確かめる・無いものは 404）に合っている。口の振る舞いは変えない
- ②の色の null は、DB が null を許していて、画面は null のとき決まった色で出す前提。契約を nullable にする（DB の列を not null にするのはこのチケットではしない）
- 契約の元は 05_flow（screen_api.py → build_api.py）と 08_api。生成物は手で直さない
