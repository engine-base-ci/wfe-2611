## 目的

2026-11-15、決める人が staging の画面を自分で触り、「読み込みが遅すぎるレベル」と指摘した。PM が測った事実：

- 口（kaname-api）の `/health` と画面（kaname-web）の `/login` の答えの頭が `x-vercel-id: hnd1::iad1::…`。入口は東京（hnd1）だが、処理（Function）は iad1（米国東部・Washington, D.C.）で動いている
- DB（Supabase）は東京（ap-northeast-1）。だから口の処理は、DB への問い合わせ 1 回ごとに太平洋を往復する
- `apps/api/vercel.json` に `regions` が無い（Vercel の既定は iad1）。`apps/web` に vercel.json は無い

このチケットは、口と画面の処理の場所を DB と同じ東京（hnd1）にする設定をリポジトリに置き、健康診断（`scripts/ci/staging_health.py`）が、答えの頭の処理の場所が決まりと違えば赤にする。

ログイン後の画面の速さ（画面が口を何回・直列に呼ぶか）は別の調べもの（PM が別に進めている）。このチケットでは扱わない。

## 前提と制約

分類: TOOL, EXT

- 公開の資料で確かめたこと（2026-11-15）：
  - 処理の場所の決め方：`vercel.json` の `regions`（例 `["sfo1"]`）か、プロジェクトの画面の Settings → Functions → Function Regions。新しいプロジェクトの既定は iad1。関数ごとの上書きは `functions` の `regions`（https://vercel.com/docs/functions/configuring-functions/region ）
  - Hobby の制約：「Hobby plans can select any single region」（https://vercel.com/docs/project-configuration/vercel-json の `regions`）。1 か所だけなら Hobby でも vercel.json で決められる。2 か所以上は Pro から。予備の場所（`functionFailoverRegions`）は Enterprise だけ。上限を超える指定は組み立ての前に配りが落ちる（region の頁の Limits）
  - 東京の符号：`hnd1`（ap-northeast-1・Tokyo, Japan）。大阪は kix1（https://vercel.com/docs/regions の Region list）
  - 画面側の扱い：Routing Middleware（`apps/web/middleware.ts`）は地域の指定にかかわらず全部の地域に配られる（Hobby では少なめ）。画面の各道（`/login` など）は middleware が nonce を付けるため動的に組み立てられ、Function で動く（今 `/login` の頭が `hnd1::iad1::…`）。だから画面のプロジェクトにも `regions` を置く。middleware は DB を読まない（守りの頭を付けるだけ）
- **設定はコードに残す**（vercel.json）。Vercel の画面の Function Regions は触らない。プロジェクトの Root Directory（`apps/api`・`apps/web`）の vercel.json を Vercel が読むことは、今の `apps/api/vercel.json` の Build Command が効いていることで分かる
- 処理の場所の決まりは 1 か所（`scripts/ci/staging_region.json` の `function_region`）。vercel.json 2 つ・STAGING.md・環境の正本は、試験がこれと同じかを見る
- DB の場所（Supabase の東京）は変えない。健康診断から DB の場所は見られない（鍵を使わないので）。STAGING.md の 1 行で「変えるときは両方」とする
- 健康診断は道を増やさない：口の場所は `/health` の答えの頭、画面の場所は `/login` の答えの頭から読む（K-200 の「当てる道は 3 つだけ」を変えない・K212-FR-007）
- 本番（顧客に触らせる前に作るもう 1 組）も同じ vercel.json で配られる。本番の DB も東京に作る（STAGING.md の S1 の Region のまま）

## 確かめたこと（切る段・2026-11-15）

1. 頭の形：`curl -s -o /dev/null -D - <口>/health` を 2 回 → `x-vercel-id: hnd1::iad1::<番号>`・`x-vercel-cache: MISS`。画面の `/login` も `hnd1::iad1::<番号>`。3 つに分けた最後が要求の番号、その 1 つ前が処理の場所（今の形では 2 つ目）
2. 認証の要らない口で DB を読む物：`GET /api/v1/auth/terms/current`（今の規約の版。`apps/api/src/features/F1/consent-terms/index.ts` の getCurrentTerms が DB の `app.current_terms()` を読む・誰でも読める）。`/health` は DB を読まない（`apps/api/src/app.ts` の health）
3. 環境の正本（`02_tech_stack/selected-stack.json`）の `stack.hosting.stages` の段階 1（id stage1）に `database: Supabase（東京・…）` はあるが、処理の場所の欄は無い。足す
4. 今の健康診断の答えの頭は読んでいない（`check_health`・`check_login` が頭を捨てている）

## リスクと懸念

- **場所を変えると外のサービスへの距離が変わる**：Resend（メールの送り）と Infisical（顧客の資格情報の預かり・地域は US か EU）は、東京から遠くなる。起動時の Infisical の往復（入れるかの確かめ・D-101.4）と Resend の送りは、その分遅くなる。どちらも 1 回の要求あたりで DB ほど回数が多くないので、全体では速くなる側と見る。Infisical の地域は STAGING.md の S1b のまま（変えない）
- 初回の起動（コールドスタート）の時間は場所では大きく変わらない見込み。直す前の 1 回目（1.4 秒）は起動の待ちを含む
- Hobby は 1 か所だけ。2 か所以上・予備の場所を書くと配りが落ちる（K212-FR-001 で形を止める）
- 取り込んでから配られるまでの間に staging の回（K-204）を流すと、健康診断の処理の場所の項目は赤になる（配った版がまだ iad1）。配られた後に流し直す
- Vercel の画面で Function Regions を手で替えてあっても vercel.json の `regions` が上書きする（資料・上の「PM に見てほしいこと」）。それでも配られた後の頭で確かめる（完了の条件）
- 健康診断の画面の場所は、`/login` が動的（`apps/web/app/layout.tsx` が `cookies()` を読む・今の答えは `cache-control: private, no-cache` で `x-vercel-cache: MISS`）で Function を通ることが前提。静的になると「読めない」の赤になる（K212-FR-012・黙って緑にしない）
- 頭 `x-vercel-id` の形は資料に書いていない（実測で `入口::処理の場所::番号`）。形が変わると健康診断は「読めない」の赤になる（黙って緑にはならない）
- 画面の vercel.json を足すと、チケットの CI で画面の組が動く（時間がかかる）
