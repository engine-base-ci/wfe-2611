## 目的

2026-11-15、CI（自分の Mac の Linux の VM）で、承認の帯の画面の試験が 1 日に 4 回、60 秒の時間切れで赤になった。どの回もその回のチケットの変更とは関係が無く（配りの設定・道具だけ）、関係のないチケットの取り込みが止まった。

| 回 | 落ちた行 | 記録（Call log） |
|---|---|---|
| 43679342176 | K-63 の UI-022（approve-complete-approve.spec.ts:81「承認して送る」） | locator resolved to `<button …>承認して送る</button>` → element is not stable → **element was detached from the DOM, retrying** → 60 秒 |
| 43681091878 | K-63 の UI-043（approve-complete-return.spec.ts:181） | locator resolved → **element was detached from the DOM, retrying** → 60 秒 |
| 43693781963 | K-63 の UI-043（同じ） | 同じ（ほかの 337 行は通った） |

揺れを止め、同じ形（試験が画面を開いた直後に口の答えを替える）を全部同じ道具で直す。

## 原因（調べた事実と見立て）

### 事実（記録・コード・手元で再現）

1. **仕組み**：チケットの詳細（`ticket-detail.tsx`）は、チケット（getTicket）と実行の一覧（listTicketRuns・`use-run.ts` の useRuns）を別々に読む。試験の土台（`approve-complete.harness.ts` の mockApi）は、**一覧の答えをその時点の `m.on.ticket` から作る**（bandNow）。試験の開く道具 `openTicket` は**見出しが出たら返る**（＝チケットが届いた時点）。一覧の最初の答えが届いたかは見ていない
2. 落ちた 2 行（K-63 の UI-022・K-63 の UI-043 の前半）は、`openTicket` の直後に `m.on.ticket` を「承認の後の実行が走っている」に替え、そのあと帯の「承認して送る」を押す。**一覧の最初の問い合わせが替えた後に届くと**、一覧は「実行中の実行」を返す → 帯（`band.tsx` の usePolledTicket）が走っている実行を見てチケットを読み直す → 承認待ちが無いチケットが帰り、帯は「実行中」に替わり、ボタンの節が消える。押す操作は消えたボタンを待って 60 秒で落ちる（記録の「detached」と同じ）。押した後の確かめ（「実行中」）は満たされるが、押す前に消えるので口は 0 回
3. **手元の再現**（本番の形で組み立てた画面・使い捨ての番号・口は網の手前で差し替え）：
   - そのままで 2 行を 20 回ずつ（並べて 4）：**0 / 40 回落ちた**（速い台では一覧が先に届く）
   - 一覧の答えを網の手前で止め、答えを替えた後に離す（遅い台で起きる順を作る）：**2 / 2 回落ちた**。記録は CI と同じ（locator resolved → element was detached from the DOM, retrying）。替えた後に `/runs`・`/action_runs`・`/tickets/:id` が続けて読まれ、ボタンの節が消える
   - CPU を 20 倍遅くする（CDP の Emulation.setCPUThrottlingRate・並べて 6〜8）：**3 / 120 回、同じ記録で落ちた**（ほかに 1 回は調べの道具の 20 秒の時間切れ）。落ちた 3 回とも、一覧の問い合わせが答えを替えた後に出ていた（替える前に出ていた回は 1 回も落ちていない）
   - 一覧の最初の答えを待ってから答えを替える形（直した後の形の試し）・CPU 20 倍：**0 / 200 回**（後の 5 回）。最初の 1 回の 40 回のうち 5 回は落ちたが、その回の記録を残しておらず、落ち方は確かめられていない（下の見立て）
4. **製品は節を作り直していない**：読み直しが続く承認待ち（24 時間の聞き直し・実行待ちで PC が閉じている）で 3 秒ずつ 10 回読み直させても、「承認して送る」は同じ節のまま（isConnected・取り除かれた数 0・チケットの読み直し 8 回）。差し戻しの小窓を開いて書いている間に 5 回読み直しても、小窓は開いたまま・書いた文も残る。帯のボタンが消えるのは、口が「もう承認の後の実行が走っている」と答えたときだけで、それは正しい振る舞い（もう決まった承認のボタンは出さない）
5. 同じ揺れは、同じ試験のファイルの後半（K-63 の UI-043 の差し戻しの所）で前に一度見つかって直されていた（K-181 のコミット 5fadd1d6「実行の一覧の読み込みを待ってから答えを替える」）。前半と、ほかの行には広がっていなかった

### 見立て（確かめていない）

- CI の 1 回目の「element is not stable」は、承認の中身（getApproval）が届いてボタンの上に成果物の文が出て、ボタンの位置が動いた瞬間（揺れの原因ではない。押す前の待ちが少し延びるだけ）
- 3 の最初の 5 回の落ち方は、CPU 20 倍・並べて 8 で調べの道具の 20 秒の時間切れに当たったと見ている（記録が無い）。直した後の形の 200 回では 0。**原因がもう 1 つ残っている疑いは消せていない**（001〜006 は一覧の最初の答えと時計 1 回分の答えしか見ない）。精査が読んで潰した候補：窓に戻ったときの読み直しは切ってある（`lib/api/query.tsx` の refetchOnWindowFocus: false）／帯がチケットを読み直すのは走っている実行がある間だけで、落ちた 2 行は開いた時点で実行が無い。残りは下の完了の条件の「記録つき 200 回」と「取り込み後の CI 5 回」で捕まえる
