## 目的

メンバーの 1 人の画面（`/members/:id`・下絵 md-view・md-self・md-suspended・md-failed）が開くときに読む口 `getMember`（GET /api/v1/members/:id）を作る。管理者が、人を選んで「どのグループにどの役割で居るか・担当しているもの・PC のつながり・ログインの仕方・最近の記録」を見る。

**人ごとの「できること」は返さない**（D-154.10）：契約の今の答えにある role_bundle・granted・revoked は外す（K-800 が契約を作り直す）。権限は役割と所属で決まるので、どのグループに入っているか（groups）が答え。

口の登録・断る番号（errors）は K-800 が持つ。入力と答えの形は K-800 の「契約」の節で決めた形で、この葉の口の分をこの葉が契約（.d）に書く。この葉は `members/get.ts` の空の形を本物にして `ready = true` にする。

**画面が使う答えの形**（K-819 が使う）：200 `{ data: MemberDetail }`・`Cache-Control: private, no-store`。鍵はちょうど 6：

```text
member: { id, name, email, role, suspended, suspended_at, since, self, is_owner, role_changed }
  role            会社の役割（admin・manager・member・viewer・requester）
  suspended       止めているか（members.suspended_at か所属の status suspended）・suspended_at は ISO 8601 か null
  since           入った日（所属の joined_at・無ければ members.created_at）の ISO 8601
  self            呼んだ人本人か（画面が「止める」「外す」を押せない形にする印）
  is_owner        会社を作った人か（members.role_id が owner・真偽。画面の「会社を作った人」の印・外せない扱いの字に使う）
  role_changed    { at, by（変えた人の名前）, from（前の役割） } か null（audit_events の member.role_change の新しい物）
groups: [{ id, name, code, primary, role }]        主の所属が先・兼ねるグループは作った順。role はそのグループでの役割（manager・member・viewer）で、所属の行が無ければ null（管理者の主の所属など）
assigned: { tickets, overdue, stuck, handing }      担当で完了前の数・期限が日本時間の今日より前・7 日触っていない・渡し中（待っている渡しの渡す側）
clone: { pc, pc_days_away, device }                 pc は K-419 と同じ（ok・away・never・none）・device は最後の bridge の行の端末の名前か null
login: { passkeys, has_password, two_factor, last_login_at }
recent_events: [{ id, action, at, by }]            その人が起こした・その人に起きた記録を新しい順に 5 件まで（payload は返さない）
```

画面の「承認する人 N 件」は、承認は担当者が受け持つ（D-150.21）ので担当の数と同じになる。別に数えないので、K-819 は下絵の字を「担当 N 件・期限切れ N・渡し中 N」に直すか、承認の件数を担当の数から出す（申し送り）。「今月の実行・人ごとの枠」は後のフェーズ（押せない形）なので口に鍵を持たない。

## 前提と制約

分類: PERM

- **だれが読めるか**：契約の PERMS のまま（members の view・会社全体＝管理者と、個別に付けた人）。入口が先に 403。DB の関数も頭で `app.admin_can('members', 'view')`（守りは入口と関数の 2 層）。**マネージャー・メンバー・閲覧のみは読めない**。自分の分は自分の設定で見る（D-128.58）。ただし管理者が自分自身を読むのは許す（md-self）。**「members の view を個別に付けた人」の行（K810-API-011）は DB の守りとして残す**：人ごとの「できること」を作らない（D-154.10）ので、製品の画面からは個別に付けられない。試験は DB に直に入れた権限の行で確かめる
- **読める相手**：`app.admin_target`（K-800）が null でない人＝同じ会社の人（human）・消していない・所属の status が active か suspended。止めている人は読める（md-suspended）。外した人・消した人・別の会社の人・AI・無い id は 404・E-MEM-002（欄・details を付けない・在るかを漏らさない）
- **groups**：主の所属（members.scope_id）を先に、兼ねる所属（消していない scope_memberships）を scope の作った順（created_at・id）に。消したグループは出さない。role は所属の行の role（manager・member・viewer）。**主の所属に行が無い人は role null**（管理者・会社を作った人の主の所属は所属の行を持たないことがある）。**兼務（D-154.15）**：同じ人が複数のグループで別々の役割（違う層のマネージャーを兼ねる・別の部署に作業員として入る）を持つので、groups は 1 グループ 1 行・役割はグループごと
- **assigned**：tickets＝tickets.assignee_member_id がその人・completed_at が空・消していない（**下書きも数える**：外す下見 K-815・外す K-848 と同じ数え方。外すときは下書きの担当も引き継ぐので、数えないと 1 人の画面と外す小窓の数が食い違う・まとめ役の決め）。overdue＝そのうち due_on が日本時間（Asia/Tokyo）の今日より前。stuck＝そのうち updated_at が 7 日より古い。handing＝ticket_handovers で from_member_id がその人・state が waiting（段 9 の渡し中）。完了した・消したチケットは数えない・ほかの人の担当は混ざらない
- **clone**：pc・pc_days_away は K-419 の `app.workspace_members` と同じ決め（sessions の bridge の行の max(last_seen_at)：1 日の内＝ok・それより前＝away と何日前か・行が無い＝never・閲覧のみ／依頼する側＝none）。device は同じ bridge の行のうち last_seen_at がいちばん新しい行の device_label（無ければ null）
- **login**：認証の表は読む DB の関数 `app.login_methods(auth_user_id)`（0113・K-308）をそのまま使い、passkeys・has_password・two_factor を返す（認証の表を直に読まない）。last_login_at＝その人の画面（web）のセッションの issued_at のいちばん新しい物（失効した行も数える・無ければ null）。**2 段階認証を戻す（resetMemberTwoFactor）は作らない**（D-154.3）ので、この口は戻す印を持たない
- **recent_events**：audit_events のうち、actor_member_id がその人か、target_type が members で target_id がその人の id の物。新しい順 5 件まで。返す鍵は id・action（記録の名前の元の字）・at（occurred_at の ISO 8601）・by（起こした人の名前・無ければ null）だけ。**payload・宛てのメール・ほかの会社の記録は返さない**。「記録をすべて見る」の先（K-823・K-825）は別の口
- **何も書かない**（読むだけ）。証跡を増やさない。読むときに本人確認は要らない
- **会社の文脈**：読みは withTenant の 1 取引・関数 1 回。DB の失敗は 503・E-PAGE-003（画面は md-failed の「読めません」）
- 入口の共通が先に効く：401・429・同意し直し 403・道の id の形 422・NUL 422
- 断る番号は控え帳どおり（404 は欄・details なし／503・E-PAGE-003）
