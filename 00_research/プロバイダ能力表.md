作成 2026-09-07 / 目的：**プロバイダ内蔵機能に依存した設計を作らない**ため。
Kaname は Claude / OpenAI / Gemini / ローカル LLM の 4 経路を持つと決めている。
**1 つの経路でできることを「できる」と一般化しない。**

## 2. ここから導かれる設計原則

```
   プロバイダ内蔵機能に依存した設計
        ↓
   プロバイダを変えた瞬間に壊れる
        ↓
   ★全経路で動く必要がある機能は、自前で持つ
     プロバイダ内蔵は「あれば速い最適化」に降格する
```

**これはブラウザ操作と API の関係とまったく同じ構造。**
（ブラウザ＝実装ゼロで全部に届く標準 ／ API＝速度と堅牢性の最適化）

### 自前で持つべきもの（ローカル LLM 経路でも動く必要がある）

| 機能 | 自前実装の手段 | 段階 |
|---|---|---|
| **文書解析** | TS：pdf.js / pdfium / mammoth / SheetJS<br>Python：**docling**（MIT・61k★・表とレイアウトの構造化まで） | 要判断 |
| **Web 検索** | 検索 API（Brave / Exa / SerpAPI 等）を自前で呼ぶ | 段階 4 |
| **Web フェッチ** | 自前 HTTP ＋ HTML → テキスト変換 | 段階 2 |
| **コード実行** | **Microsandbox**（Apache-2.0・8.1k★） | 段階 2 |
| **ブラウザ操作** | **Stagehand ＋ Playwright**（既に自前と決定済み） | 段階 1 |
| **MCP クライアント** | 公式 TypeScript SDK | 段階 4 |
| **プロンプトキャッシュ** | 自前のキャッシュ層 | 段階 5 |
| **担当業務（Skills 相当）** | **Markdown ＋ ツール宣言として自前で持つ**（Anthropic の Skills API に依存しない） | 段階 1 |

### プロバイダ内蔵を「使ってよい」もの（最適化として）

内蔵があれば使い、無ければ自前にフォールバックする。**どちらでも同じ結果になることを保証する。**

## 3. 画面への影響 ── 能力表を UI に出す

```
  顧客がプロバイダを選ぶ
        ↓
  能力表を引く
        ↓
  ┌ できる機能      → 通常表示
  └ できない機能    → グレーアウト ＋ 理由を表示
                      「ローカル LLM では音声の文字起こしができません。
                        文字起こし済みのテキストを貼り付けてください」
```

**黙って動かないのを禁止する。** これは「失敗したら黙って止まるを作らない」と同じ原則。

## 4. 文書解析をどう作るか ── ここが Python 採否の実質的な分かれ目

| 方式 | 品質 | 言語 | ローカル LLM 経路 | 判定 |
|---|---|---|---|---|
| **プロバイダに任せる** | 高い | — | **動かない** | 段階 1〜4 の Claude/OpenAI/Gemini 経路のみ |
| **TS で自前**（pdf.js / mammoth / SheetJS） | テキスト抽出は可。**表・レイアウトは弱い** | TS | 動く | 中核に組み込める |
| **docling を独立サービスに**（Python） | **表・レイアウト・読み順まで構造化** | Python | 動く | 型がまたがらないので drift しない |

### Kaname の用途を踏まえた評価

OJT で読ませるのは **請求書・提案書・業務マニュアル**。
つまり **表とレイアウトが意味を持つ文書**が中心で、単純なテキスト抽出では書式が再現できない。

→ **docling の優位が効く領域**。

### 現実的な結論（案）

```
  段階 1〜4    プロバイダ内蔵（Claude/OpenAI/Gemini）＋ TS の簡易抽出をフォールバックに
  段階 5       ローカル LLM 対応と同時に docling を独立サービスとして足す
```

**または、最初から docling を独立サービスとして持つ**（プロバイダ非依存を最初から徹底する場合）。
独立サービスなので型がまたがらず、中核は TS のまま保てる。

## 5. 「Python が要るか」の再評価（能力表を踏まえて）

| 機能 | プロバイダ内蔵で足りるか | ローカル LLM 経路 | Python が要るか |
|---|---|---|---|
| 文書解析 | 足りる（3 経路） | **足りない** | **表・レイアウトが要るなら docling** |
| 音声の文字起こし | OpenAI / Gemini なら足りる | 足りない | faster-whisper（段階 5） |
| Web 検索 | 足りる（3 経路） | 足りない | **不要**（検索 API を TS から呼ぶ） |
| コード実行 | 足りる（3 経路） | 足りない | **不要**（Microsandbox は Rust・API で呼ぶ） |
| ブラウザ操作 | — | — | **不要**（Stagehand は TS） |
| 記憶・RAG | — | — | **要判断**（自前 pgvector なら不要 / mem0 なら要る） |

**Python が本当に必要になるのは 3 つだけ：文書解析（docling）・音声（faster-whisper）・記憶（mem0 を使う場合）。**
**3 つとも「独立サービス」として切り出せる。** 中核を TS に保ったまま足せる。

---

## 6. この表の使い方

- **新しい機能を設計するたびに、この表に行を足す。** 4 経路すべてで動くかを確認する
- 「プロバイダ内蔵で足りる」と書いた機能は、**ローカル LLM 経路で必ず代替を用意する**
- 代替が無い機能は、**画面でグレーアウトし理由を出す**（黙って動かないのを禁止）
