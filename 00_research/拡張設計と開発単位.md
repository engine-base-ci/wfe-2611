# 拡張設計と開発単位 ── 後から足しても壊れない構造

作成 2026-09-07
目的：**先に主要部分を作り、後から拡張する。そのとき先の実装を壊さない。**
これを気合いではなく構造で担保する。

---

## 1. 原則 ── 「後で N 個に増えるもの」は、1 個の時点で N 個用に作る

```
  ✗ 壊れる作り方
     ブラウザ操作を1つ作る → 後でAPI連携を足す
     → アクションの呼び出し口が2種類になる
     → 承認・証跡・ポリシー・課金を2箇所で書くことになる
     → 3つ目を足すと3箇所。漏れが出る

  ✓ 壊れない作り方
     アクションの抽象を先に作る（実装は1つだけ）
     → 承認・証跡・ポリシー・課金は抽象の側に1回だけ書く
     → 2つ目・3つ目は「実装を足す」だけ。既存は1行も変わらない
```

### 投機的な抽象化はしない

抽象化するのは **要件定義で「将来 N 個になる」と明示されているものだけ**。
想像で抽象化しない。Kaname は要件が固まっているので、増えるものが分かっている。

## 2. 拡張点リスト ── 先に空けておく穴（12 箇所）

| # | 拡張点 | 最初の実装 | 後から増えるもの | 抽象を先に作る理由 |
|---|---|---|---|---|
| **E1** | **アクション種別** | ブラウザ操作 | API/MCP・コード実行・ローカル・人へのハンドオフ | 承認・証跡・ポリシー・課金・サービス台帳判定を**抽象側に 1 回だけ**書く |
| **E2** | **LLM プロバイダ** | Claude | OpenAI・Gemini・ローカル LLM | 能力表・フォールバック・課金計測を 1 箇所に |
| **E3** | **実行経路** | Bridge | BYOK・運営マネージド・ローカル | 経路解決を 1 関数に（Atelier `llm_route` 相当） |
| **E4** | **台帳の型** | ファネル型 | 取引型・将来の型 | 動的スキーマの解決・描画・クエリ生成を型に依存させない |
| **E5** | **スコープ層** | 個人 | 会社・部署・運営 | 「近い層が勝つ」の解決ロジックを 1 箇所に。後から層を足しても解決は変わらない |
| **E6** | **トリガー種別** | 手動 | 時間（cron）・イベント | 発火 → タスク生成の経路を共通化 |
| **E7** | **通知チャネル** | アプリ内 | メール・Slack・LINE・プッシュ | 宛先解決と本文生成を分離 |
| **E8** | **承認ポリシー** | auto / approve / off | 段階承認・金額しきい値・複数承認者 | ポリシー判定を宣言的に |
| **E9** | **担当業務** | 数個 | 無制限 | 定義はデータ。コードに書かない |
| **E10** | **画面** | 8 枚 | 追加画面 | 画面固有ロジックを持たせない。全部 API を叩くだけ |
| **E11** | **課金プラン** | 3 プラン | エンタープライズ・従量 | 制限を「数量のデータ」として持つ。プランごとの分岐を書かない |
| **E12** | **クライアント** | Web | ネイティブアプリ・Bridge | API を唯一の入口にする |

**この 12 箇所だけは、実装が 1 つの時点でも抽象を作る。**
それ以外は素直に書く（YAGNI）。

## 3. データモデルの前方互換 ── 後から足せる形にする

### 後から足すのが簡単なもの
- 列の追加（NULL 許容 or デフォルト付き）
- テーブルの追加
- インデックスの追加

### 後から変えるのが地獄なもの（最初から正しく作る）

| 項目 | 最初から入れる | 入れないとどうなるか |
|---|---|---|
| **`tenant_id`** | **全テーブルに必ず** | 後から入れるとデータ移行 ＋ 全 RLS 書き直し |
| **`scope`（4 層）** | 共有され得るもの全部に | 後から共有機能を足すと全行の意味が変わる |
| **`created_by` / `updated_by` / `created_at` / `updated_at`** | 全テーブルに | 証跡が後から作れない |
| **`deleted_at`（論理削除）** | 消してはいけないものに | 物理削除すると監査で復元できない |
| **関連の多重度** | 1 対多で足りても**中間テーブルを足せる形**にしておく | 1 対多を多対多に変えるのは全面書き直し |
| **enum ではなくマスタテーブル** | 値が増えるものは全部 | enum に値を足すのは migration ＋ 型再生成 ＋ 全分岐の見直し |
| **バージョン列**（担当業務・台帳定義・目標） | 履歴が要るもの全部 | 「いつ何が変わったか」が後から作れない |

### 特に：`id` は UUID にする
後からテナント分割・シャーディング・データ移行をするとき、連番だと衝突する。

## 4. API の前方互換

| ルール | 内容 |
|---|---|
| **追加は自由、削除と型変更は禁止** | フィールド追加は非破壊。削除・リネーム・型変更は破壊 |
| **OpenAPI で契約を固定** | CI で破壊的変更を検出して fail |
| **バージョンは URL に持つ**（`/v1/`） | どうしても破壊が要るときの逃げ道 |
| **レスポンスは常にオブジェクト** | 配列を直接返すと、後からメタ情報（ページング等）を足せない |
| **enum は文字列で返す** | 数値だと値を足したとき意味が変わる |
| **不明なフィールドは無視する**（クライアント側） | サーバーが先に進んでもクライアントが壊れない |

## 5. 開発の単位 ── 垂直スライス

### 画面単位・API 単位で作らない

```
  ✗ 横に切る
     Week1: 全部のテーブルを作る
     Week2: 全部のAPIを作る
     Week3: 全部の画面を作る
     → 3週目まで何も動かない。触れない。漏れが最後にまとめて出る（旧jobrainの死因）

  ✓ 縦に切る（垂直スライス）
     Slice1: 商談を登録して、一覧で見えて、目標に反映される
             （テーブル1〜3 + API 3〜8 + 画面1〜2 + テスト）
     → 2〜4日で動くものができる。触れる。すぐ直せる
```

### 1 スライスの定義

**「1 つの業務が最後まで通る」単位。** 画面単体ではない。

| 含むもの | 目安 |
|---|---|
| テーブル | 1〜3 個 |
| API | 3〜8 本 |
| 画面 | 1〜2 枚 |
| L1 テスト行 | 20〜40 行 |
| 実装期間 | **2〜4 日** |
| **確認にかかる時間** | **15〜30 分**（高本さんが実際に触る） |
| PR | **1 スライス ＝ 1 PR** |

### なぜこのサイズか

| サイズ | 問題 |
|---|---|
| 大きすぎ（1 週間超） | 触る範囲が広くて**漏れる**。レビューが雑になる。直すコストが上がる |
| 小さすぎ（半日） | 触っても価値が分からない。**確認疲れ**を起こす |
| **2〜4 日 / 確認 15〜30 分** | 一度に頭に入る。直しがすぐ効く |

## 6. 1 スライスの進み方（毎回同じ手順）

```
  ① 設計       スライスの範囲・触る拡張点・L1テスト行を先に書く
       ↓
  ② 実装       tickets.json の files_changed_predicted を守る
       ↓
  ③ L1テスト   実装者（Claude）が staging で全行を実行する
       ↓
  ④ ★実機確認  高本さんが実際に触る（15〜30分）
       ↓
  ⑤ 判定       OK → 次のスライス ／ NG → 直して③へ戻る
       ↓
  ⑥ 記録       出た問題を「この種の壊れ方を次に検出できる観点」として
                テスト正本に行を足してから完了（Atelier 絶対ルール20）
```

**④を飛ばさない。** 「テストが緑だから完了」を禁止する（旧 jobrain の死因）。

### 確認しやすくするための工夫

| 工夫 | 内容 |
|---|---|
| **確認手順を私が書く** | 「①ここを開く ②これを入力 ③この表示になるはず」を 5〜10 手順で |
| **実データで確認する** | 高本さんの実際の商談・請求データを使う（テストモードで安全に） |
| **前スライスの回帰も 1 行だけ入れる** | 「前に作ったこれがまだ動くか」を毎回 1〜2 行だけ確認 |
| **確認できない項目は BLOCKED として残す** | 黙って飛ばさない |

## 7. 後から要望が来たときの判定（これで壊れなくなる）

```
  「これも欲しい」が来た
        ↓
  拡張点リスト（12 箇所）のどれかに収まるか？
        ↓
  ┌ YES → 設定・データの追加で済む。実装不要 or 局所的
  │        例：新しい担当業務、新しい台帳の段階、新しい通知先
  │
  └ NO  → 新しい拡張点が要る＝設計変更
           gap-tracker に登録し、どの段階でやるかを決めてから着手
           ★その場では作らない
```

**この判定を挟むだけで、「後から足して壊れる」が構造的に防げます。**
