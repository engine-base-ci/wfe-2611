# Kaname 実装フェーズ

> 何を今作り、何を後に回すかの正本。迷ったら **`00-product-definition.md` の製品憲法**
> （「それは検査層を強くするか？」）と、この文書のフェーズ表だけで判定する。

- 最終更新: 2026-10-31
- 前提: 技術方針・層構造・製品憲法は `00-product-definition.md` を正とする

---

## 1. 順序を決める原則

```
1. リスクの高い順に潰す。機能の多い順ではない
2. 1フェーズ = 1つの問いに答える。答えが出るまで次に行かない
3. 後付けできないものだけ、最初から入れる
4. それ以外は「要らない」ではなく「まだ」
```

### リスクの大きさ

| | リスク | 理由 |
|---|---|---|
| **検査層が成立するか** | ★★★★★ | 製品価値の100%。未検証 |
| **昇格ロジックが回るか** | ★★★★★ | 唯一の堀。回らなければ模倣される |
| **他人が使うか** | ★★★★ | 最大の未検証仮定 |
| テナント分離 | ★★★ | 事故ると他社データ漏洩。ただし技術的な解はある |
| チケット管理UI | ☆ | 誰でも作れる。ただ面倒なだけ |

---

## 2. ⚠️ 後付け不可リスト（Phase 1 から必ず入れる）

後から入れると全データの作り直しになるもの。**ここだけは妥協しない。**

| | 内容 | 後付けすると |
|---|---|---|
| 1 | **`tenant_id` を全テーブルに** | マルチテナント化で全テーブル移行。事故る |
| 2 | **検査項目の「出所」**（①個人/②部署/③会社/④共通） | 解約時に顧客のものと弊社のものを分離できない |
| 3 | **監査ログ**（誰が・いつ・何を・なぜ） | 過去分は永久に作れない。承認証跡が成立しない |
| 4 | **成果物のバージョン** | 「何を承認したか」が特定できない |
| 5 | **作成AIと検査AIの分離** | 一体で作ると分離に全面改修。しかも形骸化が検出できない |
| 6 | **検査項目は構造化データ**（ベクトルに入れない） | 説明可能性が消える。「なぜ落ちたか」が言えない |
| 7 | **却下理由を1行で残す導線** | 昇格ロジックの学習データが取れない＝堀が生えない |

## 3. フェーズ表

| Phase | 問い | 期間目安 | 要るもの |
|---|---|---|---|
| **0** | 検査層は成立するか | **1日** | スクリプトだけ。DB・UI・ライセンス判断不要 |
| **1** | ループが1周回るか | 〜2週 | 最小DB ＋ 1画面 ＋ 作成/検査AI分離 |
| **2** | 自分以外の1人が使うか | 〜2週 | 認証、ユーザー2人、担当と承認者の分離 |
| **3** | 顧客1社に入れるか | 〜1ヶ月 | RLS実運用、ロール、部署、プリセット投入、介在時間の計測 |
| **4** | 蓄積が効くか | 〜2ヶ月 | ナレッジ4層、お手本(pgvector)、適用・合成ロジック |
| **5** | 横断で複利が回るか | 〜2ヶ月 | 横断統計（オプトイン）、観点の昇格審査、業種フィルタ |
| **6** | 顧客の顧客を入れられるか | 〜1ヶ月 | クライアントロール、依頼→チケット化 |
| **7** | 目標と接続できるか | 〜1ヶ月 | 実行記録と目標の接続、Driver Tree |
| **8** | セルフサーブにできるか | 条件達成後 | サインアップ、課金、プラン、オンボーディング |

**Phase 2 までで止まる可能性が高い。** そこで止まったら、それは失敗ではなく**最短で分かった**ということ。

## Phase 0：検査層は成立するか（1日）

### 目的
製品価値の100%が検査層。**ここが通らなければ、他は全部無意味。**

### やること

| | |
|---|---|
| 入力 | 実物の成果物1つ（提案書 / 契約書 / メール）＋ **意図的に欠陥を入れた版** |
| 検査項目 | 10個だけ。**全部「状態」で書く**（存在チェック禁止） |
| 構成 | 作成AIと検査AIを分離。検査AIには**成果物と項目だけ**渡す（意図・経緯を渡さない） |
| 要らないもの | DB / UI / Postgres / better-auth / ライセンス判断 / チケット |

### 測る3つ

| | 検証 | 外れたら |
|---|---|---|
| 1 | 検査AIの判定が人間の判定と一致するか | **製品が成立しない。** 根本から作り直し |
| 2 | 空の価格表を入れたら通ってしまうか（報酬ハック） | 「状態で書く」が機能していない。項目の書き方を再設計 |
| 3 | 却下理由を項目に昇格できるか | **堀が消える。** 差別化を別の場所に置き直す |

### Go条件
1 が実用水準（人間の判定と概ね一致）、かつ 2 がハックされない、かつ 3 が言語化できる。

### 補足
成果物は**できれば提案書とメールの両方**。頻度の違いが堀の速度に直結するため、
第一業務の選定（提案書 or メール）をこの結果で決める。

## Phase 1：ループが1周回るか（〜2週）

### 目的
**自分1人が、1チケットを完走する。**

### 入れるもの

```
チケット     1枚（単層。親子孫はまだ入れない）
設計欄       何をするチケットか（Lexical）
検査項目     AIが起草 → 人が消す/直す/承認（空のフォームは出さない）
作成AI       成果物を作る
検査AI       別プロセス。成果物と項目だけで判定
承認          緑でも承認必須
却下          理由を1行で記録 → 検査項目に昇格
ログ          誰が・いつ・何を参照し・どう実行したか
```

後付け不可リストの 1〜7 を**全部この時点で入れる**。

### 入れないもの
親子孫 / 複数ユーザー / ロール / 部署 / ナレッジ4層 / クライアント / 盤UI / ガント /
通知 / 検索 / プラン / 課金 / 複数業務スキル / ベクトル検索

### Go条件
自分で5回連続、ループが1周回る。かつ **5回目の指摘が1回目より減っている**（昇格が効いている）。

### 計測
| | |
|---|---|
| 1周あたりの指摘件数の推移 | 減っていれば昇格ロジックが効いている |
| 検査項目の累積件数 | 増えていなければ①が回っていない |

---

## Phase 2：自分以外の1人が使うか（〜2週）

### 目的
**最大の未検証仮定を潰す。** 「117スキルを作者以外が使って価値を感じるか」。

### 入れるもの
認証（better-auth）／ ユーザー2人以上 ／ 担当と承認者の分離 ／ エクスポート

### 入れないもの
部署 / クライアントロール / ナレッジ4層 / 横断統計 / 課金

### Go条件
**自分ではない人間が1人、1チケットを完走する。** かつ「また使いたい」と言う。

### ここで止まったら
設計が間違っているのではなく、**価値の伝え方か対象業務が間違っている**可能性が高い。
Phase 0 の結果に戻って第一業務を変える。

---

## Phase 3：顧客1社に入れるか（〜1ヶ月）

### 目的
提供モデル（人間が入ってCS）で、1社目を回す。

### 入れるもの
RLS の実運用 ／ ロール（メンバー / 管理者） ／ 部署 ／
**プリセット投入**（117スキルから1業務分を移植） ／ **介在時間の計測**

### 絶対ルール（`00-product-definition.md` 製品憲法 8・9）
- 顧客カスタムを製品に逆流させない（**3社ルール**）
- **日々の成果物の添削を自社の人間がやらない**（検証が汚染される）

### Go条件
顧客が自分たちで日々回している。かつ**自社の介在時間が月ごとに減っている**。

### 計測
**人間の介在時間（顧客別・月次）。** これが減らなければ製品は機能していない。

---

## Phase 4：蓄積が効くか（〜2ヶ月）

### 目的
堀を1社の中で深くする。

### 入れるもの
ナレッジ4層（①②③④）／ **お手本（pgvector）** ／ 例示型の蓄積 ／
**適用ロジック**（いつどの項目を出すか）／ **合成・衝突解決**（①②③④が矛盾したとき）／
形骸化検知（通ったのに失敗した）

**ここで初めてベクトルが必要になる。** Phase 3 までは不要。

### Go条件
検査項目が数百件になっても、ノイズで使われなくならない（適用ロジックが効いている）。

---

## Phase 5：横断で複利が回るか（〜2ヶ月）

### 目的
**moat を線形から複利に変える。** 顧客数に比例して④が強くなる状態。

### 入れるもの
横断統計（**オプトイン**）／ 観点の昇格審査（匿名化・一般化・重複排除）／ 業種フィルタ

### 絶対ルール
顧客の成果物そのものは使わない。使うのは「抜けていた観点」のテキストだけ。契約に明記。

### Go条件
2社目以降の**初日の検査品質**が、1社目の初日より明確に高い。

---

## Phase 6：顧客の顧客を入れられるか（〜1ヶ月）

クライアントロール ／ 依頼 → チケット化 ／ 顧客向けビュー ／ 権限の最小化

**RLS が Phase 3 で正しく入っていることが前提。** ここで初めて外部ユーザーが入るため、
テナント分離のミスが実害になる。

---

## Phase 7：目標と接続できるか（〜1ヶ月）

実行記録（チケット＝実際にやったこと）と目標の接続 ／ Driver Tree ／ 達成管理

**順序を守る。** 目標を先に作ると、分解した先に実行データが無く「わかるけど他でもできる」になる
（`00-product-definition.md` 7.6）。

---

## Phase 8：セルフサーブにできるか

### 着手条件
**顧客別の介在時間が閾値を下回ったとき。** 売上やユーザー数ではなく、これで判断する。

### 入れるもの
サインアップ ／ 課金 ／ プラン（軸＝任せる業務数）／ セルフオンボーディング

---

## 4. 絶対に後回しにするもの（全フェーズ共通）

`00-product-definition.md`「やらないこと」の実装版。

| | 理由 |
|---|---|
| 盤UI / ガント / 高度な通知 / 全文検索 | **チケット管理の機能競争に参加しない。** Linear/Jira と張り合わない |
| 親子孫の多階層 | Phase 1 では単層で足りる。必要になってから |
| 複数業務スキルの同時対応 | 1業務が回ってから。スキルは後から無限に追加できる |
| プラン・課金 | Phase 8。価値が実証される前に引くと必ず引き直す |
| モバイルアプリ | 承認だけなら Web で足りる |
| オンプレ提供 | 要求が来てから。**④はクラウドのみ**の設計で対応可 |
