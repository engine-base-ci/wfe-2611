# Kaname 製品定義

> この文書は、Kaname が「何であって、何でないか」を固定するためのもの。
> 機能を足すかどうか迷ったら、ここの **製品憲法** だけで判定する。
> ここに書かれていない理由で機能を足さない。

- 最終更新: 2026-10-31
- 状態: ドラフト（①②③④の潰し込みを完了、未検証仮定あり）

---

## 1. 一文定義

> **Kaname は、AIが作った仕事を「合格か」を機械で判定してから人に回すツール。**

ユーザーに対して言う言葉はこれ。

> **同じ指摘を、二度しなくて済む。**

「業務にCIを入れる」は作る側の言葉。顧客には使わない（中小企業に通じない）。

---

## 2. 既存ツールとの境界

| | 何をするもの |
|---|---|
| Notion | 情報を**置く場所** |
| Slack | 会話を**する場所** |
| Backlog / Jira / Linear | タスクを**置く場所** |
| Notion AI / Copilot など | 成果物を**作る**（検査はされない） |
| **Kaname** | 成果物が**合格かを判定してから人に回す** |

### 空いている理由

2026年の痛みは「AIで作れない」ではなく **「AIで作れるようになった結果、確認が全部人間に残った」**。
既存SaaSのAIは「作る」で止まっている。**検査の層だけが空いている。**

### 既存SaaSが構造的に入れない理由

各社のエージェントは、自社のデータ内しか見えない。**やっていない仕事はデータを生まないので、穴が見えない。**
横断の合格条件を書けるのは、特定SaaSに属していないツールだけ。

---

## 3. 誰の・何の痛みか

- フリーランス / 個人
- 一人社長
- 中小 5〜30名（専任のいない機能がある会社）

痛み: **専任がいない機能が穴になっていて、気づいた時には手遅れ**。
そして中小の本質的なボトルネック: **すべての判断が社長を通る。社長が止まると会社が止まる。**

課金軸（プラン設計の軸）: **何部門・何業務を任せるか。**

| | |
|---|---|
| 個人 / フリーランス | 1業務 |
| 一人社長 | 2〜3業務 |
| 中小 5〜30名 | 全業務 ＋ 自社業務のスキル化 |

---

## 4. 役割分担（自律実行はしない）

| 人間 | Kaname |
|---|---|
| 決める | 調べる |
| やらないと決める | 作る・下書く |
| **合格条件を決める** | 気づかせる（穴を指摘する） |
| **承認する** | 基準に沿って実行する |

**意思決定は常に人間に返す。** 自律実行は、技術的な可否以前に**ビジネスモデル上やってはいけない**
（人間の承認/却下が消えると、判断が蓄積しなくなり moat が消える）。

## 5. 層構造

```
┌─ レイヤーA：基盤 ＝ これが製品 ────────────────────────┐
│  チケット     親子孫 / 担当 / 管理者 / 期限 / 状態遷移    │
│  設計         何をするチケットか                         │
│  完了条件     ← チケットに属する                         │
│  検査項目     ← チケットに属する                         │
│  参照         何を引用するか（ナレッジ層から）            │
│  実行         AIが作る                                  │
│  承認         人が見て、直す / OKを出す                   │
│  ログ         誰がいつ何を参照し、どう実行したか           │
│  スレッド     担当間のやり取り / AIとの対話               │
│  決定         決定事項 → 設計へ反映 / 新チケットを切る     │
│  ナレッジ     個人 / 部署 / 会社 の3層                   │
│  ロール       メンバー / 管理者 / クライアント             │
└────────────────────────────────────────────────────────┘
                          ↑ 差し込む
┌─ レイヤーB：スキル ＝ コンテンツ。後から無限に追加 ──────┐
│  提案書を作る / 見積を出す / 契約をレビューする /         │
│  メールを返す / 記事を書く / 請求書を出す …               │
│                                                        │
│  スキルが供給するもの：                                  │
│    1. やり方（手順）                                    │
│    2. 検査項目のプリセット                               │
└────────────────────────────────────────────────────────┘
```

**検査項目はチケットに属する。スキルにも成果物タイプにも属さない。**
既存の117スキルは、レイヤーB の初期カタログ。MVPに全部要らない。

## 6. 1チケットの流れ

```
1. チケットを切る            担当 / 管理者 / 期限 / 親子関係
2. 設計を書く                何をするチケットか
3. 合格条件が入る            AIが起草。人は消す / 直す / 承認するだけ
4. 作成AIが作る              参照した資料・実行経緯がログに残る
5. 検査AIが判定する          作成意図を知らない状態で、成果物と項目だけで判定
6. 落ちたら自動で直して再検査
7. 人が承認する              緑でも承認は必須
8. 却下したら                理由が合格条件に昇格する（次から自動で防がれる）
9. 通ったのに差し戻されたら   抜けていた観点が合格条件に昇格する
```

## 7. 蓄積（moat）

### 2段ある

| 段 | 内容 | 真似できない理由 |
|---|---|---|
| 1段目 | **プリセットの質**（117スキル由来） | 実務を数年やらないと作れない。時間でしか買えない |
| 2段目 | **その会社固有の合格条件とお手本** | 他社に持ち出せない。乗り換えると品質基準がゼロに戻る |

**乗り換えコストが、使用時間に比例して上がる。**
Notion に溜まるのはドキュメント（エクスポート可能）。Kaname に溜まるのは判断の基準（形式が製品固有）。

### 蓄積は二本立て

| 直しの種類 | 例 | 蓄積の形 | 人間がやること |
|---|---|---|---|
| **ルール型** | 「実績スライドが抜けてる」「損害賠償の上限がない」 | **検査項目** | 直す |
| **例示型** | 「なんとなく硬い」「トーンが違う」 | **お手本**（承認済み成果物を基準登録） | OKを出す |

どちらも**人間の入力コストはゼロ**。直す / OKを出す、という必ずやる行為だけで溜まる。

## 8. 製品憲法（迷ったらこれだけで判定する）

### 判定基準

> **「それは検査層を強くするか？」**

### 絶対ルール

1. **人間が白紙から合格条件を書く「入力」画面は作らない。**
   「編集」画面は持つが、常にAIが埋めた状態から始まる。空のフォームを人間に見せない。
2. **検査項目ゼロのチケットを作らせない。**
   設計を書いた時点でAIが必ず起草する。0件にするには人が明示的に「検査なし」を選ぶ。
3. **作成AIと検査AIを分離する。** 同じコンテキストで「作る→自己検査」をさせない。
4. **検査項目は「存在」ではなく「状態」で書く。**
   NG: 「価格表がある」 / OK: 「価格表の各行に単価・数量・小計があり、合計が本文の金額と一致する」
5. **緑でも人の承認を必須にする。** 検査通過 ＝ 納品OK ではない。**検査通過 ＝ 人が読む価値がある状態。**
6. **「ミスがなくなる」「AIが品質を保証する」と言わない。** 約束は「同じミスを二度しない」まで。
7. **AGPL / GPL / SSPL のコードを製品の構成要素にしない。**

### 引き受ける業務の条件（3つ全部満たすものだけ）

1. 合格条件を文で書ける（有無・記載・数値の整合・前回との矛盾 で判定できる要素が過半）
2. その合格条件が会社ごとに違う（＝既存SaaSがフォームで強制できない。できるものは既に取られている）
3. 間違えると社外に損害が出る（社内メモは対象外）

1つでも欠けたら引き受けない。「将来対応」とも言わない。

### やらないこと（明示）

- **チケット管理の機能競争に参加しない。** 盤・ガント・通知・検索の作り込みで Linear / Jira と張り合わない
- ナレッジ管理ツールとして Notion と張り合わない
- 請求書・給与・申告（既存ツールがフォームで強制済み。検査層の価値が出ない）
- 創造性が本質の成果物の品質判定（企画のアイデア等）

## 9. 技術方針

### TTP の正しい形

| | |
|---|---|
| ⭕️ パクる | **設計**。情報構造 / 操作体系 / UXパターン / データモデルの考え方 |
| ❌ パクらない | コードのコピー / AGPL・GPL製品のフォーク / ピクセル単位の模倣 / アイコン・イラスト・商標 |

アイデア・機能・操作方法は著作権で保護されない。コードと表現は保護される。

### ライセンス調査結果（2026-10 時点）

#### チケット管理 / プロジェクト管理 OSS

| プロダクト | ライセンス | 保守状況 | 判定 |
|---|---|---|---|
| **Planka** | **Fair Use License**（source-available / fair-code） | 活発 | ❌ **第三者へのホスティング提供を明示的に禁止**。最も危険 |
| Plane | AGPL-3.0 | 活発 | ❌ ネットワーク条項。改変してSaaS提供すると改変部分の開示義務 |
| Taiga / Vikunja / Worklenz / Leantime | AGPL-3.0 | — | ❌ |
| Redmine (GPL-v2) / OpenProject (GPL-v3) | GPL | 活発 | ❌ |
| Focalboard | AGPL-3.0（かつてMIT） | **2024-06 に Mattermost が開発停止** | ❌ |
| Kanboard | MIT | **maintenance mode**（新機能なし） | 🟡 参考のみ |
| **Wekan** | **MIT** | 活発（v8.35 / 2026-02、週次リリース） | 🟡 Meteor 製。今から乗るのは技術負債 |
| **Gitea** | **MIT** | 活発（v1.26.4 / 2026-06） | 🟡 Go製で言語が違う。**設計の教科書としては最良**（issues / kanban / milestones） |
| **Huly** | **EPL-2.0** | 活発 | 🟡→⭕️寄り。ファイル単位の弱いコピーレフトで、義務のトリガーは「**配布**」であり**ネットワーク提供ではない**。ビジョンが最も近い（Linear＋Notion＋Slack 統合）が巨大 |

#### エディタ

| | ライセンス | 判定 |
|---|---|---|
| **Lexical** (Meta) | **MIT**（LICENSE 直接確認済み） | ⭕️ 採用 |
| ProseMirror | MIT | ⭕️ 代替候補 |
| TipTap | core MIT / Pro はサブスク必須 | ❌ 「エンドユーザーが自分のEnd Productを作れる製品」禁止条項あり。プラットフォーム製品に抵触リスク |
| BlockNote | base OSS / 商用は別ライセンスのケースあり / XL は別 | ❌ |

#### 認証・権限・マルチテナント

| | ライセンス | 判定 |
|---|---|---|
| **better-auth** | **MIT** | ⭕️ **採用**。TSライブラリ。organizations / SSO / SCIM を持つ |
| Keycloak | **Apache-2.0**（有料機能の囲い込みなし） | ⭕️ 将来SSO必須要件が来たら。realms ＋ Organizations で B2B マルチテナント。ただし重い |
| ZITADEL | ⚠️ **v2 まで Apache-2.0 → v3 で AGPL-3.0 に移行** | ❌ バージョンで変わる。採用しない |

> **外部サービスとして使うもの（Firebase / Supabase Cloud 等）はライセンス問題ではない。**
> ライセンスが問題になるのは「自社製品に同梱・改変して提供するコード」だけ。

### 何を流用し、何を流用しないか

**チケット管理アプリ全体を流用する価値は低い。**

理由: チケット管理OSSの重さは **UI と周辺機能**（盤・ガント・通知・検索・各種インテグレーション）にある。
データモデル自体は Postgres のテーブル10枚程度で済む。
そして **Kaname はその豪華な管理UIを作らないと決めている**（製品憲法・やらないこと）。
→ **流用したい「重い部分」が、要らないと決めた部分と一致している。**

| | 方針 |
|---|---|
| チケット管理アプリ（Plane / Huly / Wekan 等） | **流用しない。** 設計を読む対象。特に **Huly のデータモデル**（チケット＋ドキュメント＋チャット統合の唯一のOSS実装）と **Gitea の issues 周り** を教科書にする |
| UI部品（表・盤・DnD・エディタ） | **流用する。** パーミッシブのみ |
| **認証・権限・マルチテナント** | **流用する。** ここを自作するとSaaSで最も事故る（テナント間のデータ漏洩）。**better-auth（MIT）＋ Postgres RLS** |
| **検査層** | **自作。** 差別化なのでOSSに頼らない |

### 採用スタック

| 層 | 採用 | ライセンス |
|---|---|---|
| DB | **Postgres**（決定） | — |
| フロント | React + TypeScript + Vite | MIT |
| UI | shadcn/ui + Radix + Tailwind | MIT |
| 表・盤 | TanStack Table + dnd-kit | MIT |
| エディタ（設計欄） | **Lexical** | MIT |
| 認証・組織・権限 | **better-auth** ＋ Postgres RLS | MIT |
| **検査層（独自CI）** | **全部自作** | 差別化のためOSSに頼らない |

Postgres を選んだ理由: 親子孫・履歴・監査ログ・権限マトリクスが全部関係データ。
RLS でロール別アクセス制御（クライアント招待含む）をDB層で担保できる。

### チケット基盤の方針

**極小自作。** チケットは「設計＋検査項目＋成果物＋ログ」を持つ最小構造だけ作る。
豪華な管理UI（盤・ガント・通知・検索）は作らない。開発力を検査層に集中させる。

## 10. 未検証の最大仮定

> **117スキルを、作者以外の人間が使って価値を感じるかどうか、まだ誰も確認していない。**

これが外れると製品全体が成立しない。
したがって MVP の目的は「機能を作ること」ではなく **「他人1人に1チケットを完走させること」**。

### moat の成立条件

> **「指摘が項目に変わる」ループが実際に回ること。**

回らなければプリセットだけの製品になり、半年で模倣される。**moatの全部が2段目にかかっている。**

### 検証方法（聞くのではなく、ログで取る）

製品に「直した理由を1行残す」導線を最初から入れる。
→ ルール型 / 例示型の実比率がログで出る。推測も自己申告も不要になる。

## 11. 要棚卸し（商用SaaS化の前提作業）

| | 内容 | リスク |
|---|---|---|
| 1 | **`proposal` スキルの実績base64画像** | 過去クライアントの実績画像を製品テンプレに同梱すると守秘義務違反・権利侵害 |
| 2 | 117スキル全体の他者由来素材 | テンプレ・画像・文面に第三者の権利物が混ざっていないか |
| 3 | OSS/ライブラリのライセンス | 採用時に必ず LICENSE 原文を確認（Supabase は情報源が Apache-2.0 / MIT で割れていた。Planka の Fair Use License も原文確認が必要） |

> **Twenty（`twenty-metadata` / `twenty-records` スキル）は対象外。** ユーザー確認済みで、既に使っていない。
> ただしスキルファイルはディスクに残っているため、**製品の構成要素には持ち込まない**（Twenty は AGPL-3.0）。

> 本番投入前に、AGPL周りは専門家レビューを推奨。

## 付録：潰し込みの記録（①〜④）

| | 問題 | 結論 |
|---|---|---|
| ① | 合格条件を誰も書かない | プリセット（初日）→ 学習（却下/承認から自動蓄積）。入力画面を作らない。ルール型＋例示型の二本立て |
| ② | 検査できない成果物がある | 検査項目はチケットに属するので基盤は成果物タイプに依存しない。真のリスクは「ゼロ件チケットが多いとコモディティに見える」→ ゼロ件を作らせない |
| ③ | 検査が形骸化する | 作成/検査の分離・状態で書く・緑でも承認必須・「通ったのに失敗した」の逆学習。完全には防げないので約束を「同じミスを二度しない」に留める |
| ④ | チケットUI自作のコスト | 極小自作 ＋ パーミッシブライブラリ ＋ 設計のTTP。Postgres 採用 |

①の根拠と③の実例は、どちらも `engineering-rules/rules/common/test-ladder.md` の
「2026-09-02 に本番実走で5件の穴」の記述。テストは存在し緑だったが観点がなく漏れた。
**①を解いても③は残る**ため、別問題として個別に潰している。
